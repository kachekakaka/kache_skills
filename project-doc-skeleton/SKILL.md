# 项目文档骨架管理

## 保持职责单一

只负责：

- 固定目录和条件目录；
- 文档入口与实际链接可达性；
- 已确认的文件职责与承接路径；
- 待办、活动方案和归档的机械生命周期；
- 测试治理结构及通用机械资产；
- 用户最终确认后的结构迁移和机械修复。

不负责判断文档内容是否符合代码、配置或产品行为。需要检查事实时建议用户显式调用
`$project-doc-consistency check`；需要同步可直接证明的事实时建议显式调用
`$project-doc-consistency sync`。术语、`CONTEXT.md`、ADR 或语义取舍交由用户另行显式选择语义裁决
方式；环境中已经提供 `$grill-with-docs` 时可以把它作为可选方式，否则直接列出待决问题。不得假定外部
Skill 存在，也不得自动触发另一个 Skill。

## 先执行适用性与授权检查

1. 读取目标路径适用的全部 `AGENTS.md`。
2. 把显式调用理解为只读调查授权，不理解为文件修改授权。
3. 发现 `CONTEXT-MAP.md`、多个领域 `CONTEXT.md` 或明显独立的业务上下文时停止。本 Skill
   只支持单一上下文项目，不得压平多上下文结构。
4. 发现目标项目已有语言约定时，展示当前规则、建议规则和影响，询问是否变更。未确认前保留原规则；
   修改语言约定不包含批量翻译授权。
5. 不自动执行构建、测试、产品程序、真实数据操作、commit、push、PR、发布或认证。
6. 不修改产品代码，不覆盖已有工作区修改。

## 按场景读取资源

- 每次调用读取 [`references/skeleton-rules.md`](references/skeleton-rules.md)。
- 新建、首次迁移、测试结构变化或验证层级问题出现时，再读取
  [`references/testing-baseline.md`](references/testing-baseline.md)。
- 只有准备安装或审查通用资产时才读取 `assets/SoftwareTesting/` 下对应源码。安装时必须从
  `assets/SoftwareTesting/` 原样复制，禁止凭记忆重写、顺手优化或按项目改写；目标路径已存在且内容
  不同时停止并展示冲突。
- 不把 Skill 参考文件复制进目标项目；目标项目形成自己的唯一真源。

## 调查并判断场景

直接调查能够从环境查明的事实：

- 当前适用的协作规则；
- 根 README，以及现有构建、交付和公开入口的位置；
- 活动 Markdown、模块 README、测试目录和归档；
- 工作区已有修改；
- 当前骨架和文档门禁是否存在。

这里只定位入口和结构，不判断入口中的命令、产物或能力声明是否真实。

据此判断：

- 核心文档基本不存在：新项目；
- 已有代码或非标准文档：首次迁移；
- 标准骨架已存在：日常结构审查。

非空既有项目如果没有用户确认的职责映射，不实施完整迁移。建议先显式调用
`$project-doc-consistency check`；一对一且职责明确的旧文档可以在最终清单确认后原样移动，正文保持不变。

## 确认规则

先集中展示固定基线并确认一次是否采用。把互相独立、任一答案都不会改变其他问题或后续范围的未知项合并为
一份短清单，允许用户一次作答。只有存在依赖、冲突、不可恢复的结构变化，或某个答案会改变后续选项时，
才一次只询问一个真实取舍：

- 现有规则冲突；
- 条件目录是否适用；
- 旧文档的承接位置；
- 是否移动、归档或删除文档及本 Skill 管理的机械资产；
- 测试现场和验证层级；
- 无法从项目事实直接证明的结构决定。

能够调查的事实不得反问用户，也不得为了逐项留痕拆分互不依赖的确认。日常结构审查只询问新增问题；
用户明确要求全面复核时才重新审查固定基线。

新建或首次迁移在形成最终清单前，以下项目必须得到明确结果，不能用“尚未确认”占位：

1. 文档与交流语言；
2. 修改授权边界；
3. commit、push、PR 是否分别授权；
4. 构建入口与交付产物，确实没有时由用户确认“不适用”；
5. 普通验证、全量测试和正式认证的层级；
6. 测试根命名、既有目录冲突处理和精确清理边界；
7. 是否涉及真实数据或产品进程；不涉及时在 `SoftwareTesting/SAFETY.md` 明确写“不适用”。

固定规则可以随固定基线一次确认；第 4、7 项属于项目事实，无法直接证明时可以和其他互不依赖的未知项
集中询问。答案存在依赖或冲突时再逐个澄清。用户暂不确认时保持只读并报告待决项，不生成含占位结论的
骨架。

每次取得新确认后，都要与本轮已有确认和直接可见结构做一致性复核。发现可以直接证明的冲突时，一次
只展示并澄清一个冲突，不把矛盾答案带入最终清单。例如规范命令调用项目未声明的测试运行器时，不得
同时记录“外部依赖不适用”；应先确认该运行器由项目管理、由环境预置，还是改用其他入口。这里只检查
本轮确认能否同时成立，不扩展为产品事实审计。相对命令还要确认工作目录；`failed`、`blocked` 和
`inconclusive` 的触发条件不得互相重叠，不能只用“非零退出码”覆盖所有失败类型。

## 坚守内容边界

新建空项目只写：

- 标题和文件职责；
- 必要导航；
- 用户明确确认的“不适用”。

不得根据代码、配置、构建或测试自行推导并填写产品能力、实现结构、测试事实或交付事实。已有文档进行
一对一迁移时保持事实正文原样。可直接证明的事实补写与修订交给显式调用的
`$project-doc-consistency sync`。

不生成大段 TODO、目标架构、虚构能力或通用内容模板。尚未实现的目标进入待办。

`CONTEXT.md` 是条件文件。只有存在项目专属术语时，才把创建或维护需求交给用户另行选择的语义裁决
方式；没有项目专属术语时不创建，也不阻塞骨架。不得创建、编辑、移动、拆分或格式化 `CONTEXT.md`
和 ADR 内容。

发现过期、重复、冲突或职责越界的内容时，只展示位置并建议显式调用 `$project-doc-consistency check` 获取事实
证据。涉及合并、拆分、归档、删除或新承接职责的真实取舍时，列出待决问题并由用户显式选择语义裁决
方式。决定确认后，本 Skill 只实施对应结构变化。

## 形成最终变更清单

写入前列出并取得一次最终确认：

- 每个新建、改写和移动路径；
- 入口与索引变化；
- 条件目录及创建理由；
- 归档和删除目标；删除只能涉及已逐项确认的文档或本 Skill 管理的机械资产；
- 通用资产；
- 需要备份的不可恢复文件及备份位置；
- 测试层级、验证影响域和具体验证项；
- 留给其他显式 Skill 的问题。

形成清单前重新检查所有必需确认是否已有明确结果、彼此是否直接冲突。存在待决或冲突时停止，不得以
占位文案或相互矛盾的 suite 说明继续实施。

修改授权不包含 commit、push、PR 或发布。

## 安全实施

- 先建立承接位置和入口，再处理旧位置。
- 仅当修改前状态无法从 Git 或其他可靠来源精确恢复时创建外部备份。
- 未跟踪、已有未提交修改或无版本控制的内容，在移动、合并、覆盖、归档或删除前必须备份或停止询问。
- 不为新文件、纯新增入口和可可靠回退的机械链接修改默认创建备份。
- 发现旧文档中明显的凭据或真实用户数据时不复制、不回显，只报告位置；本 Skill 不承担仓库秘密扫描。
- 通用文档门禁默认安装。两个 Python 源码必须与本 Skill 的 `assets/SoftwareTesting/` 对应文件
  逐字节一致；如需改变规则，先修改并验证 Skill 资产，再重新安装，不在目标项目内制作分叉。
- 本 Skill 不创建、复用、检查或清理测试根及测试 run。
- 不得删除产品代码、配置、构建脚本、项目测试或测试根。任何文档或托管资产删除都必须在最终清单中
  逐路径确认。
- 目标冲突时停止，不覆盖。

## 验证和交接

申请命令授权前，先用普通语言说明两类门禁的目的：规则夹具验证门禁自身能否正确接受和拒绝隔离样例；
目标项目的 `T-DOC` 检查当前骨架是否满足机械规则。把精确命令、工作目录、输出和副作用集中列出，允许
用户在一次回复中分别授权。

至少：

1. 运行文档门禁的规则夹具；
2. 运行目标项目的 `T-DOC`；
3. 验证必要入口、相对链接、标题锚点和两跳可达性；
4. 比较已安装的两个文档门禁源码与 Skill 资产，确认逐字节一致；
5. 检查意外文件、绝对本地路径 warning 和旧名称残留；
6. 复核没有修改项目事实、产品代码、`CONTEXT.md` 或 ADR 内容。

未运行适用验证项时，只能报告“静态审查未发现问题”及明确的未验证范围，不得使用“骨架完整”“验证通过”
等总体结论。只有适用验证项实际通过后，才给出对应层级的通过结论。

最终报告实际结构变化、验证命令与结果、未覆盖范围、备份状态，以及未获授权的 Git 和外部操作。
