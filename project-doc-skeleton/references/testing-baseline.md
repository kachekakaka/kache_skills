## 1. 适用路线与职责边界

本参考定义标准骨架路线的测试治理。新项目或用户明确选择标准迁移时采用；结构等价的成熟项目保留自己的
测试目录、Registry schema、类别词汇和项目专用门禁。

骨架只检查测试治理的结构职责、入口、选择关系、授权边界和机械门禁，不判断产品测试是否覆盖充分、是否重复
或过度，也不把直接接线核对扩张为全项目安全认证。发现这些内容问题时形成交接。

## 2. 标准固定与条件结构

固定：

```text
SoftwareTesting/
├── README.md
├── PROTOCOL.md
├── SAFETY.md
└── doc_consistency/
    ├── README.md
    ├── test_doc_consistency.py
    └── test_doc_consistency_rules.py
```

按需：

```text
SoftwareTesting/<project-suite>/
SoftwareTesting/manual/
archive/SoftwareTesting/
```

产品命令、fixture、进程、端口和交付物必须来自用户确认或当前项目直接证据；骨架只建立承接位置，不推导产品
事实。默认不引入核心矩阵、多层快照、Release runner、产品锁、lease、二进制审计或项目级测试 manifest。

## 3. 验证层级与方案字段

### 普通验证

默认层级。按实际影响选择最小可证明范围，不自动执行完整测试集合。

### 全量测试

只有用户明确开启时进入。覆盖全部 `full`、本轮受影响的 `affected_only` 和用户明确加入的 `explicit`。

### 正式认证

只有用户明确要求时进入。包含必要全量测试、候选身份核对和结构化交接，不自动授权 commit、push、PR、
真实数据、发布或分发。

普通措辞不提升层级。clean build 是构建义务，不等于全量测试或正式认证。实际发布前仍未选择必要验证层级时
停止询问。

每份活动方案恰好各记录一次“测试层级、验证影响域、具体验证项”。没有活动方案的小修在实施前说明和最终
交接中记录同样三项。`待确认` 方案记录拟验证范围，但保存方案不授权运行命令；施工时按当前证据复核。

## 4. 标准 Registry

`docs/软件测试.md` 的机器表格固定为：

```markdown
| ID | 执行类别 | 入口 | 唯一职责 |
| --- | --- | --- | --- |
| T-DOC | full | [文档机械门禁](../SoftwareTesting/doc_consistency/README.md) | 检查标准文档骨架机械一致性 |
```

ID 使用 `T-` 前缀、大写字母、数字和连字符，不得复用当前 Registry、测试归档和可发现 Git 历史中的既有 ID。

类别：

- `full`：每次全量测试必须执行；
- `affected_only`：相关能力受影响时执行；
- `explicit`：真实数据、破坏性、联网费用或特殊环境，只有用户明确加入才执行。

标准路线中 `T-DOC` 必须存在且为 `full`。Registry 不保存日期、数量、耗时、run-id、哈希或结果。机械门禁
只检查 ID、类别、入口和非空职责，不判断测试项实际价值。

成熟项目可以使用不同 schema 和类别，只要现有机制能解释完整、受影响和显式执行的选择职责，并提供稳定入口，
就不要求改成四列表格。

## 5. 测试入口职责

### `SoftwareTesting/README.md`

链接 Protocol、Safety、Registry 和每个活动 suite README。标准路线的活动 suite README 必须直接可达。

### `SoftwareTesting/PROTOCOL.md`

保存验证层级、影响域、测试类别、构建与验证关系、结果语义、重试失效、全量与认证顺序和任务交接；不保存
项目具体命令、安全细节或动态结果。

### `SoftwareTesting/SAFETY.md`

保存测试根、真实数据保护、进程所有权、串行、输出 containment、人工清理和敏感信息规则。项目不涉及真实
数据或产品进程时，用当前证据明确写“不适用”，不要编造流程。

### Suite README

保存 Registry ID、独有触发条件、输入、fixture、工作目录、规范命令、断言、失败语义和专项清理；不复制公共
规则或动态结果。命令、依赖、覆盖声明和产物必须来自用户确认或当前项目证据。

规范命令直接调用的运行器、运行时或软件包属于 suite 依赖。项目没有提供该依赖时，确认它由项目管理、由环境
预置还是改用其他入口；不要自行安装依赖。相对命令必须明确工作目录。

失败语义按执行阶段互斥：前置条件不足通常是 `blocked`；进入可判定阶段后的断言、收集或项目错误可以是
`failed`；中断或运行器异常导致证据不可解释时是 `inconclusive`。不要只用“非零退出码”覆盖所有失败类型。

## 6. 仓库外测试现场

标准默认测试根：

```text
<项目父目录>/<项目名>_test/
```

每次运行：

```text
<项目名>_test/<run-id>/
```

默认根已存在但没有当前项目合法所有权标记时停止。已有合法标记时核对项目所有权。输出解析后必须仍位于本次
直接 run；符号链接、junction、reparse point 或路径逃逸失败关闭。

骨架只把约束写入治理文档，不提供创建、复用、检查或清理测试现场的工具。输出默认保留；用户明确要求清理时，
重新验证所有权、展示精确绝对路径并另行取得删除授权，只允许删除本次运行的精确 run 目录。

测试不得修改真实数据库、配置、媒体或账号资料。只能管理本次启动并记录所有权的产品进程，禁止按名称批量
结束进程。

结构检查只核对这些规则是否有唯一入口，以及直接声明的默认触发是否明显与规则相反；更深的实现验证属于独立
测试或安全任务。

## 7. 验证执行账本、结果与证据

每次申请验证命令授权前，在对话中建立仅用于本次任务的验证执行账本。每个拟运行项列出：

- 实际运行器及其入口；
- 工作目录；
- 项目管理或环境已经提供的依赖；
- stdout、临时目录、仓库外目录或其他输出位置；
- 可预见的 Git、联网、产品进程、真实数据、安装和其他嵌套副作用。

账本不写入仓库、不跨任务继承，不用顶层命令名掩盖嵌套动作，也不自动安装缺失依赖。涉及自动化、外部副作用
或授权选择时，先按“会发生、不会发生、既有状态”给出三行白话效果摘要，再请求对应授权。

动态状态使用：`passed`、`failed`、`blocked`、`inconclusive`、`not_run`。

规范验证没有执行时必须保持 `not_run`。静态阅读、格式检查、字节比较或其他替代证据可以单独形成结论，但不能
把未执行的原验证写成 `passed`。门禁结果只绑定实际执行时的候选；活动待办、方案、归档索引或条件目录随后变化
时，施工中途结果不能替代最终状态门禁。

skip 只是项内计数，不能把缺失结论补成成功。同一候选只重跑失败、中断、blocked、inconclusive 或失效项；
产品输入、测试契约或候选身份变化后重新判断范围。

全量测试和正式认证摘要位于仓库外，绑定验证层级、run-id、候选身份、实际范围、逐项结果和总体结论。标准
骨架默认不提供 evidence helper；项目首次实际需要时逐项设计。

## 8. 标准文档机械门禁

标准路线默认从 Skill 资产安装：

- `SoftwareTesting/doc_consistency/test_doc_consistency.py`
- `SoftwareTesting/doc_consistency/test_doc_consistency_rules.py`

两个源码必须从 Skill 对应路径整文件逐字节复制，并在验证阶段比较字节结果。具体复制机制只在施工授权后按
当前环境选择，不增加永久复制 helper；不能保证整文件复制时停止，不以片段补丁、手工转录、顺手优化或项目
分叉替代。目标已有不同内容时停止并展示冲突，由用户决定保留项目门禁、迁移标准门禁或另行处理。

通用门禁 error 只包含标准路线可以机械证明的问题：

1. 固定文件与条件文件关系；
2. 活动 Markdown 的 UTF-8 与 LF；
3. 普通行内相对链接和标题锚点；
4. AGENTS、README、文档入口和测试入口；
5. 活动文档两跳实际可达性；
6. 待办 ID、唯一状态和活动方案数量；
7. `待确认` 可选一份方案、`实施中` 必须一份、其他状态禁用方案；
8. 方案中的三项测试决策和实际待办链接；
9. 四列 Registry、类别和 `T-DOC full`；
10. 归档唯一登记、当前承接及活动导航不直接链接归档正文。

warning 只包含绝对本地用户路径、机器入口复杂 Markdown 语法，以及根 README 与 `docs/README.md` 的重复专题导航。

通用门禁不检查正文是否符合代码、动态测试结果、`CONTEXT.md`/ADR 内容、秘密扫描、检查记录承接位置的语义、
测试覆盖、重复或过度设计，也不判断非标准成熟项目是否结构等价。

## 9. 门禁自测试

通用 T-DOC 每条阻断规则至少有一个正确夹具和一个错误夹具，每条 warning 至少验证一次触发和不触发；新增或
修改规则时同批更新夹具。

等价既有项目可以使用不同自测组织方式，但必须证明当前结构门禁至少接受一个合规样例并拒绝一个关键违规
样例。只有门禁脚本而没有可执行自证时，对应机械门禁维度记为 `证据不足`。
