## 1. 适用条件与职责

只在标准测试治理、标准 T-DOC 或标准验证规划适用时读取本文件。成熟等价项目保留自己的测试目录、Registry
schema、类别词汇、测试安全规则和项目专用门禁；不能只因它存在测试入口或测试根而加载本基线。

骨架只检查测试治理结构、入口、选择关系、授权边界和机械门禁。测试资产信息架构调查方法见
[`test-asset-structure.md`](test-asset-structure.md)；覆盖、重复、断言质量、成本和产品测试重构不属于骨架职责。

## 2. 固定与条件结构

标准固定结构：

```text
SoftwareTesting/
├── README.md
├── PROTOCOL.md
├── SAFETY.md
└── doc_consistency/
    ├── README.md
    ├── test_doc_consistency.py
    └── test_doc_consistency_rules.py
```

按需结构：

```text
SoftwareTesting/<project-suite>/
SoftwareTesting/manual/
archive/SoftwareTesting/
```

产品命令、fixture、进程、端口和交付物必须来自用户确认或当前项目直接证据；骨架只检查承接位置，不推导产品
事实。默认不引入核心矩阵、多层快照、Release runner、产品锁、lease、二进制审计或项目级测试 manifest。

## 3. 验证层级、方案字段与授权

- **普通验证**：默认层级，按实际影响选择最小可证明范围；
- **全量测试**：只有用户明确开启时执行最小充分能力证明集，即全部 `full`、本候选实际触发的 `affected_only` 和
  用户明确加入的 `explicit`，不机械并入全部测试资产或历史场景；
- **正式认证**：只有用户明确要求时，在上述最小集合通过后核对候选身份并形成结构化交接；不得自动增加目标项目
  未声明、未交付，或没有直接敏感性证据的平台、环境和场景。

普通措辞不提升层级，clean build 不等于全量测试或正式认证。`affected_only` 相对于普通实施任务开始时冻结的候选基线
判断，使用能够覆盖已跟踪内容和未忽略新文件的实际变更集合。集合不能可靠形成、不能证明直接输入未变或既有证据已经
失效时，执行对应项。每份活动方案恰好各记录一次“测试层级、验证影响域、具体验证项”。保存方案时拟运行项保持
`not_run`，普通任务施工时按当前证据复核。

标准项目的一次明确实施授权覆盖确定文件变更、方案列明的普通验证和结果记录，以及完成条件满足后的状态更新、方案
归档、索引更新和精确任务清理；方案列明的普通下载和公开资源获取在来源、用途、规模和副作用不变时一并覆盖。
验证升级、新副作用、候选漂移或新语义决定只申请差额。commit、push、PR、发布、安装、认证／私有访问、上传、
外部写入、付费或明显大规模联网、产品进程、真实数据、全量测试、正式认证，以及方案外或高风险删除仍需明确授权。

标准路线的验证要求按组件直接输入逐项选择，不机械列入全部命令：门禁说明、实现、规则夹具或机械规则合同变化时运行
规则夹具；标准资产安装或更新时逐字节比较目标内三份 T-DOC 资产；目标 T-DOC 的直接输入变化时运行目标门禁；生命周期
变更形成最终候选后只运行一次目标门禁，失败修复或直接输入再次变化才重跑。等价既有治理改列项目自己的门禁、自测试和
静态复核。

标准路线规划会读取文本的新增 Python 验证入口时，方案必须把 `-X utf8` 或由当前证据证明等价的显式 UTF-8 模式
列为必要运行参数；需要禁止默认字节码缓存时另列 `-B`，两者不能互相替代。外部验证脚本依赖 Python 默认文本编码时，
由入口提供显式运行模式，不因此修改脚本本身。

在正确模式下发生 `UnicodeDecodeError` 或等价严格解码错误时，验证为 `failed`；不得猜测 GBK 等本地编码、使用替换
字符继续或自动转换文件。该要求不扩大 T-DOC 的活动 Markdown 集合、文件编码规则或项目级 Skill 根扫描，也不强制
迁移成熟等价项目已有的权威命令；后者的 locale 依赖只记录为可移植性残余、影响和可能修订路径。

## 4. 标准 Registry

`docs/软件测试.md` 的机器表格固定为：

```markdown
| ID | 执行类别 | 入口 | 唯一职责 |
| --- | --- | --- | --- |
| T-DOC | affected_only | [文档机械门禁](../SoftwareTesting/doc_consistency/README.md) | 检查标准文档骨架机械一致性 |
```

ID 使用 `T-` 前缀、大写字母、数字和连字符，不得复用当前 Registry、测试归档和可发现 Git 历史中的既有 ID。

- `full`：所有候选都适用、没有等价替代的最小核心能力证明，每次全量测试必须执行；
- `affected_only`：对应能力、直接输入或已声明条件实际变化时执行；
- `explicit`：真实数据、破坏性、费用或特殊环境，只有用户明确加入才执行。

标准路线中 `T-DOC` 必须存在且为 `affected_only`。它的直接输入包括活动 Markdown、归档索引、固定结构、Registry、
门禁说明、实现和规则夹具；产品源码变化本身不触发 T-DOC。Registry 不保存日期、数量、耗时、run-id、哈希或结果。
“唯一职责”应表达该活动项独有的能力或故障模式；已有直接证据证明被其他测试完全覆盖、产品已经退役，或在当前支持
合同和生产前置约束下不可达的场景，不作为完整测试或正式认证的独立项，仅有“历史上没有命中”不能证明不可达。
Skeleton 只规定选择与承接关系，不因此读取全部测试实现、审计充分性或生成删除测试的切片。机械门禁只检查 ID、类别、
入口和非空职责，不判断测试项价值。成熟项目可以使用不同 schema 和类别，只要能解释完整、受影响和显式执行的选择
职责并提供稳定入口。

## 5. 测试入口职责

### `SoftwareTesting/README.md`

链接 Protocol、Safety、Registry 和每个活动 suite README。标准路线的活动 suite README 必须直接可达。

### `SoftwareTesting/PROTOCOL.md`

保存验证层级、影响域、测试类别、构建与验证关系、结果语义、重试失效、全量与认证顺序和任务交接；不保存项目
具体命令、安全细节或动态结果。

### `SoftwareTesting/SAFETY.md`

保存测试根、真实数据保护、联网数据边界、进程所有权、串行、输出 containment、保留和清理规则。项目不涉及真实
数据或产品进程时，用当前证据明确写“不适用”。

### Suite README

保存 Registry ID、独有触发条件、输入、fixture、工作目录、规范命令、断言、失败语义和专项清理；不复制公共
规则或动态结果。命令、依赖、覆盖声明和产物必须来自用户确认或当前项目证据。相对命令必须明确工作目录，缺少
依赖时先确认由项目管理、环境预置还是改用其他入口，不自行安装。

失败语义按执行阶段互斥：前置条件不足通常是 `blocked`；进入可判定阶段后的断言、收集或项目错误可以是
`failed`；中断或运行器异常使证据不可解释时是 `inconclusive`。

## 6. 仓库外测试现场

标准默认测试根：

```text
<项目父目录>/<项目名>_test/<run-id>/
```

默认根已存在但没有当前项目合法所有权标记时停止；已有标记时核对所有权。输出解析后必须仍位于本次直接 run；
符号链接、junction、reparse point 或路径逃逸失败关闭。

骨架方案只记录应由治理文档承接的约束，不提供测试现场工具。输出默认保留；方案已经列明清理本任务创建的精确 run
时，普通任务仍须验证所有权和绝对路径。未列明清理、其他 run、测试根、仓库外非任务产物或所有权不明的目标必须
另行取得精确授权。

测试不得修改真实数据库、配置、媒体或账号资料。只能管理本次启动并记录所有权的产品进程，禁止按名称批量结束。
骨架只核对这些规则是否有唯一入口及直接默认接线，不执行更深安全验证。

## 7. 验证证据与结果语义

本节只规定方案如何描述验证，不指导 skeleton 运行命令、组织临时候选或执行关闭。每项验证写明证明目标、适用候选
和会使结果失效的状态变化，不预写运行器、临时索引、输出路径或执行结果。

动态状态只在实际执行后使用：`passed`、`failed`、`blocked`、`inconclusive`、`not_run`。方案保存时未运行项目
一律为 `not_run`。

各层分别记录实际范围、适用候选和状态：

1. **T-DOC 机械门禁**：只证明对应文档结构机械规则；
2. **内容一致性审计**：只记录实际执行的内容事实核对，skeleton 不自动触发；
3. **受影响项目测试**：只覆盖本次变化直接影响的项目测试、脚本或 CI 断言；
4. **完整项目测试**：记录项目自己的完整测试入口。

各层结论不得互相代替。计划执行、静态阅读或其他层证据不能把未运行层改写为 `passed`。

方案和验收记录还要区分：

- **初始检查证据**：保存方案时的历史快照；
- **完成条件**：判断是否达成目标的标准；
- **实施结果**：实际写入后已经发生的变化；
- **关闭结果**：验证、review、移动、删除、最终门禁和状态转换的实际结果。

任何未执行动作都不得预写成结果。门禁只绑定执行时的候选；生命周期随后变化时，中途结果不能替代最终状态门禁。

## 8. 标准文档机械门禁

标准路线从 Skill 资产整文件安装：

- `SoftwareTesting/doc_consistency/README.md`
- `SoftwareTesting/doc_consistency/test_doc_consistency.py`
- `SoftwareTesting/doc_consistency/test_doc_consistency_rules.py`

三份资产必须逐字节复制并比较。目标已有不同内容时停止并展示冲突，由用户决定保留、迁移或另行处理；不以片段补丁、
手工转录或永久复制 helper 替代整文件结果。

本源仓库的 `SoftwareTesting/doc_consistency/` 还承接项目专属职责命令，不是三份目标资产的 README 镜像；其中两个
Python 文件分别与 Skeleton 资产逐字节一致，两个 README 按各自标准职责和本仓库扩展职责静态核对。

通用门禁 error 只包含可以机械证明的标准规则：

1. 固定文件与条件文件关系；
2. 活动 Markdown 的 UTF-8 与 LF；
3. 普通行内相对链接和标题锚点；
4. AGENTS、README、文档入口和测试入口；
5. 活动文档两跳实际可达性；
6. 待办 ID、唯一状态和活动方案数量；
7. 待办状态与活动方案关系；
8. 方案的三项测试决策和实际待办链接；
9. 四列 Registry、类别和 `T-DOC affected_only`；
10. 归档唯一登记、当前承接及活动导航不直接链接归档正文；
11. 非标准顶层目录中的活动 Markdown 必须由根、项目文档或测试总入口直接链接目录内所有者入口。

门禁精确排除 `SKILL.md` 列明的七类标准项目级 Skill 根，不排除整个工具目录或其他位置的 `SKILL.md`。审计流程
可以按 `SKILL.md` 的精确证据例外读取必要 Skill 文件；通用 T-DOC 不解析自定义 Skill 根、工具配置或 manifest。

warning 只包含绝对本地用户路径、机器入口复杂 Markdown 语法，以及根 README 与 `docs/README.md` 的重复专题导航。
门禁不检查正文事实、动态结果、`CONTEXT.md`／ADR 内容、秘密、测试设计或成熟项目是否结构等价。

## 9. 门禁自测试

通用 T-DOC 每条阻断规则至少有一个正确夹具和一个错误夹具，每条 warning 至少验证一次触发和不触发；新增或修改
规则时同批更新夹具。

等价既有项目可以使用不同自测组织方式，但必须证明当前结构门禁至少接受一个合规样例并拒绝一个关键违规样例。
只有门禁脚本而没有可执行自证时，对应机械门禁维度记为证据不足。
