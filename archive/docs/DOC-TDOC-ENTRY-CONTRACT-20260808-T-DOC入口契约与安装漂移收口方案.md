## 活动真源与冻结范围

- 审计模式：`project-doc-consistency full`。
- 活动真源及所有者：`docs/设计文档.md` 承接当前实现结构；
  `project-doc-skeleton/references/testing-baseline.md` 和 `SoftwareTesting/doc_consistency/README.md` 承接标准 T-DOC
  机械契约；`SoftwareTesting/doc_consistency/test_doc_consistency.py` 是直接实现证据。
- 冻结声明：T-DOC 哪些项目级 Skill 根会被机械排除，以及自定义 Skill 根是否会被解析。
- 一轮直接依赖：实现中的七类标准根常量、活动 Markdown 忽略逻辑，以及门禁说明中的自定义根边界。
- 排除项：归档正文、两个 Skill 的阶段模型、顶层 Markdown 根判定算法、产品代码、其他测试与 CI、外部项目和用户级
  安装目录正文。
- 未覆盖边界：外部项目行为和重新安装后的实际状态；未执行项保持 `not_run`。

## 当前证据与审计结论

1. T-DOC 实现只机械排除七类标准项目级 Skill 根；不读取项目配置来发现自定义根。
2. T-DOC 说明和 skeleton 测试基线都明确写明“不解析自定义 Skill 根”。
3. 原设计文档笼统写成“项目级 Skill 根不进入该判断”，会被理解为自定义根同样自动排除，与当前实现不一致。
4. 需求、设计和门禁说明已经明确顶层 Markdown 根规则是最小机械所有权检查，并且不解析正文语义；当前直接链接
   判定与该契约一致，不构成实现缺口，不需要重命名术语、函数或夹具。
5. 实施时用户级 skeleton 安装对应当前已提交版本，而工作区包含尚未提交的新候选。这是交付顺序形成的安装版本差异，
   不是仓库内容缺陷，也不由本方案实施授权处理。

用户决定：先只修订方案；review 收缩范围后，用户确认按修订方案实施。安装和 Git 交付未授权。
