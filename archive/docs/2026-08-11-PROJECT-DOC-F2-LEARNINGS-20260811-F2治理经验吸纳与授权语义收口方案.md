## 1. 目标与已确认决定

本方案把两份 F2 施工后经验报告重新按当前 Skill 职责取舍，不把 F2 路径、测试名称、manifest、运行次数或 Windows
特例复制为通用默认值。两个 Skill 继续只读检查并按请求保存方案，保存后退出执行链；新增规则只提高证据边界、方案
可实施性和授权解释的准确性。

用户已逐项确认以下结果：

1. `D-01`：区分“只报告”和“形成方案”。只报告时不询问评审轮数、不形成候选、不询问保存；意图不清默认只报告。
   形成方案时一次询问评审轮数和是否在实施完成后生成反哺报告，推荐“两轮、不生成”，“按推荐”同时接受这两个结果。
   施工、验证和关闭仍交给普通任务。
2. `D-02`：分别说明当前待办状态、该状态是否允许方案、是否取得实施授权，以及方案存在能否证明已经开工；标准路线
   现有生命周期不变，成熟项目服从自己的明确规则。
3. `D-03`：上下文数量优先服从用户当前声明、项目长期规则和公开入口，再看所有权、发布节奏、术语和变更闭环；目录、
   语言、产品形态和外部上游只作为最后的调查信号。
4. `D-04`：需要完整盘点当前资产时使用 Git 感知的有界候选集合：已跟踪且仍存在的文件，加未跟踪但未忽略的新文件，
   排除已不存在索引路径和生成残留。Git 不可用时使用明确资产清单；没有等价证据则标记证据不足。
5. `D-05`：测试资产分别判断活动独立项、活动附属项、隔离保留项和历史项，并独立记录纯静态、合成本地、真实数据或
   产品进程、外部只读、外部写入等已暴露副作用；允许项目使用等价词汇。
6. `D-06`：分开 Registry 或等价登记、唯一所有者、直接消费者、实际执行入口和正式选择范围，不从任何一层反向推导
   其他层身份，也不要求项目新增 manifest。
7. `D-07`：会改变归档、删除、替代或正式选择边界的关键关系使用“已证明存在、已证明不存在、证据不足”三态；负证据
   必须绑定完整成功的有界查询，不把无命中扩写成全项目不存在。
8. `D-08`：每项发现保持唯一归宿并说明实际影响、是否阻止切片进入确定范围和解除条件；不新增固定高／中／低字段或
   持久发现账本。
9. `D-09`：普通实施任务自动修复原范围内且由当前权威唯一裁决的验证消费者漂移，安全处理临时环境阻断；新语义、
   新权限或当前任务阻断才立即询问。独立非阻断问题去重后在收尾前统一询问是否登记，不逐项打断。
10. `D-10`：冻结声明涉及 Registry、CTest、CI、Release 或等价选择时，检查权威、实际声明、expected／选择清单、唯一性、
    缺失与多余项、按项目语义适用的顺序和协议版本、实际入口与正式范围。
11. `D-11`：分阶段、全量或昂贵验证说明各阶段绑定输入、失效条件、最低复用证明和必须重跑的下游项；证据不足时不复用。
12. `D-12`：昂贵动态验证在授权前根据直接入口估算场景、产品启动、退出上限、保守耗时、前台或环境占用、进程 owner、
    失败清理和恢复停点；能查明的自行计算，真正涉及成本选择时才询问。
13. `D-13`：合成夹具必须在预期失败点之前满足现行最低输入合同，同时保持虚构、离线和不读取真实用户数据；故障注入
    应实际到达目标阶段。
14. `D-14`：测试以文字搜索或正则提取源码证据时，必须唯一定位目标实现；零匹配、多重歧义或范围不完整时失败关闭，
    不把 F2 的 C++ 语法细节硬编码为跨语言规则。
15. `D-15`：只有精确范围涉及 GUI 或真实输入时，检查启动、就绪、当前可用退出、失败清理和外部输入阻断语义；不替
    实施任务选择自动化框架，不绕过系统安全界面。
16. `D-16`：明确区分技术证据完整与正式认证、签名、发布、部署或外部回写完成；未获授权阶段保持 `not_run` 或项目
    等价状态，最终结论不得升级。
17. `D-17`：用户回复“确认、接受、按推荐、就这样”只确认当前问题明确展示的语义结果；当前问题没有明确询问写文件、
    登记待办、保存方案、切换状态或开始实施时，不产生相应动作授权。旧授权不扩展到后来出现的新需求，生命周期转换
    也不能由单项语义确认推导。

归档决定：只保留两份自包含报告，不复制 F2 完整实施方案；把报告中的失效来源链接改成无链接的外部项目来源说明，
在当前归档索引各登记一次，并保留原文件名。实施完成后不再生成新的反哺报告。

## 2. 初始证据与覆盖／残余矩阵

### 2.1 冻结发现

- `F-01`：两个 Skill 当前对所有新问题统一询问评审轮数并进入候选流程，不能承接已确认的只报告分支；语义决定、
  最终保存和实施授权虽已分开，但尚未明确禁止从普通“确认”推导写入、状态转换或继承旧授权。
- `F-02`：Skeleton 已支持标准与等价路线，但缺少上下文证据优先级，以及对项目自定义“允许方案／已经开工”的四项
  分离判断。
- `F-03`：Skeleton 测试资产调查只有入口、所有者和实现根映射，尚无 Git 感知候选集合、生命周期／副作用双轴、
  多层身份关系及有界负证据。
- `F-04`：发现清单已有唯一归宿和影响字段，但没有直接要求说明是否阻止切片进入确定范围和解除条件。
- `F-05`：Consistency 的一跳测试证据链尚未覆盖声明与 expected／正式选择的精确身份对账。
- `F-06`：Consistency 方案没有统一承接实施期验证漂移、证据失效／复用、动态预算、技术与认证终态，以及独立问题
  收尾批量登记的规则。
- `F-07`：有条件测试设计参考尚未覆盖合成夹具到达目标阶段、源码文字提取失败关闭、GUI 退出与外部输入阻断。

  的 `20260810` 与正文形成日期不同，用户已决定保留原文件名。

## 3. 确定实施切片

### 3.1 请求分流、语义确认与动作授权

1. 新增 ADR-0010，记录“只报告／形成方案”按请求分流、方案入口的联合首问、语义确认与动作授权分离，以及对
   ADR-0009“每次检查都进入候选和保存停点”部分的替代；ADR-0005、ADR-0006 的退出执行链决定保持有效。
2. 在当前 `AGENTS.md` 和标准 Skeleton 协作规则中加入长期红线：普通确认只绑定当前语义；写入、登记、方案保存、
   生命周期转换和实施必须由当前问题明确询问并取得接受；旧授权只绑定原范围。
3. 两个 `SKILL.md` 先按明确请求选择报告或方案路线。只报告路线完成同等严格的冻结、检查和对话报告后停止；方案
   路线才询问“交付方案前自查几遍”和“实施完成后是否生成反哺报告”。意图不清默认报告路线。
4. 联合首问的推荐固定为“两轮、不生成反哺报告”；“按推荐”只在该首问中同时接受两项推荐。选择生成时只把独立
   报告登记为普通实施任务完成项目修改和验证后的交付物，不由两个文档 Skill 生成，也不自动修改目标 Skill。
5. 语义决定卡、授权差额卡、最终方案保存卡继续分开；任一卡片的确认不向其他卡片、后来需求或普通任务传播。

### 3.2 Skeleton 的上下文、资产证据和结构关系

1. 在 `project-doc-skeleton/SKILL.md` 增加上下文证据优先级、四项生命周期判断、关键发现的确定范围阻断与解除条件，
   并把详细测试资产调查路由到新的直接 reference。
2. 新增 `project-doc-skeleton/references/test-asset-structure.md`，集中承接 `D-04`～`D-08`：Git 感知候选集合、
   非 Git 等价证据、生命周期／副作用双轴、登记／所有者／消费者／执行／正式选择关系、三态存在证据及范围限制。
   文件超过 100 行时在顶部提供目录，不复制主流程。
3. 更新 `references/skeleton-rules.md` 与 `references/testing-baseline.md` 的引用和标准路线说明，删除“测试资产方法只
   存在于主 SKILL.md”的过时断言；标准生命周期和标准 T-DOC 机械规则不因成熟项目的不同做法改变。
4. 不要求项目创建新 manifest、固定目录或统一类别；不把测试结构检查扩张成覆盖率、断言质量、安全认证或测试实现
   重构。

### 3.3 Consistency 的验证规划与有条件测试设计

1. 在 `project-doc-consistency/SKILL.md` 保留只读双遍审计和条件测试设计触发，只增加两类直接 reference 的读取条件
   与方案最小路由，不把实施、运行或修复能力收回 Skill。
2. 扩充 `references/test-design-audit.md`，增加验证身份链、合成夹具在目标失败点前合法、源码文字提取唯一定位并
   失败关闭、GUI 当前退出合同和外部输入阻断；只处理已冻结精确入口，不扫描全部 fixture、静态测试或 GUI 流程。
3. 新增 `references/validation-planning.md`，承接实施期验证消费者漂移／新范围／环境阻断分流、独立问题收尾批量
   登记、证据输入分类和失效／复用、动态预算、进程 owner、恢复停点以及技术终态／认证终态。
4. 普通实施任务只自动处理方案已列范围和直接依赖内、由当前权威唯一裁决的消费者漂移；新语义、新权限或阻断当前
   完成的问题立即停问，其他独立问题去重后只在收尾前统一询问一次。计划不得形成开放式“测试失败即可顺手修改”授权。
5. 验证身份顺序只在项目声明顺序有意义时检查；产品输入或二进制不变也不能自动复用证据，必须同时满足项目协议和
   本方案列明的最低证明。
