## 1. 目标、边界与历史说明

本方案修复一个明确的完整性缺口：Consistency 即使逐路径记录了双遍结果，仍可能只依据某个局部问题或抽样结论，
就把整份长期文档判为已经完成内容收缩审计。修改后的合同必须让局部证据不能代表未检查正文，也不能把完整审计留给
后续实施任务补做。

已确认的目标边界如下：

1. `full` 必须覆盖活动入口列出的每份长期文档，并为每份文档给出“需要收缩”“无需收缩”“无法核验”
   “需要决策”或“未覆盖”之一，以及该文档特定的依据。
2. 只有全部活动长期文档都有处置，才可声称完成项目级收缩审计或形成完整方案；局部发现、抽样结果和文件级概括
   都不能替代其余正文。
3. `incremental` 只对冻结种子及一轮直接依赖中的长期文档给出处置，不静默升级为 `full`，也不得宣称项目级完成。
4. 保存的方案必须直接承接逐文档结论和确定处置；实施任务按结论修改并处理实施期漂移，不重新承担全面审计。
5. 规则保持高自由度：不规定固定标题、表格、编号、计数公式、关系矩阵或输出顺序，不按篇幅阈值判定收缩。

此前尝试把缺口固化为多张硬表、集合公式、候选哈希和逐轮前向修复记录，连续迭代后逐渐变成对预期输出的重建，
没有形成可信的泛化证据。相关任务已由用户停止；既有记录只作为失败历史，不作为本方案的验收证据，也不在仓库继续
保存详细运行日志。

## 2. 确定实施切片

### 2.1 收紧主 Skill 的完成语义

以 `project-doc-consistency/SKILL.md` 的 `HEAD` 内容为基线，只增加以下不可绕过的合同，并保留现有显式调用、
静态只读、报告／方案分流、候选评审和最终保存确认边界：

- `full` 在形成完整报告、完整候选或询问保存前，核对全部活动长期文档均已有文档特定的收缩处置与证据；
- 一个局部问题、样本、标题或文件级一句话只能证明对应范围，不能证明同一文档其余正文已检查；
- `incremental` 只报告冻结范围内的逐文档处置，并明确项目级未覆盖部分；
- 方案路线必须把逐文档结论和真实发现带入方案，不能写成“实施时再审计全部长期文档”；
- 记录形式由项目结构和证据自然决定，不引入固定硬表、数量门、恒等式或可复制输出模板。

### 2.2 精简内容收缩方法

以 `project-doc-consistency/references/content-contraction.md` 的 `HEAD` 内容为基线，补充以下方法：

1. 对较长或承担多种职责的长期文档，自然覆盖其主要职责、主要章节和实质性无标题正文；不建立逐标题持久账本。
2. 对存在直接所有者／消费者关系的文档核对重复正文、实现镜像、过程记录、历史快照和错位职责；不进行全量文档两两比较。
3. “职责明确”“内容聚焦”或“已经拆分”等概括不是无需收缩的证据；结论应说明唯一所有者、独有价值以及删除或
   只留链接会损失什么当前能力。
4. 优先删除失效或重复内容、改为链接唯一所有者、收敛错位正文；同时保留唯一事实、消费者特定义务和必要的短摘要。
5. 继续区分活动真源总内容足迹与默认入口加载量，不设置跨项目行数、字数、页数或缩减比例。

### 2.3 保留两项条件测试设计规则

以 `project-doc-consistency/references/test-design-audit.md` 的 `HEAD` 内容为基线，只保留此前已经确认的两项通用补强：

1. 合成夹具构造会被产品加载、迁移或重建的持久结构时，使用权威当前 schema／构造入口；如果测试目标就是旧版、
   损坏或非法结构，则明确固定版本及预期迁移、重建或失败结果。
2. 场景包含中间态、未就绪态或最终一致状态时，写明正式状态转换、可观察就绪条件或预期失败关闭；不得用任意固定
   等待掩盖未知转换。

这两项只在测试设计审计的既有触发条件成立时适用，独立于内容收缩完成判断，不扩大普通审计或验证范围。

### 2.4 最小同步当前真源
