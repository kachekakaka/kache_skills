## 1. 目标、结论与既有决定

本方案解决的不是“给一致性 Skill 新增收缩能力”，而是让已经存在的收缩合同不能被执行过程绕过。当前
[`SKILL.md`](../../project-doc-consistency/SKILL.md) 已把内容膨胀列为职责，并要求 `full` 对每份活动文档分别完成
事实／契约遍和职责／删除优先遍；[`CONTEXT.md`](../../CONTEXT.md) 也已把内容膨胀定义为超出文档职责的
源码镜像、过程记录、历史快照或重复说明，不以篇幅长短判断。

F2 真实治理暴露的失效方式是：任务把审计称为 `full`，但保存方案只冻结并承接四项高显著度验证问题，没有物化
每份活动文档的双遍结果，也没有承接需求、设计等长期文档中的分散膨胀。普通实施任务随后准确执行了这份不完整方案，
所以最终文档仍然很大。根因分成两层：

1. 运行时没有在“冻结发现、形成候选、完成评审、询问保存”之前执行可机械对账的逐文档完整性门；
2. 现有前向契约虽覆盖 `full` 报告路线的三文档双遍，却没有单独证明 `full` 方案路线会拒绝缺行、缺遍或只处理显眼
   冲突的候选。

本方案沿用以下既有决定，不新增语义选项：

- 收缩按职责、唯一所有者和删除优先判断，不设置统一行数、字数或百分比指标；
- `full` 的活动文档集合必须逐文档完成两遍，显眼发现不能使其他文档短路；
- 一份综合方案只承接真实发现形成的切片；没有问题的文档仍须有双遍结论，但不为了集合对称制造空修改；
- consistency 继续只读审计、按请求报告或保存方案，保存后停止，施工和验证仍由普通任务承担；
- 详细判据通过 progressive disclosure 放入直接 reference，主 `SKILL.md` 只保留不可绕过的硬门、触发和失败语义；
- 本次是对既有 ADR-0006、ADR-0008、ADR-0009 和 ADR-0010 的实现收紧，不改变架构方向，不新增 ADR。

## 2. 初始证据、冻结发现与覆盖／残余矩阵

### 2.1 冻结发现

- `F-01`：`SKILL.md` 已要求逐文档双遍，但只规定“双遍矩阵填满”这一结果，没有把活动文档清单、矩阵行、两遍单元格、
  最终报告和保存资格定义为可对账集合，也没有明确缺一项时禁止冻结发现、完成评审或询问保存。
- `F-02`：当前发现集合对账只比较“发现—矩阵—候选处置”，无法发现某份活动文档从未产生第二遍结果；如果遗漏发生在
  发现冻结之前，后续集合对账会对一个不完整集合自洽。
- `F-03`：当前主 Skill 只列出“职责不清、重复真源、内容膨胀、位置不当”，缺少足以稳定执行删除优先遍的角色证据、
  唯一所有者、删除／引用／收敛／保留顺序，以及“拆分或加索引不等于总内容收缩”的判据。
- `F-04`：现有 `CASE-CONSISTENCY-FULL` 已覆盖三份活动文档、显眼事实冲突与低显著度膨胀，但只走报告路线；现有
  `CASE-CONSISTENCY-PLAN-HANDOFF` 重点验证语义决定、综合切片、验证规划和保存退出，没有复现 `full` 方案遗漏收缩
  切片的失败方式。
- `F-05`：`agents/openai.yaml` 的默认提示强调事实、验证身份和验证规划，没有向运行时再次暴露“`full` 逐文档双遍
  未齐不得形成完整结论或保存”的关键行为信号。
- `F-06`：需求与设计真源只描述“逐文档双遍并填矩阵”，没有承接集合基数门、第二遍收缩证据和方案路线拒绝条件；
  后续实现若只改 Skill，会造成当前行为真源与测试契约继续偏弱。

## 3. 确定实施切片

### 3.1 在主 Skill 增加不可绕过的完整性门

修改 `project-doc-consistency/SKILL.md`，保留现有 `full`／`incremental`、只读边界和发现集合对账，并增加以下核心
不变量：

1. 读取实现证据前，从活动入口冻结精确活动文档路径列表；列表不得用“核心文档若干”或分组名隐藏成员。入口无法
   形成完整列表时保持 `未覆盖`，不得声称完成 `full`。
2. 每个 `full` 路径必须有且仅有一行覆盖记录，分别填入事实／契约遍与职责／删除优先遍的结论、直接证据或残余；
   `不适用` 只能给出该文档特定理由。`incremental` 对每个精确内容种子及其一轮直接依赖执行同样的行级约束。
3. 在冻结发现之前执行集合门：活动文档路径集合必须与双遍矩阵路径集合完全相等，每行两遍单元格均已填充。缺行、
   重复路径、缺遍或通用占位理由一律失败关闭；先补齐受影响文档，不能继续形成完整报告、候选或评审计数。
4. 发现冻结后继续执行现有“发现—矩阵—候选处置”对账。前一集合门保证没有文档在发现前消失，后一集合门保证
   已发现问题没有在报告或方案中消失；两者职责不同，不合并成一份持久账本。
5. 高显著度冲突只允许生成发现，不能终止剩余路径或第二遍。只有活动集合完整、逐文档两遍完整、全部适用结论无残余，
   才能使用“完整审计完成”或“活动文档一致”等总体措辞。
6. 方案路线在候选评审和最终保存问题前再次核对完整性门。没有问题的文档保留双遍矩阵行，不生成空修改切片；存在
   收缩问题的文档必须在综合方案中有发现归宿和就绪或待决切片。

这组规则只约束审计完整性，不要求持久 profile、manifest、运行日志、固定严重度或新的命令执行阶段。

### 3.2 新增内容收缩直接参考

新增 `project-doc-consistency/references/content-contraction.md`。`full` 在职责／删除优先遍前完整读取；`incremental`
在冻结的种子或一轮直接依赖中包含长期活动文档，或已经暴露重复、源码镜像、过程／历史、位置不当或删除候选时读取。
这样配置或代码种子直接影响活动文档时也不会漏载。reference 承接详细方法，主 Skill 只保留触发、输出合同和失败语义：

1. 先写明文档角色、该事实的唯一当前所有者和直接消费者，再判断内容是否为职责所需；“内容正确”不能替代职责证明。
2. 对每份文档分别检查：跨文档重复真源、逐段源码／配置镜像、一次性实施与排障过程、动态运行快照、历史结果、属于
   其他长期所有者的内部细节，以及只有默认入口才需要的导航摘要。
3. 处置顺序为删除失效／重复内容、改为链接唯一所有者、收敛到正确所有者、最后才是有证据保留；“加目录、拆文件、
   搬到另一个活动文档”本身不构成收缩。
4. 分开报告“活动真源总内容足迹”和“默认入口加载量”。拆分可能降低默认加载量，但只有删除重复、快照、过程或源码
   镜像才降低总内容足迹；两种收益不得互相冒充。
5. 判为无需收缩时，记录文档角色、抽查到的风险类别、唯一所有者和保留必要性；不得使用“模型完整”“以后可能有用”
   或“已经分文件”等通用理由跳过第二遍。
6. 完成条件以唯一所有者、无重复真源、过程／历史退出活动真源和直接链接可达为准，不设置跨项目统一的行数、字数、
   页数或收缩百分比。

### 3.3 元数据与当前真源同步

1. 使用当前 `skill-creator` 提供的生成脚本更新 `project-doc-consistency/agents/openai.yaml`，在默认提示中简洁暴露：
   `full` 必须逐文档完成双遍，矩阵不齐不得形成完整结论或进入保存。保持显式调用策略和“只报告／形成方案”分流。
2. 更新 `docs/需求文档.md`，把集合门、失败关闭、无问题文档不制造空切片和收缩不按篇幅阈值写成当前可观察合同。
3. 更新 `docs/设计文档.md` 的模块树和内容一致性处理流，接入新的 reference、前置集合门与保存前复核；不复制
   reference 的详细清单。
4. `CONTEXT.md` 的“内容膨胀”定义已经准确，ADR 方向未改变，均保持不变。根 `README.md`、`docs/README.md`、
   `docs/软件测试.md` 和 `SoftwareTesting/README.md` 只做一跳直接消费者复核；现有摘要仍准确时不修改。

### 3.4 报告与方案路线防回归

1. 加强现有 `CASE-CONSISTENCY-FULL`：评估者必须核对活动入口路径集合与矩阵路径集合完全相等、每行两遍均有文档特定
   证据或残余，并明确“显眼冲突不能在发现冻结前截断其他文档”。
2. 扩展现有 `CASE-CONSISTENCY-PLAN-HANDOFF`，不增加第六个代表性样本，也不绑定 F2 名称或路径：在当前高显著度
   语义决定和验证规划之外，让活动入口列出多份文档，其余文档分别隐藏重复真源、源码镜像、一次性过程和错位内部
   说明，并把自然请求明确为 `full` 方案路线。
3. 扩展后样例的硬结果是：保存问题之前逐路径双遍完整；保存方案包含精确活动列表和同行矩阵；所有低显著度膨胀都有
   删除、引用、收敛、保留证据或待决归宿；没有问题的文档不生成空切片；仅拆文件或加索引不能算收缩完成。
4. 更新 `SoftwareTesting/manual/project_doc_skills/README.md` 的代表性范围、自然提示、consistency 硬断言和结果记录字段。
   保持现有五样本矩阵，不新增 Registry ID、自动评分脚本、持久 profile 或仓库内 run 记录。
5. 前向执行仍遵守盲评：执行任务只接收物化后的原始项目和自然请求，不读取契约预期、F2 诊断或本方案结论；评估者
   在仓库外持有预期并记录结果。

## 5. 普通验证与结果语义

- 使用当前 `skill-creator` 的 `quick_validate.py` 校验 `project-doc-consistency`，并静态核对 frontmatter、reference
  路由、`agents/openai.yaml` 字段与显式调用策略。
- 静态核对：核心不变量只在 `SKILL.md` 保留一份；详细收缩判据只在 direct reference 保留一份；reference 触发覆盖
  所有 `full` 和适用 `incremental`，不存在悬空链接或相互矛盾的重复规则。
- 运行 T-DOC 规则夹具与当前 T-DOC；使用 `git diff --check` 检查差异格式，并复核确定路径及其新产生或改变的一跳
  直接消费者。
- 生命周期关闭后对最终状态重新运行 T-DOC。普通验证不启动产品、GUI、浏览器、Docker 或网络，不读取真实数据。
- 普通验证通过只证明 Skill 包结构、文档机械规则和静态契约一致；不能证明模型在真实 `full` 方案中一定执行完整双遍，
  也不能宣称 F2 已收缩、Skill 已安装、全量测试或正式认证完成。

## 6. 受控前向验收与授权停点

本失效属于运行时行为遗漏，只有静态校验不足以证明修复有效。用户已明确授权在实施完成后执行完整的
`T-PROJECT-DOC-FORWARD` 五样本代表性矩阵；修改后的 `full` 报告和综合方案样本共同验证本次缺口，其余样本证明
硬门没有破坏 Registry 全局、Skeleton、Skill 隔离和普通任务独立接手边界：

1. 每个样本按现行协议使用全新隔离任务和仓库外物化副本；执行任务看不到预期答案、本方案诊断或 F2 结论；
2. 对本次修改的 `full` 报告样本和综合方案样本，评估者核对活动路径集合、双遍矩阵、报告和保存方案，确认所有隐藏
   膨胀均有归宿，且没有空修改切片；其余三个代表性样本继续执行各自全部硬断言。
