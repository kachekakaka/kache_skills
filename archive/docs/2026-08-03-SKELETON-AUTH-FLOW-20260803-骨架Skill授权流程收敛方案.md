## 1. 当前证据与问题

- [`project-doc-skeleton/SKILL.md`](../../project-doc-skeleton/SKILL.md) 已正确分离检查、保存和施工，也要求文件修改、命令、Git、安装及其他受限操作不得相互推定；这些安全边界应保留。
- [`project-doc-skeleton/SKILL.md`](../../project-doc-skeleton/SKILL.md)、[`skeleton-rules.md`](../../project-doc-skeleton/references/skeleton-rules.md) 和 [`testing-baseline.md`](../../project-doc-skeleton/references/testing-baseline.md) 都要求在验证和关闭前披露副作用并获得明确授权，但没有说明多个授权类别可以在同一次申请中逐项列明并由用户一次确认。
- 当前规则没有明确维护“同一任务已授权范围—新增授权差额”，容易在跨用户回合的同一活动方案中重复申请已经明确授予的范围。
- 当前关闭顺序要求检查临时输出、Git 副作用和空条件目录，但没有要求在申请授权前预判最后一份活动方案退出、缓存 Git 索引与工作树候选差异等可提前发现的情况，可能导致执行中途追加授权。
- [`AGENTS.md`](../../AGENTS.md) 要求命令、文件修改、commit、push、PR、发布和安装分别取得授权，但没有要求每一类别必须拆成单独用户回合。因此可优化申请方式，而不放宽授权含义。
- 当前实际使用反馈确认授权申请过于碎片化；这是交互编排问题，不是取消安全停点或扩大默认权限的理由。
- 候选 ID 已在当前文件、归档和只读 Git 历史中核对，未发现既有使用。

## 2. 目标与非目标

### 2.1 目标

1. 明确“授权类别分别成立”不等于“必须分多轮申请”；允许在一个自包含申请中逐项列明并一次确认多个精确授权类别。
2. 在同一任务中维护已授权范围，只对新增动作、扩大范围或新副作用申请授权差额，不因普通用户回合切换重复询问。
3. 支持用户在完整披露后授予条件关闭：全部必需验证通过、候选无实质漂移且没有新增副作用时，按既定顺序完成生命周期关闭和最终门禁。
4. 在申请验证与关闭授权前，预判嵌套只读 Git、临时索引副本、验证临时产物、最后一份活动方案退出及精确空目录清理等可见需求。
5. 为授权体验增加最小前向试用契约，证明减少重复确认没有演变为隐式授权。
6. 让 skeleton 保存的每份方案实例化“收尾与联合复核”字段，并在标准路线的 `docs/README.md` 生命周期中建立
   项目级稳定模板；等价既有项目保留自己的生命周期真源，不强制迁移路径或 schema。

### 2.2 非目标

- 不合并检查、保存和施工三个阶段，不允许首次检查直接写入，也不让保存授权自动成为施工授权。
- 不把文件修改、命令、真实 Git 索引修改、commit、push、PR、发布、安装、联网、产品进程、真实数据或删除相互推定。
- 不降低全量测试、正式认证、真实数据、产品进程、测试现场清理或产品文件删除的现有授权门槛。
- 不修改 `project-doc-consistency`、通用 T-DOC 源码、门禁规则、Registry schema 或目标项目文件。

## 3. 处理选项、推荐与用户决定

### 3.1 选项 A：合并申请、保留独立授权语义

- 在一次申请中列出所有可预见类别、精确目标、条件与排除项；用户可以整体确认，也可以只批准其中一部分。
- 同一任务跨用户回合复用已明确授权的精确范围，只对差额再申请。
- 条件关闭只有在全部披露条件满足时生效；任一验证失败、候选漂移或出现新增副作用时停止，不继续套用授权。

### 3.2 选项 B：放宽授权隔离或从一般措辞推定权限

- 把“施工”“验证”或“关闭”等一般措辞自动解释为 Git、删除、产品进程或其他未披露操作授权。
- 该选项会破坏项目长期红线，不能解决不可预见副作用的真实决策问题。

### 3.3 推荐与决定

- 推荐：选项 A。它减少往返次数，同时仍让每一类受限动作可见、可拒绝、可审计。
- 用户决定：同意选项 A，已保存本方案并另行授权按方案施工。

## 5. 拟定行为规则

1. “分别授权”表示每个类别必须被明确列出和确认，不表示必须拆成不同消息。
2. 在请求授权前先形成授权差额：已授予且目标、范围和副作用未变化的项目不重复询问；新类别、扩大目标或新副作用必须再次申请。
3. 验证执行账本在同一任务内跨普通用户回合有效，但不跨不同任务、不同活动方案或候选实质漂移继承。
4. 一个授权包可以同时列出普通验证、嵌套只读 Git、仅作用于临时副本的 Git 写入、由本次验证创建的精确临时产物清理、生命周期文件修改、精确空目录删除及最终 T-DOC；每项必须说明实际目标和不会发生的动作。
5. 临时产物的创建和清理只有在位置、所有权与边界已披露并获批时才能视为同一验证项；不得借此清理既有输出、真实数据或用户文件。
6. 用户可以明确授予“全部必需验证通过且候选无漂移时关闭”的条件授权。条件不满足时不得关闭，也不得把失败结果改写为通过。
7. 关闭前先判断活动方案退出后条件目录是否为空，并检查受影响测试是否读取缓存 Git 索引；可预见需求必须在授权包中一次列出，不等失败后才追加。
8. 真实 Git 索引、commit、push、PR、发布、安装、联网、产品进程和真实数据没有被逐项列明时始终保持未授权。
9. skeleton 保存的每份方案必须实例化收尾字段；没有关联职责时写“不适用”及依据，存在关联方案时记录共享文件、
   对方状态和联合复核触发。项目级模板是规则真源，方案只填写任务特定值，不复制完整模板正文。
