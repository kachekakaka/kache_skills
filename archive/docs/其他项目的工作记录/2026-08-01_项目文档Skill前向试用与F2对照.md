# 项目文档 Skill 前向试用与 F2 对照

## 结论

本轮分别在 hg_workspace、bili_workspace、douyin_recorder_workspace 和
bili_uploader_workspace 上执行了独立的 project-doc-consistency check 与
project-doc-skeleton check。四个工程均保持只读，没有运行命令、修改文件、调用 Git、联网或接触真实数据。

两项 Skill 的问题发现和边界判断已经达到可用水平：四个工程的关键预期均被识别，没有出现错误归档、
把有意重叠判成重复、越权修改或把开放治理报告为闭环的硬失败。最明显的新问题不是“还找不到问题”，而是
全量 check 容易继续扩张证据范围，多个执行任务需要评估者提示停止新增读取后才收束报告。

本轮只验证 check 体验，不验证 sync、apply、命令执行或目标工程的动态通过状态。

## 试用方法

- 每个工程、每个模式使用没有预置诊断结论的新任务。
- 执行任务只收到 Skill 路径、目标工程路径、显式模式和只读边界。
- 执行任务不得读取本目录既有工作记录、其他待测工程或 F2。
- 一致性任务覆盖活动文档、直接相关源码、测试、Registry、suite 与 CI。
- 骨架任务只做结构、入口、六类生命周期、待办/方案/归档和收口方案，不审计产品事实。
- F2 仅由评估者只读抽查，作为治理成熟度参照，不作为固定目录模板。
- 首轮曾把两个模式串在同一任务；该样本不计入模式隔离评分。最终评分只采用重新执行的独立模式样本。
- 所有记录在执行任务结束后才写入，避免工作记录污染后续判断。

## 跨项目发现

1. 核心文档有正文不等于闭环。HG 和上传器都被发现有高置信度的“文档契约与代码实现不一致”。
2. 兼容路由必须有收敛待办和退出条件。bili_workspace 的核心文档长期停在路由页，无法成为当前真源。
3. 历史材料是否退出活动导航，是后三个工程共同的主要差距。
4. Registry 存在不等于测试治理完成。还必须核对 suite、真实命令、断言、CI 触发和安全分类。
5. 多层测试覆盖同一行为通常是有意重叠。本轮没有把 Docker smoke 与 D6 E2E、单元 replay 与 CLI replay
   误判为重复。
6. 高成本或真实现场测试的触发方式必须与 explicit 分类一致；不能只在文档里声明安全边界。

## 对 Skill 的优化建议

### P0：增加全量 check 的自主收束协议

- 先形成活动范围清单，再只沿会影响结论的声明读取直接证据。
- 同一根因的文档和测试问题合并报告，不逐文件重复展开。
- 证据不足时立即使用无法验证，不为了排除所有可能性无限扩张源码范围。
- 无论是否完成全部动态验证，都必须在当前任务内输出可解释的范围账本和最终状态。

### P0：强化测试设计参考

- 显式比较 SAFETY 中的 explicit/真实数据规则与 CI 的 push、PR、定时和默认输入。
- 比较 workflow 路径过滤与 Dockerfile、锁文件、脚本、契约和 suite 文档的真实输入依赖，识别漏触发和
  过宽触发。
- 比较实际测试脚本的输出根、所有权标记、路径 containment、保留和清理行为与 SAFETY 声明。
- 把“测试在断言当前实现，但当前实现违反权威契约”稳定归为声明错位或覆盖缺口，不误写为失效测试。

### P1：完善前向测试协议

- 标准提示必须明确写全量或增量，不能只写风险抽样。
- consistency 与 skeleton 必须保持独立任务；不得把前一个 Skill 的诊断带给后一个执行者。
- 后续在干净隔离副本中分别验证“check 后确认 sync/apply”和“直接审计并修复”，再评价修改体验与 diff
  质量。

## 建议的下一轮

优先在隔离副本中选择 douyin_recorder_workspace 与 bili_workspace 做修改型试用：前者覆盖事实冲突、
测试安全和大规模历史收口，后者覆盖首次同步兼容路由、测试 Registry 拆分和归档决策。两者通过后，再用
HG 做防过度修改回归，用上传器验证复杂测试治理。
