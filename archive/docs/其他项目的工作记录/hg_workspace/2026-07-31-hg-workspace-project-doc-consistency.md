## 实战中暴露的问题

### 1. 全量审计的证据映射成本高

项目同时包含后端、Web、Android、CI、Compose、ADR 和测试治理。为了避免把摘要遗漏误判为错误，需要逐项判断文档职责、声明类型和证据抽象级别，人工检查范围较大。

建议：在 Skill 内增加不持久化的检查清单，按“构建交付、运行拓扑、数据契约、用户行为、测试入口、运维边界”六类建立证据路由；这不是项目 manifest，只用于本轮内存工作台。

### 2. 内容问题与结构问题对用户不够直观

一致性审计能发现 Registry 与 CI 的覆盖关系，但按边界不能直接修改 Registry。若只报告“不能改”，用户容易认为流程停滞或 Skill 能力不足。

建议：输出固定的交接表，包含“发现、为什么不能由当前 Skill 修改、目标流程、是否需要用户决定”。没有真实取舍时可继续串联执行，但必须保持授权边界独立。

### 3. 技术结论需要白话前置

在解释剩余问题时，用户反馈“看不懂”。详细证据对优化和审计有价值，但不适合作为第一层交互。

建议：先输出白话版，例如“有一条测试假数据长得像密钥，未来 CI 会误报；另有几项 CI 检查没有写进测试目录”。随后再展开路径和规则。

### 4. 静态事实与动态结果需要更醒目地区分

代码和配置可以证明“存在健康检查流程”，不能证明某个当前候选实际运行成功。全量内容审计很容易在总结措辞中越过这条边界。

建议：最终报告固定分成“静态事实已同步”“动态运行未验证”两栏；只有有运行证据时才使用 passed 或整体通过措辞。

### 5. `sync` 的非持久化报告边界与复盘需求并不冲突

Skill 正确地禁止默认创建持久化审计报告，避免生成第二真源。但用户在完成后明确需要实战记录来优化 Skill。

建议：继续保持默认不落盘；增加一条说明，允许在独立、明确的后续请求中生成“历史复盘记录”，并要求放入归档、标明非当前真源、链接回当前 SKILL。

### 6. CI 与 Registry 的一致性可以更早检查

当前规则将 Registry 格式视为机械结构，将具体触发与命令视为内容事实。本次直到全量代码/CI 审计后才发现多个稳定 CI 检查没有 suite 承接。

建议：全量检查时固定比较“CI 稳定步骤 ↔ Registry suite ↔ suite 规范命令”，只报告缺口；结构修改仍交给骨架。

## 建议优化优先级

1. **P0：白话结论优先。** 先说明实际影响，再给证据和边界。
2. **P1：全量审计证据路由。** 使用六类内存检查清单降低漏项和重复阅读。
3. **P1：结构交接表。** 统一展示当前 Skill 不能修改但可继续处理的问题。
4. **P1：静态/动态结论分栏。** 防止把配置存在误写成运行通过。
5. **P1：CI、Registry、suite 三方比对。** 作为全量内容检查的固定步骤。
6. **P2：显式请求下的归档复盘。** 不改变默认禁止持久化报告的规则。
