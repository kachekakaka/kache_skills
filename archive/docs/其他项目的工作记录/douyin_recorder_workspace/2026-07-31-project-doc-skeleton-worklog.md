## 8. 有效设计点

- 单一上下文前置检查阻止了无依据的上下文压平。
- “结构 Skill 不填产品事实”的边界有效：骨架提交与后续事实同步形成两个独立、可回退的里程碑。
- 实际 Markdown 链接和两跳可达性比维护第二份 manifest 更直观，T-DOC 能立即发现入口遗漏。
- 条件目录没有被预先批量创建，避免空目录和虚构职责。
- 对未确认旧文档采取“不移动、不删除”的保守迁移策略，保护了历史资料。
- 通用门禁资产有固定哈希和隔离规则夹具，安装结果可复现。

## 9. 摩擦、偏差与风险

1. **授权语义存在张力。** 用户使用了明确动作词并要求不中断，项目规则又要求 commit + push；Skill 同时规定显式调用只授权只读调查，且 Git 操作必须分别授权。执行依赖了对用户意图和项目规则的综合解释，Skill 没有给出清晰优先级。
2. **首次迁移的必答项过多。** 语言、构建入口、交付物、真实数据边界可以从项目规则和现有入口直接证明，但 Skill 的“必须得到明确结果”容易被理解为仍需逐项询问，和“能够调查的事实不得反问用户”形成操作张力。
3. **空职责文档会立即产生二阶段工作。** 骨架正确地不填产品事实，但 `需求文档`、`设计文档` 和 `字段契约` 在提交后只有职责句，必须紧接一次 consistency sync 才对维护者有实际价值。
4. **通用资产与仓库 Ruff 不兼容。** 两份要求逐字节复制的 T-DOC 资产在把 `SoftwareTesting/` 纳入 Ruff 时产生 7 条告警；项目既不能就地修复，又没有随资产提供明确 lint 排除或资产自身 lint 保证。
5. **既有历史文档数量较多。** 为满足两跳可达性，`docs/README.md` 需要直接列出大量阶段资料，入口可用但会持续增长；Skill 没有提供历史资料“先登记、后裁决归档”的紧凑迁移模式。
6. **Git 恢复性与外部备份规则有效但需解释。** 本次所有结构修改均由 Git 精确恢复，因此未创建外部备份；用户可能把“没有备份”误解为遗漏，最终报告应固定说明判断依据。

## 10. 对 Skill 的改进建议

### 优先级 A：授权与规则优先级

- 增加动作词矩阵：`检查`、`初始化`、`迁移`、`修复` 分别默认授权到哪一步。
- 明确项目 `AGENTS.md` 已要求 commit/push 时，是否仍必须重复取得独立确认；如果必须，明确其优先于项目规则。
- 允许用户一次性表达“采用固定基线 + 写入 + 普通验证 + commit + push，但不建 PR”，并要求执行器回显解析结果。
- 把“必须得到明确结果”拆成“可由项目真源直接证明”和“必须由用户选择”两类，避免不必要询问。

### 优先级 B：迁移与交接

- 为“已有文档但本轮不移动”的首次迁移增加正式安全路径：只建入口、索引和空职责文档，并输出待裁决的归档候选。
- 明确骨架完成后何时建议立即调用 consistency sync，以及两次提交应如何分界。
- 为大量历史文档提供可选二级索引策略，避免 `docs/README.md` 无限增长，同时保持两跳门禁可判定。
- 在最终交接模板中固定列出：未移动文档、未创建条件目录、备份判断、未授权 Git/外部操作。

### 优先级 C：机械资产

- 让通用 T-DOC 资产自身通过一个声明版本的 Ruff 配置，或随资产提供明确的 lint 排除边界。
- 在规则夹具输出中打印资产版本或哈希，减少额外哈希命令。
- 增加“目标仓库既有 lint 是否覆盖 SoftwareTesting”检查，并在安装前提示兼容性，而不是到全量验证时才发现。
