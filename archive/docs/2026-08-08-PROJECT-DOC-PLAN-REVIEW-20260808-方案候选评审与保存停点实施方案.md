## 1. 目标与已确认决定

本方案把已确认的语义决定落实为两个 Skill 可观察且一致的运行流程，不恢复施工、验证或关闭阶段，也不让两个 Skill
产生运行时依赖：

1. 新问题可能形成方案、或用户明确要求修订已有方案时，在实质调查前取得用户选择的正整数评审轮数；询问时推荐
   两轮，不静默采用推荐值。已有活动方案的普通施工、验证或关闭请求仍直接交给普通任务，不为它询问无用轮次。
2. Skill 完成只读检查和对话报告后，只在当前调用内形成未保存的方案候选；围绕已经冻结的证据完成指定轮次的
   自我评审、自我修订和变更后复核，不把每轮评审变成第二次完整审计，也不在评审期间新增或覆盖活动方案。
3. 可以直接调查的事实由 Skill 自行查明。发现证据无法唯一裁决的语义决定，或目标明确但副作用超出当前授权的
   授权差额时，一次只询问用户一个问题并提供推荐答案，不以推荐项代替用户确认，也不混写两类停点。
4. 用户明确暂缓的事项可以进入 `待确认` 方案，但受影响切片不得进入确定实施范围，必须记录选项、推荐、影响、
   最小解除条件和残余，且不能宣称对应评审已经完成或请求实施该切片。
5. 指定轮次完成后，Skill 展示目标、保存路径、用户决定、确定范围、残余及完成轮次，再询问是否保存。用户在方案
   候选形成前表达的修复或保存意愿不能替代这个最终停点；只有最终确认后才一次写入活动方案及必要待办。
6. 修订已有方案使用同一流程，原文件在最终保存确认前保持不变。保存后只允许机械核对写入结果与已评审候选一致，
   随即停止；不得再做会改变内容的评审、施工、验证、Git、归档、删除或关闭。
7. 没有可施工问题时不创建待办或空方案；对话检查报告仍直接输出。用户选择持久化检查记录时，只使用项目已有
   承接位置，并在写入前完成所选轮次的结果复核和最终保存确认。
8. 普通需求不会因曾使用两个 Skill 而自动生成方案。已经保存的方案由普通任务在后续明确实施授权下执行；完成时
   更新实际受影响的长期真源，并按目标项目生命周期退出待办、归档方案和更新索引，不机械重写全部长期文档。
9. 冻结检查完成后在调用内维护稳定临时发现标识；最终保存问题前，对账发现清单、覆盖／残余矩阵和候选处置的成员
   与数量。缺失、重复或无归宿时作废受影响评审并回到候选修订，不把漏项后的保存问题视为有效停点。

不新增持久 review 日志、profile、manifest、跨 Skill 共享运行状态、辅助脚本或第三个工作流。

## 3. 确定实施切片

### 3.1 两个 Skill 的核心流程

1. 修改 `project-doc-skeleton/SKILL.md`：在核心阶段中建立评审轮数、未保存候选、逐项决策、轮次内修订、最终保存
   确认和一次写入；同步无问题检查记录、已有方案修订和报告／保存段落，删除或改写所有“保存后静态自审”的活动

2. 修改 `project-doc-consistency/SKILL.md`：使用同一候选与保存停点，保持所有权停点、`full`／`incremental`、双遍、
   测试设计条件触发、综合方案和切片就绪边界不变。待决事项只能按第 1 节进入可能范围，不能由评审代用户裁决。
3. 每个评审轮次都检查当前候选与冻结证据、用户决定、确定／可能路径、验证副作用、授权、完成条件和收尾字段；
   本轮修订后核对改动没有引入内部矛盾。轮次数量不授权扩大冻结范围或新增副作用。
4. 保存后的核对只证明持久化内容与最终候选一致，不恢复内容 review。已有活动方案的普通后续请求继续交给普通任务；
   只有明确的方案修订请求才进入候选流程。
