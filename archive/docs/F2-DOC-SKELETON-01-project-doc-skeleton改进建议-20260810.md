# F2-DOC-SKELETON-01：project-doc-skeleton 改进建议报告

> 性质：项目治理完成后的经验报告，不是实施方案或当前项目真源
> 形成日期：2026-08-10
> 来源：外部 F2 项目归档方案《测试资产骨架治理实施方案》（未复制到本仓库）
> 后续用途：用户以后在 `project-doc-skeleton` Skill 工作区发起独立优化任务时作为输入

## 1. 结论

本次治理验证了 `project-doc-skeleton` 的主体方向有效：先识别项目路线、真源、入口、生命周期、测试治理和
机械门禁，确实能发现普通内容审查不容易暴露的结构问题。需要改进的不是继续扩大默认扫描范围，而是把
“请求分流、上下文判定、资产证据、生命周期与执行暴露”定义得更精确。

优先建议解决三件事：

1. 把检查报告、实施方案、实际施工和施工后经验报告分成独立产物与阶段；
2. 上下文数量优先服从用户和项目的明确治理声明，不能从语言、产品或上游数量直接推导；
3. 测试资产盘点先建立 Git 感知的候选集合，再区分活动独立项、活动附属项、隔离保留项和历史项，同时
   单列外部写等执行副作用。

本报告没有修改用户级 Skill 包，也不要求 F2 项目继续承接通用 Skill 规则。

## 2. 本次项目治理提供的事实

| 观察 | 治理动作 | 验证后的结论 |
| --- | --- | --- |
| 两个已经停止的 unlike 在线可行性目录仍在活动测试根，且 README 保留直接运行命令 | 将 Git 资产移入 `archive/SoftwareTesting/`，归档 README 只保留追溯边界 | “有 README”不能证明仍是活动测试；生命周期和外部写暴露必须先于内容完整度判断 |
| `download_tag_policy` 是可运行的普通验证，但没有活动入口 | 增加 Registry 链接，不加入 Release manifests | 活动测试身份与正式全量选择身份是两套关系，不能相互推导 |
| `test_infrastructure` 已有 Registry ID，但不是可点击入口 | 把原有 ID 改为指向 README 的链接 | 文本出现不等于导航可达，骨架检查应验证实际链接关系 |
| `structured_merge_accumulator` 没有独立 Registry 行 | 保留 `index_atomicity` 的唯一直接所有者和既有 CTest 合同 | 未登记项不一定是孤儿；明确的活动附属项是合法状态 |
| CMake 注册 `unlike_browser_feasibility_contract`，但 Release CTest expected manifest 不选择它 | 归档历史 Python 入口，不改 CMake/CTest | 实现、普通测试入口、CTest 身份和 Release 选择可以分别处于不同生命周期 |
| 工作区存在被忽略的 `__pycache__`，同时归档移动尚未暂存 | 门禁使用 Git 已跟踪文件加未忽略新文件，并过滤已经不存在的索引路径和生成残留 | 只看物理目录或只看 Git index 都会误判当前工作区 |

本次定向验证结果：测试资产结构规则 7 个纯函数正反例通过；`doc_consistency` 最终通过并检查 72 份活动
Markdown。外部普通 run 为 `doc_consistency-260810T143152Z-93d50fd3`。

## 3. 建议改进项

### S-01：按请求意图分流产物

影响：高。

Skill 应在检查开始前识别至少四种模式：

- `audit_report`：只给发现、证据、影响和建议，不创建待办或方案；
- `implementation_plan`：用户已确认需要治理时，建立待办并保存唯一活动方案；
- `implementation`：用户明确开始施工后，切换项目状态并执行方案；
- `post_implementation_report`：施工和验证完成后，单独沉淀可迁移经验。

检查报告不能因为内容足够详细就自动成为方案；实施方案也不能把施工后才能成立的经验报告冒充为已完成
交付。本次最初把“实施方案”和“Skill 建议报告”合并命名，正是缺少这一分流造成的。

### S-02：把“允许有方案”和“已经施工”分开

影响：高。

标准骨架不应硬编码“只有实施中才能创建方案”。项目可以允许 `待实施` 事项预存至多一份方案，同时要求
`实施中` 必须有且只有一份方案。Skill 应先读取项目的状态词和生命周期规则，再判断方案是否合法。

建议在检查输出中分别记录：

- 当前待办状态；
- 是否允许存在方案；
- 是否已经取得施工授权；
- 方案存在是否能证明已经开工。

### S-03：把单一上下文定义为治理选择，而不是技术拓扑

影响：高。

F2 同时包含 C++ 与 Python、Desktop 与 Server，并集成外部上游，但由同一维护者明确使用一套入口、待办、
生命周期和测试协议。因此它是一个上下文。Skill 应采用以下证据优先级：

1. 用户在当前任务中的明确声明；
2. 项目长期规则和公开入口中的明确声明；
3. 实际所有权、发布节奏、术语和变更闭环；
4. 只有前三项没有结论时，才从目录、语言、产品或上游拓扑推测。

这不等于“单维护者项目永远只有一个上下文”。真正可迁移的规则是尊重明确治理边界；维护者人数只是解释
该选择的事实之一。

### S-04：先建立 Git 感知的资产候选集合

影响：高。

骨架检查不应把磁盘上的所有目录都当成项目资产，也不应只读取当前 Git index。建议的候选集合语义是：

1. 已跟踪且当前仍存在的文件；
2. 未跟踪但未被 ignore 的新文件；
3. 排除 index 中已经删除的旧路径；
4. 排除缓存、报告输出、项目 Agent Skill、空目录和仅含忽略文件的残留；
5. Git 不可用时明确标记证据不足，不从物理目录猜测活动身份。

本项目使用的等价读取是限定路径的
`git -c core.fsmonitor=false ls-files --cached --others --exclude-standard -z`，再以当前文件存在性过滤。通用
Skill 可以描述语义，不应硬编码 PowerShell 命令或 F2 路径。

### S-05：为测试资产增加生命周期与执行暴露两个轴

影响：高。

建议至少使用四种生命周期状态：

| 状态 | 含义 | 最小结构要求 |
| --- | --- | --- |
| 活动独立项 | 可被任务直接选择 | 当前 Registry 或等价目录中有唯一身份和可达入口 |
| 活动附属项 | 只补充另一个活动项 | 有且只有一个明确的活动所有者，不重复建立身份 |
| 隔离保留项 | 仍被构建或合同消费，但不再是普通入口 | 标明消费者、禁止推导为活动手工入口 |
| 历史项 | 只用于追溯 | 位于历史区域，不出现在活动 Registry，不提供当前运行指引 |

生命周期之外还应记录执行暴露，例如：纯结构、合成本地、读取真实数据、外部只读、外部写入。外部写入口即使
文档和安全步骤齐全，只要路线已经停止，其留在活动根的影响也应高于普通断链。

### S-06：分开 Registry、所有者、执行身份和正式选择范围

影响：中高。

通用检查应避免以下错误推导：

- 不在 Release manifest，不代表不是活动普通测试；
- 不在 Registry，不代表一定是孤儿，可能是有唯一所有者的附属项；
- 有 CTest 或构建 target，不代表对应历史脚本仍是活动入口；
- 归档一个脚本入口，不自动授权删除产品合同或构建消费者。

建议为每个测试资产记录可选关系：`registry_identity`、`owner`、`direct_consumers`、`execution_identity`、
`release_selection`。Skill 只要求能解释关系，不要求所有项目创建新的 manifest。

### S-07：消费者冻结应包含“存在”和“不存在”的证据

影响：中。

施工前的一跳消费者复核不仅要列出命中，还应记录关键范围内没有命中。例如本次确认 HTTP 历史脚本没有
目录外消费者，同时确认 browser 的 CMake/CTest 合同存在而 Release expected manifest 没有该身份。后者
避免把“有 CTest”和“属于正式 Release CTest 集合”混为一谈。

建议检查报告对关键判断使用三态：已证明存在、已证明不存在、证据不足，而不是把无搜索结果直接写成事实。

### S-08：给发现增加影响级别和唯一归宿

影响：中。

每项发现至少记录：证据、用户可理解的影响、建议归宿、是否阻断施工。链接不可点击、活动入口缺失、危险的
外部写命令仍可见，不应显示为同一严重程度。每项还应只有一个归宿：当前整改、后续待办、经验报告或明确
不处理，避免同一问题同时散落在报告和方案中。

## 4. 建议的 Skill 工作流

1. 识别用户要的是报告、方案、施工还是施工后复盘；
2. 读取项目明确的上下文与文档生命周期规则；
3. 建立 Git 感知、路径有界的候选资产集合；
4. 冻结当前入口、所有者、一跳消费者、生命周期和执行暴露；
5. 使用“满足／缺口／不适用／证据不足”输出结构矩阵，并给缺口分级；
6. 报告模式到此结束；只有用户确认治理时才建立待办和方案；
7. 施工模式按项目状态规则切换到实施中，完成后验证每条完成条件；
8. 只有用户要求反哺 Skill 时，才生成独立经验报告；Skill 本体修改留在 Skill 工作区。

建议把主流程留在 `SKILL.md`，把测试资产分类、请求分流示例和验收样例放入 references，避免主文件因覆盖
每种项目形态而持续膨胀。

## 5. 建议增加的 Skill 验收样例

1. 用户只要两轮骨架检查：输出检查报告，不创建方案；
2. 项目允许待实施预存方案：保存方案后仍保持待实施，直到用户明确开工；
3. 一个维护者同时维护多语言、多产品和上游集成：若项目明确声明单一上下文，不建议拆分；
4. 活动测试根下只有被 ignore 的缓存：不报告为活动测试项；
5. 未暂存的目录移动：新归档文件可见、旧 index 路径因文件已不存在而不算当前资产；
6. 一个未登记 README 被唯一已登记测试 README 直接链接：判定为活动附属项；
7. 一个测试有 CTest target、但没有 Release expected 身份：分别报告，不合并结论；
8. 已停止的外部写验证仍提供命令：按高影响生命周期缺口报告；
9. Git 不可用：输出证据不足，不退化为全盘目录猜测；
10. 用户要求项目治理后再反哺 Skill：实施方案和建议报告使用不同文件、不同生成时点。

## 6. 不应硬编码进通用 Skill 的 F2 特例

- `download_tag_policy`、`structured_merge_accumulator`、两个 unlike 目录及具体 CTest 名称；
- F2 的 Registry 列名、三份 Release manifest 名称和 `archive/docs/` 报告路径；
- “C++、Python、Desktop、Server、集成上游必然属于一个上下文”；本项目如此是因为用户和项目规则明确选择；
- 所有项目都必须使用 Git；非 Git 项目应允许使用等价的显式资产清单，但必须标记证据来源；
- 所有附属项都不得登记；是否独立登记取决于项目的选择、执行和证据模型。

## 7. 后续 Skill 工作区交接边界

后续独立任务可以使用 `skill-creator` 检查并修改 `project-doc-skeleton`，建议顺序为：

1. 先更新请求分流、生命周期和上下文判定；
2. 再补测试资产分类与 Git 感知证据规则；
3. 把详细样例放入 references，保持 `SKILL.md` 只承载决策流程；
4. 复核 `agents/openai.yaml` 的触发描述是否仍与主流程一致；
5. 增加上述验收样例并运行 Skill 基础校验。

该后续任务不得把本报告中的 F2 路径直接复制为通用默认值。本次项目任务到报告交付为止，不修改
`C:\Users\73839\.codex\skills\project-doc-skeleton`。
