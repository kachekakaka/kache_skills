## 1. 目标与已确认决定

本方案修正两个 Skill 在必须暂停让用户拍板时的交互层级：用户决定目标结果、风险、成本和授权，Codex 根据证据决定
纯技术实现。改动不减少必须由用户确认的真实语义决定或授权差额，也不改变只读检查、逐项停问、候选评审、最终保存
确认和普通任务接手的现有阶段。

已确认采用以下结果：

1. 提问前先用允许的只读调查、项目规则和既有确认决定消解能够唯一裁决的问题；纯实现选择不下放给用户。
2. 仍需拍板时使用统一的“用户决策卡”：先用日常语言说明用户可感知的结果差异，再给明确推荐、各选项的好处／代价／
   可回退性和简短回复方式；内部字段、测试分类、路径、哈希、manifest、marker、pack 等只进入末尾可跳过的技术备注。
3. 语义决定卡使用“需要你决定的结果”，授权差额卡使用“需要你允许的动作”；两类停点继续一次只问一个，不混写。
4. 用户回复“按推荐”视为对当前卡片中已经明确命名的推荐项作出显式选择；Codex 随后用一句白话复述已记录结果，
   不把沉默、模糊回复或历史推荐当作确认。
5. 两个容易混淆的概念并存时，第一句先说明“这不是 X，而是 Y”；不得自行创造用户未使用的新流程名称，必要术语
   首次出现时用一句白话解释。
6. 评审轮数和最终保存停点也采用同一白话原则。评审轮数问题说明“交付方案前需要我自查几遍”，推荐两轮，并允许用户回复
   正整数或“按推荐”；最终保存问题明确“只保存方案，不开始实施”。

不修改仓库外的 Codex 全局 `AGENTS.md`。本方案以两个 Skill 自身的运行时契约为根修复；全局沟通偏好如需
调整，作为独立范围另行确认。

## 2. 初始证据与覆盖／残余矩阵

### 2.1 冻结发现

- `F-01`：两个 `SKILL.md` 已要求“事实自行查明、一次只问一个并给推荐”，但没有要求问题先从技术动作翻译为用户
  可感知结果，也没有固定简短回复协议。
- `F-02`：现有规则虽允许项目规则或既有决定唯一裁决，但真实使用仍出现把测试归类、标准资产迁移等实现选择直接交给
  用户的情况，说明“何时不该问”的门槛不够可操作。
- `F-03`：独立的应用版本与运行资产版本等同名概念没有强制消歧，用户可能把局部技术版本误解为产品版本。
- `F-04`：流程名称或审计标签可能在未定义时直接出现，使用户误以为新增了另一套流程。

## 3. 确定实施切片

### 3.1 共享术语与决策卡

1. 在 `CONTEXT.md` 定义“用户决策卡”，并与现有“语义决定”“授权差额”“副作用效果摘要”分工：决策卡负责所有
   用户停点的白话呈现；涉及外部副作用时，在卡片的选项影响中复用“会发生／不会发生／既有状态”摘要。
2. 决策卡保持短小，至少包含：需要决定或允许的事、推荐及理由、各选项的实际结果与主要代价、简短回复方式；只有
   确实帮助复核时才追加“技术备注（可跳过）”。技术备注不得承载作出决定所必需的信息。
3. 明确“按推荐”只绑定当前卡片中已经陈述的推荐项。新问题、推荐改变或概念发生漂移时必须重新询问。

### 3.2 两个 Skill 的核心运行时规则

1. 修改 `project-doc-skeleton/SKILL.md` 和 `project-doc-consistency/SKILL.md` 的共同停问规则：先判断现有证据能否唯一
   裁决，再区分语义决定与授权差额，最后按对应决策卡提问。保留一次一问、轮次暂停、待确认切片和最终保存边界。
2. 把“已有项目规则或已确认决定能够唯一裁决时直接采用”改成可执行检查：列出决定来源和用户可感知结果，不再追加
   “是否确认采用该技术实现”的重复问题。标准路线或推荐仍不能代替真实治理取舍。
3. 更新评审轮数入口：第一次出现时用白话说明用途；有效正整数直接采用，“按推荐”明确映射为两轮并复述选择。
4. 对范围升级、路径／所有者治理选择、版本语义、测试归属和授权差额等现有停点统一应用决策卡，但不在 Skill 中写死
   具体项目答案。用户是技术专家时仍先给结果摘要，再把精确标识放入技术备注。
5. 保持核心规则直接位于两个 `SKILL.md`，不新增共享运行时参考或跨 Skill 依赖；实施时按 `skill-creator` 原则删去被
   新规则完全覆盖的重复句，避免仅追加大段模板造成上下文膨胀。
6. 读取 `skill-creator` 的 `openai.yaml` 参考后，更新两个 `agents/openai.yaml` 的 `default_prompt`，使其与白话决策卡、
   “按推荐”和现有阶段一致；显示名、短说明及 `allow_implicit_invocation: false` 保持不变，除非结构校验表明必须同步。

### 3.3 长期文档和前向契约

1. 更新 `docs/README.md` 的方案生命周期、`docs/需求文档.md` 的两个 Skill 可观察行为，以及 `docs/设计文档.md` 的共同
   阶段模型和两条处理流；只加入决策资格与表达契约，不重写既有职责和授权阶段。
2. 更新 `SoftwareTesting/manual/project_doc_skills/README.md`：在两个落方案样本与硬断言中要求决策卡、概念消歧、
   “按推荐”显式选择，以及已有规则足以裁决时不重复询问。
3. 更新 `SoftwareTesting/manual/project_doc_skills/contract-cases.md` 的既有 plan-handoff 夹具，不新增第六个代表性样本：

   - Consistency 样本加入两个容易混淆的版本或字段体系，断言首句先消歧，再用白话结果卡询问真正语义；
   - 两个样本都断言技术标识只出现在可跳过备注，用户可用“按推荐”完成明确选择。
4. 不新增自动评分脚本或持久运行日志。评估者仍使用原始自然请求、隔离目标和隐藏预期，执行任务不得读取契约夹具。
