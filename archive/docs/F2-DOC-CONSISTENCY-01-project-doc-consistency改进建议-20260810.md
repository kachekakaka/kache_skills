# F2-DOC-CONSISTENCY-01：project-doc-consistency 改进建议报告

> 性质：项目治理完成后的经验报告，不是实施方案或当前项目真源
> 形成日期：2026-08-11
> 来源：外部 F2 项目归档方案《现行文档与验证身份一致性治理实施方案》（未复制到本仓库）
> 后续用途：用户以后在 `project-doc-consistency` Skill 工作区发起独立优化任务时作为输入

## 1. 结论

本次治理验证了 `project-doc-consistency` 的三个核心判断是可靠的：事实所有者优先于测试消费者，活动与历史
材料必须分开，静态检查与普通任务施工必须分阶段。它正确识别出“产品合同已经禁止写入，但旧写入测试仍然活动”
不是需要重新选择产品语义，而是失效消费者需要退出；也正确把动态验证保持为 `not_run`，交由取得授权的普通任务
执行。

最需要补强的不是扩大默认扫描，而是静态方案交给普通任务后如何承接一次长周期、可恢复的全量验证。本项目在实施期
连续暴露验证身份漂移、夹具合法性、源码提取器、GUI 进程生命周期和系统安全桌面干扰；这些都能由当前权威唯一裁决，
却缺少一套通用的“实施期验证漂移分流、证据失效与复用、动态成本和外部阻断”表达。

优先建议解决四件事：

1. 分开静态审计发现与实施期验证漂移，既保持原发现集合稳定，也不把后来暴露的问题静默塞进一个大类；
2. 让全量验证方案明确输入快照、失效条件和可证明的阶段复用；
3. 在计划中暴露产品启动次数、自然退出时长、GUI 生命周期和外部桌面干扰等真实成本；
4. 把合成夹具合法性与手写源码提取器的脆弱性纳入有条件测试设计审计。

本报告没有修改用户级 Skill，也不要求 F2 项目继续承接通用 Skill 规则。

## 2. 本次项目治理提供的事实

| 观察 | 治理或验证动作 | 验证后的结论 |
| --- | --- | --- |
| 当前产品合同明确取消喜欢入口必须零写入，但旧浏览器验证壳仍能点击真实喜欢按钮并注册 CTest | 按产品权威退役写入壳，在零写入测试增加防回流负合同 | 活动测试身份不是业务权威；失效消费者不能仅因仍在 CMake/CTest 中就与产品合同同级 |
| 默认 CMake 声明 37 项、expected manifest 只有 34 项，三项差异中一项已退役、两项仍是现行合同 | 删除退役身份、补入两项现行身份、同步 revision 13，并增加静态同序精确对账 | 测试身份一致性不只是“是否存在”，还包括所有者、顺序、唯一性、集合和协议版本 |
| 全量验证修复多次只改变测试或协议输入，没有改变 503 项产品构建输入及已构建产品字节 | 每次重新 review／source-freeze；有证明时复用 clean rebuild 与 36/36 CTest，只重跑失效动态项 | “源码有变化”不等于“所有证据全部失效”；复用必须由输入分类和产品指纹证明，不能凭经验判断 |
| 多个合成 Cookie 使用任意字符串，现行严格解析器只接受 `name=value` | 把完全虚构的值改成合法离线格式，再重跑相关场景 | 合成不等于可以绕过当前输入合同；夹具必须先通过与产品相同的最低合法性规则 |
| 多个静态测试用字符串切片提取 C++ 函数，误把前置声明当定义，或绑定旧签名、旧 overload | 提取器改为跳过声明、按花括号闭合并显式选择 overload，增加缺失／未闭合负例 | 手写源码提取器本身是测试实现风险，不能把一次字符串命中当作可靠实现证据 |
| GUI 子系统产品没有可附加的私有 console，旧测试仍声明 Ctrl-Break 收敛 | GUI owner 显式使用既有测试自动退出缝并验证 `natural` 生命周期、返回码和无强杀 | 进程退出合同取决于产品子系统和所有权；通用“发信号即可优雅退出”会制造虚假失败 |
| Feed 产品状态和坐标正确，但点击命中 Windows 安全中心的安全桌面 | 保留命中窗口与前台句柄证据，不绕过或伪造输入；安全桌面消失后原场景重跑通过 | 系统级输入拦截应判为外部环境阻断，不是产品失败；计划需要可恢复停点和禁止绕过边界 |
| 最终文档收口触发 source refresh 后，已有 `post-dynamics` 单例不能覆盖，状态却回到进行中 | 保留原指纹；只有产品/runtime closure 和 21 个必需 child 当前快照全部精确有效时，另写刷新复用证明 | 不可变最终证据与可恢复编排状态必须同时设计；“禁止重复写”不能使合法 refresh 永远无法闭环 |
| 全部技术阶段通过后，bundle 状态是 `evidence-ready`，Registry 和 post-evidence 仍为空 | 只生成技术指纹，不运行认证回写 | “全量测试通过”与“正式 Release 认证通过”是不同终态，必须同时说明已完成和明确未执行的阶段 |

最终技术证据包括：36/36 CTest、17/17 directed、11/11 核心矩阵、最小 GUI 入口和最终指纹通过；核心矩阵
本轮执行 DFP 28/28 profile、60 次产品启动，其余 10 套按当前共享快照复用。最终 bundle 为
`release-bundle-260810T160240Z-cbcc4573`，状态 `evidence-ready`。

## 3. 建议改进项

### C-01：为静态发现和实施期验证漂移建立双层归宿

影响：高。

当前 Skill 要求冻结发现集合，并让报告、矩阵和候选精确对账，这对防止静态审计漏项非常有效。但普通任务执行
全量验证时可能出现三种后来事实，不应全部并入原发现，也不应因此重跑完整审计：

- `同一不变量的消费者漂移`：当前权威已唯一给出结果，失败的是旧测试、夹具、选择器或生命周期声明；允许在原切片
  的验证修复通道内处理，但必须记录直接证据、修改范围和重验义务；
- `新的范围问题`：不能由原权威或一跳消费者唯一裁决；保留方案活动，形成精确残余或新的用户决定；
- `外部环境阻断`：源码和断言没有被证明错误，只记录恢复条件和安全边界，不计为新的内容发现。

建议方案模板增加“实施期验证漂移分流规则”，但不要把逐次失败日志写进静态检查产物。普通任务只在最终归档方案中
总结有结论的漂移及其证据。本项目把大量后来漂移都写入 C-02 的一跳阻塞，虽然完成了闭环，但类别过宽，降低了
复核者识别因果关系的效率。

### C-02：把验证身份链作为一等关系

影响：高。

当冻结声明直接涉及测试身份、Registry、suite、CTest、CI 或 Release 选择时，建议有条件测试设计审计记录以下关系：

- 业务或治理权威是谁；
- 实际声明身份和顺序；
- expected 或选择清单身份和顺序；
- 唯一性、集合差异与协议版本；
- 直接执行入口、核心断言和正式选择范围；
- 哪一层只是消费者，哪一层有权改变契约。

这不是要求所有项目新增 manifest。项目使用有序清单时检查顺序，使用无序集合时只检查其声明的语义。Skill 应避免
“在 Registry 中所以是当前业务权威”“有 CTest 所以属于正式 Release”“清单包含所以实现一定存在”等反向推导。

### C-03：在全量验证方案中声明证据失效与复用模型

影响：高。

用户要求全量测试时，综合方案应为每个阶段写明：绑定的输入类别、当前快照身份、哪些变化会使它失效、允许复用的
最低证明和复用后必须重跑的下游项。至少区分：

- 产品构建输入；
- 产品二进制与 runtime closure；
- 验证实现、夹具和选择清单；
- 活动文档与机械门禁；
- 外部环境或人工输入前提。

本项目连续十二次刷新 source-freeze，最终用“503 项产品构建输入不变、产品字节不变”证明可以复用 clean rebuild
和 36/36 CTest，同时重跑受影响的 directed／matrix。这类复用是证据链的一部分，不是为了省时的临时技巧。通用
Skill 应描述证明语义，不应硬编码 F2 的哈希、目录或编排器。

### C-04：在授权前暴露动态预算和产品所有权

影响：高。

Skill 自身仍应保持静态只读，但当候选包含全量动态验证时，方案应从已冻结 manifest 和直接入口估算并向用户说明：

- suite／profile 数量和预计受管产品启动次数；
- 单次自然退出或自动退出上限，以及保守总时长；
- GUI、网络、Docker、浏览器或系统桌面等环境前提；
- 哪个公共 owner 负责启动、readiness、退出、返回码、配置零写回和残留检查；
- 强杀是否允许，失败清理是否会掩盖首要断言；
- 可恢复停点和可复用阶段。

本项目仅 DFP 就有 60 次产品启动，另一个 readiness 矩阵有 111 次启动；部分进程按 30 秒自然退出。方案只写
“执行全部项”不足以让用户理解时间和前台占用成本。估算可以标注区间和证据不足，不要求检查阶段真的运行测试。

### C-05：增加合成夹具合法性预检

影响：中高。

当精确测试入口使用完全合成的 Cookie、账号、配置、路径或协议载荷时，测试设计审计应沿一跳直接依赖读取当前最低
验证器，并回答：

1. 夹具是否满足现行语法和必填字段；
2. 是否仍保持离线、虚构和不读取真实用户数据；
3. 失败注入发生在目标阶段，还是会被更早的预检截断；
4. 正例和一个非法负例是否覆盖这条边界。

本项目的任意 Cookie 字符串使目标故障注入从未到达，后续屏障只能等到自动退出。修复为合法的虚构
`name=value` 后，相关重试、取消和目录终态场景全部通过。通用规则应要求“合法的合成输入”，不能硬编码 Cookie
格式或鼓励使用真实凭据。

### C-06：把手写源码提取器列为脆弱测试信号

影响：中高。

测试若通过正则或字符串切片证明 C/C++、JavaScript 等源码结构，方案应记录提取器边界，并优先要求它至少处理：

- 前置声明与真正定义；
- 参数变化和 overload；
- 花括号闭合、缺失和未闭合；
- 多次出现时的精确选择；
- 一个会误命中的合成负例。

能使用语言解析器时优先使用解析器；项目基于依赖和成本选择手写提取器时，也必须 fail closed。此检查只针对已经
冻结的精确测试入口，不授权扫描所有静态测试寻找正则。

### C-07：细化 GUI 生命周期与外部输入阻断

影响：高。

涉及 GUI 产品或真实桌面输入的验证，方案应分别记录启动子系统、readiness、正常退出机制、失败清理和环境干扰证据。
建议至少区分 `natural`、产品内优雅退出、可用的控制信号和仅限失败的强制清理；不能因宿主进程有 console 就推断
GUI 子系统产品能接收 Ctrl-Break。

真实输入未被消费时，先检查前台句柄、命中窗口、DPI／坐标和系统安全桌面。若命中系统对话框或安全桌面，结果应为
可恢复的外部阻断：不点击外部安全提示、不改成伪输入、不把坐标正确冒充产品通过；环境恢复后使用原合同重跑。

### C-08：在完成条件中写明技术终态与认证终态

影响：中高。

综合方案不应只写“全量测试通过”。建议同时写明：

- 预期技术终态，例如当前快照的 `evidence-ready` 或项目等价状态；
- 正式认证、签名、Registry、部署或外部写入是否在授权范围；
- 未运行阶段在最终状态中如何被证明为空或 `not_run`；
- 对用户报告时禁止使用的更强结论。

本项目的正确结论是“当前技术证据完整”，不是“正式 Release 已认证”。最终状态中 Registry、post-evidence 和
evidence index 为空，是边界证据，不是遗漏。最终指纹保持单例不可变；第 12 次 source refresh 另有精确复用证明，
用于恢复编排终态而不是伪造第二份最终指纹。

### C-09：支持有界的施工后 Skill 经验报告交接

影响：中。

用户明确要求“先治理项目，再从项目反哺 Skill”时，检查阶段可以在方案中登记一个施工后交付物，但应保持以下分离：

- 实施方案只描述生成时点、目标 Skill 和边界；
- 普通任务只有在项目修改和验证完成后才写经验报告；
- 报告进入项目已有历史材料位置，不成为当前项目真源；
- 报告与方案使用不同文件，且本任务不修改用户级 Skill；
- 后续 Skill 工作区重新审查、取舍、实施和验证，不直接把报告当补丁应用。

本次分离避免了“方案里提前宣称已经吸取经验”，也符合用户希望在 Skill 工作区单独优化的安排。

## 4. 建议的 Skill 工作流

1. 冻结活动所有者、模式、精确声明和一跳直接消费者；需要测试证据时选择唯一测试设计审计模式。
2. 用稳定发现集合完成双遍审计和候选评审；保存方案后立即停止，不运行动态验证。
3. 若用户选择全量验证，在方案内增加输入分类、失效／复用、动态预算、进程所有权和外部环境前提。
4. 普通任务实施确定切片；后来失败按“消费者漂移／新范围问题／外部环境阻断”分流。
5. 每次验证资产改变后刷新相应静态证据；只有取得输入和产品指纹证明时才复用昂贵阶段。
6. 以当前快照完成前置门禁、定向项、核心矩阵、最小 GUI 和最终指纹，并明确技术终态与未授权阶段。
7. 更新当前真源、移除已完成待办并归档方案。
8. 只有用户预先要求时，才由普通任务生成独立 Skill 经验报告；Skill 本体留给后续工作区任务。

## 5. 建议增加的 Skill 验收样例

1. 产品权威明确零写入，但仍有活动写入 CTest：判为失效消费者，不询问是否恢复写入。
2. 实际声明 37 项、expected 34 项，差异中一项退役、两项现行：按所有权形成 36 项同序身份和静态门禁。
3. 只修改验证夹具，产品输入和产品字节均有证据不变：允许复用 rebuild／CTest，重跑失效验证项。
4. 合成 Cookie 不符合当前解析器：在目标故障注入前报告夹具非法，不等待屏障超时。
5. C++ 文件同时有前置声明、多个 overload 和定义：源码提取器必须选择正确函数体，缺失时失败关闭。
6. Windows GUI 子系统没有可用 console：方案选择产品内自然退出缝，不声称 Ctrl-Break 可用。
7. 点击命中系统安全桌面：报告外部阻断和恢复条件，不判产品回归、不绕过系统提示。
8. 所有技术门禁通过但没有认证回写：报告技术证据完整，明确正式认证未运行。
9. 实施期出现无法由原权威裁决的新问题：保持方案活动并请求新的决定，不并入旧发现假装已评审。
10. 用户要求项目治理后反哺 Skill：实施方案和施工后经验报告分文件，用户级 Skill 保持不变。

## 6. 不应硬编码进通用 Skill 的 F2 特例

- F2 的 CTest 名称、17 个 directed 身份、11 个核心矩阵 suite、60／111 次启动数量和 30 秒自动退出时长；
- `protocol_revision=13`、503 项产品输入、36 项 CTest 以及本报告中的哈希和 run-id；
- F2 的四份 manifest、Release bundle 状态字段和 `archive/docs/` 路径；
- 所有项目都必须按有序集合比较测试身份；顺序只有在项目声明其有意义时才是合同；
- 所有 GUI 测试都必须使用自然退出；退出机制取决于产品子系统与当前 owner；
- Windows 安全桌面这一具体实现。可迁移的是“区分外部输入拦截与产品失败，并禁止绕过安全边界”；
- 验证资产变化永远可以复用构建。只有输入分类、产品字节和项目协议共同允许时才可复用。

## 7. 后续 Skill 工作区交接边界

后续独立任务可以使用 `skill-creator` 检查并修改 `project-doc-consistency`，建议顺序为：

1. 先增加实施期验证漂移分流，以及全量验证的输入失效／复用模型；
2. 再补动态预算、合成夹具、源码提取器和 GUI 生命周期检查项；
3. 把详细样例放入 references，保持 `SKILL.md` 只承载决策流程；
4. 复核 Skill 的触发描述是否仍明确“只读检查、保存方案后停止”，不要让新增内容暗示 Skill 可以施工；
5. 为上述验收样例增加 Skill 级评估，并在实际修改后运行 Skill 基础校验。

后续任务应重新判断每条建议是否适合通用项目，不得把 F2 路径、manifest、状态字段、启动数量或 Windows 特例直接
复制为默认规则。本次项目任务到报告交付为止，不修改
`C:\Users\73839\.codex\skills\project-doc-consistency`。
