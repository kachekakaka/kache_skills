# DOC-AUDIT-COVERAGE-20260807：文档审计覆盖、单方案实施、范围隔离与独立复核改进方案

- 状态：已完成
- 完成日期：2026-08-07
- 方案类型：现有项目文档 Skill 的审计覆盖、范围隔离与单方案闭环修正
- 历史授权说明：本文件和同 ID 待办的保存不构成 Skill 实施、验证、安装、Git 交付或生命周期关闭授权。

## 1. 目标与初始证据

本方案修复一个真实使用失败：局部方案中的已知事项全部完成，并不能证明审计发现集合已经完整。目标按优先级为：

1. 让 `project-doc-consistency` 对每份纳入范围的活动文档强制完成事实／契约核对和职责／去膨胀核对两遍审计。
2. 在用户明确要求审计测试体系、Registry、测试项职责或冗余时，提供有边界的 Registry 全局审计子模式。
3. 让两个 Skill 的检查结果和保存方案都使用覆盖与残余矩阵，明确区分已覆盖、无法验证、未覆盖和未运行验证。
4. 让内容方案关闭前从最终活动真源重新建立范围并执行发现集外复核，不能只逐项复查原始发现项。
5. 让 consistency 保存的一份闭环主责方案承接为同一审计目标所必需、证据和语义已经收敛的文档、结构、产品、
   构建、测试、CI 与安全实施切片；后续普通任务统一实施，不再为这些已发现事项另起方案或二次调用审计。
6. 让每个跨职责切片在进入确定实施前完成有边界的就绪补证，并把任务特定范围、所有者、矩阵和最终复核方法
   物化进方案，使没有参加审计对话的普通任务也能独立接手。
7. 把项目内用于 Codex 发现的 `.agents/skills/**` 明确分类为工具资产而不是活动项目文档，默认排除于两个 Skill
   的文档范围和 T-DOC 通用 Markdown 检查，只在精确声明需要实现证据或用户明确审计 Skill 时读取。

当前证据：

- `project-doc-consistency/SKILL.md` 已要求识别内容膨胀，但现行 `full` 流程没有强制逐文档证明该维度已经完成。
- 现行测试设计参考只允许比较已经精确命名的候选对，无法响应用户对 Registry 全表职责和测试项经济性的明确请求。
- 现行前向夹具包含小型膨胀样本，却没有覆盖“高影响事实冲突吸走注意力后，低显著度膨胀分散在多份文档”的失败形态。
- 现行方案字段能记录已知发现和分层验证，但没有要求最终复核从活动真源重新取种，因而可能只证明已知事项关闭。
- 现行 ADR 和 Skill 规则要求结构、产品与测试实现只形成交接、不进入内容方案确定范围；真实试用因此把同一根因
  拆成多次裁决和后续任务，无法满足“一次审计、一份方案、一次普通任务闭环”的目标。
- 现行跨职责切片字段没有要求在确定实施前核清活动所有者、直接消费者、修改链路、测试义务和副作用；现行方案
  也没有要求把任务特定活动清单、所有者、已填充矩阵和最终复核种子完整物化，普通任务仍可能依赖原审计对话。
- 现行前向契约只观察 Skill 能否保存方案，没有证明一个只获得目标项目、方案和实施授权的全新普通任务能完成
  跨职责实施、验证、发现集外复核与生命周期关闭。
- `SoftwareTesting/doc_consistency/test_doc_consistency.py` 当前遍历工作区全部 Markdown，而忽略目录没有精确排除
  `.agents/skills/**`；skeleton 的“列举活动 Markdown”也没有定义该边界。因此项目级 Skill 会被误当作活动文档
  或通用文档门禁输入。consistency 虽从活动入口建立集合，也缺少相同的显式排除和精确证据例外。
- 现行方案把 `docs/软件测试.md`、`SoftwareTesting/README.md`、`project-doc-skeleton/references/skeleton-rules.md`
  和通用 T-DOC 列为不修改，但新增独立接手验收与项目级 Skill 隔离会直接改变这些真源或实现，原排除已经过窄。
- 当前工作树中的两个 Skill、相关参考、`CONTEXT.md` 和前向协议已有上一任务的未提交修改；这些内容属于受保护
  基线。本方案实施不得回退、覆盖或把它们冒充为本方案新增结果。

## 2. 已确认方向与非目标

用户已接受本方案第 1 节的优先级。实施时按以下方向收敛，不重新讨论是否需要这些能力：

| 编号 | 方向 | 固定边界 |
| --- | --- | --- |
| D-01 | Consistency 双遍审计 | 增加覆盖深度，不把 `full` 扩成全源码、全历史或全安全审计 |
| D-02 | Registry 全局审计子模式 | 仅由明确的测试体系／Registry 请求触发，不随普通文档 `full` 自动运行 |
| D-03 | 覆盖与残余矩阵 | 只暴露本轮证据边界，不建立持久 profile、manifest 或隐藏账本 |
| D-04 | 发现集外复核 | 由后续普通实施任务在最终候选上只读执行，不恢复 Skill 的施工、验证或关闭阶段 |
| D-05 | 单方案闭环实施 | 确定切片先完成就绪补证，方案物化完整交接；Skill 只保存，全新普通任务也能统一实施 |
| D-06 | 项目级 Skill 资产隔离 | `.agents/skills/**` 默认不是活动项目文档；精确证据读取和显式 Skill 审计除外 |

非目标：

- 不改变 skeleton 对结构治理的独占职责，不让它审计内容事实或测试经济性。
- 不让 consistency 自己创建、删除、合并、拆分或重构文档结构、产品、测试、CI 和安全实现；这些动作可以作为
  同一闭环方案的精确实施切片，由后续普通任务按目标项目规则和授权执行。
- 不取消 `full`／`incremental` 内容模式，不递归遍历全部源码、历史、工作流或安全实现。
- 不改变 T-DOC 的 Registry ID／类别、现有 ADR 和授权模型；T-DOC 只增加 `.agents/skills/**` 的精确范围排除，
  不借机重构其他机械规则，也不使用宽泛的 `.agents` 整目录忽略隐藏无关内容。
- 不使用项目文档审计替代 Skill 专项审查或 `skill-creator` 校验，也不因文件名为 `SKILL.md` 就排除
  `.agents/skills/**` 之外的仓库产品源码或精确实现证据。
- 不安装仓库候选 Skill，不修改本机已安装 Skill 目录，不操作外部真实项目。

## 3. 目标行为

### 3.1 内容双遍审计

Consistency 在冻结活动文档集合后分别完成：

1. **事实／契约遍**：分类当前事实、规则与决定、历史结果、待办状态和非穷举摘要；按声明选择一轮直接证据。
2. **职责／删除优先遍**：逐份活动文档按其唯一职责检查章节或连贯内容块，识别实现镜像、下层命令复制、重复真源、
   过程／历史混入和不影响使用者判断的局部细节；不能因同一文档已有事实问题就跳过该遍。

`full` 必须在临时覆盖表中逐份登记两遍结论；`incremental` 只登记精确种子及直接受影响内容。输出保持摘要化，
不要求把每个合规段落写进对话，但没有覆盖记录时不得宣称对应范围内容一致。

### 3.2 Registry 全局审计子模式

测试设计参考新增两种互斥范围：

- **声明绑定**：保留现行精确声明和候选对规则。
- **Registry 全局**：仅在用户明确要求审计测试体系、Registry、全部活动测试项、职责划分、重复或成本时启用。

Registry 全局模式先从权威 Registry 或等价选择入口枚举每个活动 ID，再按测试义务、层级、环境、入口、核心断言、
失败信号、触发和副作用形成职责分组；只对有重叠证据的分组读取 suite 与一轮直接实现锚点。每个活动 ID 都必须
在覆盖表中有结论，但证据不足时只能标记无法验证，不能为证明“没有其他重复”遍历全部测试实现。

### 3.3 覆盖与残余矩阵

两个 Skill 的检查结论和保存方案至少列明：

| 字段 | 含义 |
| --- | --- |
| 维度 | 结构、事实／契约、职责／膨胀、测试设计、动态验证等适用维度 |
| 本轮范围 | 实际文件、声明或 Registry 范围 |
| 结论状态 | 已覆盖、无法验证、需要决策、未覆盖或不适用 |
| 证据／残余 | 当前依据、最小补证、交接主责或未运行验证 |

Skeleton 只据实把内容和测试经济性列为未覆盖或不适用，不因此调用 consistency。Consistency 不能用“已完整读取”
替代两遍审计，也不能用 T-DOC 或受影响测试结果替代内容覆盖结论。最终措辞必须称为本次范围完成；只有矩阵中计划
适用维度均取得可解释结论时，才能使用项目级闭环表述。

保存方案时必须写入本次任务已经填充的矩阵实例，不能只引用 Skill 中的通用字段或要求实施者重新推导。矩阵至少
物化活动文档清单及所有者、每份文档的两遍结论、触发后的 Registry 活动 ID 清单与职责分组、无法验证／未覆盖项
和未运行验证；不适用项也要写明当前依据。

### 3.4 发现集外复核

Consistency 保存的方案必须先把审计交接物化为自包含内容：任务特定活动真源及所有者、冻结范围与排除项、已填充
覆盖矩阵、发现和决定、确定／可能路径、切片就绪证据、验证与授权边界，以及下列最终复核方法和取种入口。一个
没有参加审计对话的普通任务只获得目标项目、该方案和实施授权时，也必须能够判断施工、停点、验证和关闭条件。

后续普通实施任务在最终候选上：

1. 从当前活动入口和职责所有者重新建立范围，而不是把原发现清单当作完整种子；
2. 重新执行适用的事实／契约遍、职责／删除优先遍，以及已明确触发的测试设计子模式；
3. 对照覆盖与残余矩阵记录新发现、证据不足和未覆盖面；
4. 新发现仍属于本方案目标但超出确定路径、需要语义决定或改变验证边界时停止，不得先关闭再另报问题。

该复核只是一项方案验收要求，不由 consistency 自己执行，也不要求自动调用 skeleton、子代理、新任务或本 Skill。
实施者不得依赖原审计对话补齐活动清单、矩阵或复核种子；方案缺少这些内容时不能进入实施。

### 3.5 单方案闭环实施

Consistency 保存的方案不再把跨职责发现只写成需要另起方案的交接。只要第 3.6 节就绪闭包通过，且必要语义已经
由当前真源或用户决定，方案就为同一审计目标建立一组实施切片：

| 切片字段 | 最低要求 |
| --- | --- |
| 职责域 | 文档、结构、产品、构建／配置、测试、CI 或安全 |
| 问题与目标 | 权威契约、当前证据、影响和预期唯一真源 |
| 路径边界 | 确定路径、可能路径、直接消费者及明确不修改范围 |
| 动作边界 | 普通任务可以执行的修改、禁止动作和重新冻结触发 |
| 验证与授权 | 对应普通验证、`explicit`／高风险差额和未运行状态 |

同一方案可以包含多个切片，但只有已经收敛的切片才能列入确定实施。所有权不清、证据不足、语义取舍未决或无法
可靠分离结构与产品断言时，保持待决并在方案确认前请求最小决定；不能用“放进一个方案”掩盖未知边界。

用户确认该方案后，普通实施任务按目标项目授权语义统一完成全部确定切片、列明验证、发现集外复核和生命周期关闭。
Consistency 不恢复施工阶段，不自动调用 skeleton，也不要求各切片再生成子方案。最终复核发现的新问题若仍属于
原审计目标，保持本方案活动并申请必要差额或修订同一方案；只有用户确认属于独立目标时才建立新待办和新方案。

### 3.6 跨职责切片就绪补证闭包

每个跨职责候选在列为确定实施前，以该发现的精确声明、路径或标识符为种子完成一次有边界的直接补证：

1. 确认活动所有者、权威契约、预期唯一真源及必要语义已经收敛；
2. 确认确定路径、可能路径、直接消费者、实际修改／调用链路和明确不修改范围；
3. 确认该变更产生的测试义务、现有精确入口、需要新增或调整的断言和未运行验证；
4. 确认文件写入、进程、联网、真实数据、删除、安装、Git 或外部状态等副作用及授权差额；
5. 写明完成条件、重新冻结触发和仍无法验证的残余。

闭包只展开会改变切片是否可实施的一层直接依赖，不借机审计整个产品、测试或 workflow。五项均有足够证据且没有
未决语义时才能进入确定路径；否则仍保留在同一方案的待决部分，在方案确认前请求最小决定或补证，不能另起子方案
绕过未知边界。

### 3.7 项目级 Skill 资产隔离

两个 Skill 和通用 T-DOC 都把仓库内任意 `.agents/skills/**` 识别为 Codex 项目级 Skill 工具资产，默认不纳入：

- 活动项目文档集合、结构／历史分类和两跳可达性；
- consistency 的事实／契约遍、职责／删除优先遍和覆盖矩阵；
- T-DOC 的通用 Markdown 编码、换行、链接、锚点、绝对路径、导航和生命周期检查。

若活动项目文档精确声明某个 Skill 的存在、入口或职责，可以只读取对应 `SKILL.md` 或必要资源作为该声明的一轮
实现证据；该读取不把 Skill 资产升级为活动文档，也不顺带审计其正文。用户明确要求审查或更新 Skill 时，转入
Skill 专项任务及其校验，不由项目文档审计或 T-DOC 替代。

实现必须按 `.agents/skills` 路径语义精确排除，不能简单忽略整个 `.agents`，也不能按文件名全局排除 `SKILL.md`；
本仓库在其他路径维护的 Skill 源码仍可作为产品实现证据和本方案目标。
