# 测试设计一致性参考

本文只扩展 `project-doc-consistency` 已冻结的内容范围，不建立独立测试治理范围，也不认证全项目测试或安全。

## 触发条件

只有以下情况才使用本文：

- 用户明确要求审计测试设计、测试覆盖、Registry、suite、CI 或测试安全；
- 某项已冻结文档声明必须以具体测试、CI 或安全实现作为直接证据。

`full` 不自动触发本文。仓库中存在测试目录、Registry、workflow 或 SAFETY 文件也不是触发条件。

## 选择互斥审计模式

触发后必须先选择且只选择一种模式，并把模式、入口、范围与排除项写入主 Skill 的覆盖／残余矩阵。

### 声明绑定模式

用户只点名具体声明、测试、suite、CI 或安全证据时使用。先写明触发本文的文档声明和要回答的问题，只为这些声明
建立证据链，不把 Registry 全表、suite 目录、workflow 目录或安全脚本扩张为新审计主题。

可用链路为：

```text
权威需求或设计契约
→ 当前实现或配置
→ 测试义务
→ Registry/suite/选择器
→ 精确测试入口与核心断言
→ 与该声明直接相关的 CI 或安全实现
```

不是每个问题都需要完整链路。只读取能直接回答当前声明的节点；每个节点只沿精确路径、标识符或当前差异展开
一轮直接依赖。缺少锚点时使用“无法验证”，不得递归扫描同类测试或全部 workflow 寻找替代证据。

### Registry 全局模式

只有用户明确要求审计测试体系、全部 Registry、suite 组织或全局测试覆盖时使用。先从当前测试入口和职责声明冻结
所有活动 Registry 的精确清单、分组依据与排除项；入口不能形成完整清单时停止并报告结构所有权不清，不猜测
Registry，也不把测试目录遍历结果当成 Registry。

对清单中每个条目记录标识符、声称的义务与层级、入口或选择器、直接实现、核心断言、触发与成本证据。只沿条目
明确指向的入口和一轮直接依赖读取，不借全局模式遍历无登记测试、全部源码、workflow 或安全脚本。按相同契约、
层级、环境、触发和断言形态形成候选组，在组内比较覆盖、重叠与成本；另对声称覆盖同一义务的跨层条目检查是否
具有不同边界或失败信号。每个条目和候选组都必须在矩阵中留下 `已覆盖`、`无法验证`、`需要决策`、`未覆盖` 或
`不适用`，以及相应证据或残余。

## 确认测试义务

只有以下来源形成测试义务：

- 当前权威契约明确要求的行为、不变量或失败边界；
- 实现中会改变可观察结果且被当前文档承接的风险；
- Registry、suite 或 CI 已明确声称的覆盖；
- 用户显式指定的测试设计问题。

不要求每个实现分支都有文档或独立测试。测试通过不能反向证明实现符合权威契约；实现与测试共同接受契约禁止
的行为时，报告“实现与测试共同偏离契约”。

多个同等级权威来源冲突或优先级不明时使用“需要决策”，不能简单把需求或设计文档判为过时。

## 检查选择与断言

对精确测试项记录：

- 测试义务和权威契约；
- 层级与运行边界；
- Registry、suite 或选择器的覆盖声明；
- 实际入口、输入和一处核心断言；
- 失败时提供的独有信号；
- 成本、触发和已知副作用。

suite 没有给出可定位入口，或声明与实际命令、输入、断言不符时，报告“声明错位”或“无法验证”，不要遍历
测试目录猜测实现。

## 判断覆盖、重叠与成本

使用以下子类型，它们附着在主 Skill 的内容结论下：

- `覆盖缺口`：存在明确测试义务，但没有可信测试或核心断言；
- `声明错位`：文档、Registry、suite 或 CI 声称的覆盖与实际入口、实现或断言不符；
- `有意重叠`：覆盖同一能力，但层级、边界、失败信号或独有证据不同；
- `冗余候选`：义务、环境、边界、断言和触发基本相同，没有新增独有证据；
- `过度候选`：矩阵、环境或触发成本超出支持契约，且没有直接风险依据；
- `失效测试`：只验证已由权威来源明确移除、替代或不再支持的行为。

声明绑定模式只有当前范围已经精确命名候选对，才能比较重复和过度。Registry 全局模式只比较由已冻结清单按本页
规则形成的候选组，不读取未登记测试来证明“没有其他重复”。缺少成本、风险或独有证据时使用“无法验证”，不能
暗示已经证明应删除测试。

### 区分结构机械断言漂移

只有精确种子或已经冻结的直接证据包含可执行断言，且当前权威结构决定已经明确删除、替代或收窄该断言所约束的
路径、入口、生命周期或文档职责时，才将其记录为 `结构机械断言漂移`。这不是普通内容事实不一致，也不同于验证
已移除产品行为的 `失效测试`。

记录当前结构决定与位置、精确断言与位置、直接影响和结构实施交接。不得为寻找同类项搜索其他测试、脚本或 CI；
不得把 API、数据或业务行为断言归入结构类别。同一测试中两类断言可以可靠分离时只交接结构部分；不能可靠分离
时记录冲突并交给结构与测试实现方共同判定，不修改任何断言。

## 按声明检查 CI 与安全

只有文档声明直接涉及选择、触发或安全行为时，才检查相应调用方：

- 实际触发器和默认输入是否符合声明的执行类别；
- 路径过滤是否覆盖已证明会改变该测试输入或交付结果的文件；
- 需要认证或私有资源、上传本地或非公开内容、外部写入、费用、明显大规模下载、破坏性或真实数据的测试是否被
  默认触发；不要仅因测试读取公开网络就把它归为受限测试；
- 声明涉及输出或清理时，实际根目录、所有权证明、containment、保留和删除行为是否相符；
- 声明涉及进程时，实际所有权和停止边界是否相符。

只读当前声明精确命名的 CI 调用方或一份直接 helper。不能据此宣称全项目 CI 完整或安全等价，也不能为补证
遍历所有 workflow、脚本或发布入口。

## 静态结论与方案交接

静态读取可以证明入口、映射、断言形态和声明冲突；故障捕获能力、flaky、性能成本、恢复效果通常需要运行、
故障注入、mutation testing 或历史数据。未获授权时保持“无法验证”，对应规范验证记为 `not_run`。

已经明确契约、精确范围、直接消费者、验证义务、副作用、授权和完成条件的测试、CI 或安全改动，可以通过主 Skill
的切片就绪检查后进入同一综合方案的确定实施范围。证据不足、候选边界漂移或需要语义取舍的项留作同一方案中的
待决项，并写明最小补证与再冻结条件。本 Skill 保存方案后仍然停止，不执行任何修改或验证，也不要求实施任务
重新调用本 Skill 或另写测试方案。
