# 一致性反证与跨载体扫描参考

本文只扩展 `project-doc-consistency` 的 `full` 审计方法，用来主动寻找“初审看起来一致”背后的跨载体矛盾。
它不建立新的业务权威，不做内容收缩，也不要求全仓两两比较。

## 使用条件

- `full` 审计必须完整读取本文，并在普通自然契约单元审计后完成四类扫描。
- `incremental` 只有在内容种子涉及时间状态、允许／禁止合同、聚合入口或操作粒度时读取相应小节。
- 扫描只沿已冻结文档和一轮直接证据工作；发现新的活动文档范围问题时按主 Skill 记录 `未覆盖`，不得静默扩张。

## 四类跨载体扫描

每类扫描都先形成两个有限、可见的双向清单，再比较差额；不得只从文档出发找若干正例后宣布闭合。

### 1. 初始状态与运行时转换

- 文档侧清单：初始态、当前态、允许转换、失败态、终态和持久化边界；
- 实现／消费者侧清单：切换 API、状态机、代际、租约、恢复路径及直接消费者实际允许的转换。

检查“启动时、初始、当前、阶段性、永久、仅在某阶段”等限定是否与第二份清单冲突。

### 2. 允许、禁止、退役合同与夹具

- 权威侧清单：当前明确允许、禁止、退役或收窄的依赖、字段、路径、身份和状态；
- 执行侧清单：正向 fixture、allowlist、构建依赖和负向 fixture 实际接受或拒绝的成员。

正向夹具仍接受已退役项，或负向夹具仍拒绝当前允许项，都形成差额；测试和实现共同接受旧行为时，不能以“测试通过”
证明一致。

### 3. 聚合入口与成员闭包

- 声明侧清单：`all`、`run-all`、suite、manifest、expected、Registry 汇总或“顺序跑以上”点名的精确成员；
- 调度侧清单：dispatcher、函数调用、选择清单或注册表实际调度的精确成员。

按名称比较遗漏、多余、顺序和条件差异；数量相同不能代替成员闭包。

### 4. 身份与操作粒度

- 声明侧清单：被写成同一 source、lease、snapshot、请求、响应、调用或生命周期的对象；
- API／消费者侧清单：公开操作、返回字段、lease 取得边界、独立精确操作和直接消费者实际使用的粒度。

“同一 source／lease／snapshot”不自动等于“同一请求／响应／调用”。必须点名普通操作与独立精确操作、可选字段与显式
查询、共享身份与独立生命周期的边界。

## 候选编号与闭环

每个双向清单差额生成稳定候选编号，例如 `CE1-01`、`CE2-01`。每个候选必须归入一致性发现、有证据的不适用、
`无法核验`、`需要决策` 或 `未覆盖`；不得用“扫描完成、无新发现”跳过候选归宿。没有差额时也要展示两份清单的实际
边界和比较结果。

## 正式证据

每类扫描都在一个或多个正式 `Axxx` 中记录：

1. 被挑战的具体声明和路径锚点；
2. 双向清单及其直接锚点；
3. 当前权威与初审正向证据；
4. 不同角色的相反证据或邻接消费者；
5. 每个 `CExx` 候选的结论、发现或明确残余。

没有适用候选时，也要写明检查过的限定词／聚合入口／夹具／操作边界和“不适用”的具体理由；“已搜索、未发现问题”
或文件数量对账不能算完成。

## 第一轮反证式查漏

进入第一轮时，对每份文档级 `一致` 结论独立记录：

- 可证伪主张；
- 初审正向证据；
- 与正向证据不同角色的相反证据或邻接消费者；
- `改变`／`未改变`；
- 反证为何推翻或未推翻原结论。

只有主张、证据角色和结论完全相同，才可显式分组；即使分组，每条路径仍要独立命名并给出锚点。
`N/N 不变`、`同前`、`原证据仍成立` 或按职责类别列名单都不能替代上述记录。

## 第二轮防语义误改

每项拟议修正必须分别回答：产品语义、权限／安全边界、测试选择／分类／覆盖义务、运行行为、历史决定和一层直接消费者
是否改变，并给出 `通过`、`修改` 或 `撤销`。一段综合说明不能代替逐轴结论。

## 失败关闭

任一四类扫描缺少双向清单、候选存在未归宿、第一轮缺少不同角色反证、第二轮缺少逐轴结论，或正式记录在保存前已无法
从当前线程或经用户授权的仓库外轨迹中取得时，完整性门失败；只能报告 `未覆盖`，不得询问保存完整方案。
