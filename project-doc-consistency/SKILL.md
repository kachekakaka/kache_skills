# 项目文档一致性检查与方案

## 职责与退出边界

本 Skill 只负责：

- 确认活动文档的当前所有者和有限审计范围；
- 核对文档事实、规则、契约、决定、前提、例外、状态与当前实现或可观察行为；
- 检查需求、设计、字段契约、ADR、运维、待办和测试登记之间的契约或状态漂移；
- 检查当前所有者是否明确，直接消费者是否仍履行当前合同；
- 核对 Registry、manifest、测试入口、实际注册和核心声明是否一致；
- 在条件成立时核对直接相关的测试契约、身份、入口和核心断言，并为后续普通任务规划验证；
- 按用户明确要求交付只读报告，或保存一份纯一致性实施方案。

本 Skill **不负责内容收缩**。它不判断文档是否太长，不评价默认加载量，不决定哪些内容应删除、迁移、摘要加链接、
合并或简化，也不输出 `无需收缩`。发现完全重复、实现镜像、过程快照或内容错位但没有改变当前含义时，只登记
`后续收缩候选`，写明路径、疑似所有者和交接理由；不得把该候选放入一致性实施方案。

本 Skill 不调用或依赖 `project-doc-contraction`、`project-doc-skeleton`，也不认证项目骨架、不安装门禁、不施工、
不运行验证、不归档、不关闭目标项目生命周期。已有活动方案的施工、验证或关闭请求只报告普通任务接手位置。

归档和历史材料默认只提供历史语境；只有活动入口明确继续把它定义为当前契约时，才作为当前权威。

以下标准项目级 Agent Skill 根是工具资产，不是活动项目文档：

- `.agents/skills/**`
- `.cursor/skills/**`
- `.claude/skills/**`
- `.codex/skills/**`
- `.opencode/skills/**`
- `.opencode/skill/**`
- `.github/skills/**`

其他 Skill 根只有在用户、适用项目规则或已冻结的精确配置明确声明时才排除。活动文档点名某个 Skill 的存在、
入口或职责时，只把对应 `SKILL.md` 或必要资源作为该声明的实现证据，不因此审计整个工具目录。

## 请求分流与只读边界

1. 明确只要检查、审计、review 或报告时，直接走只报告路线；报告后停止。
2. 明确要求形成、保存或修订方案时，直接走方案路线。
3. 请求只有 `$project-doc-consistency` 或意图不足以可靠分流时，在实质调查前询问“只要一致性报告，还是检查后形成
   一致性方案”，推荐先只要报告。取得回答前只读取本 Skill、共享参考和遵守安全边界所必需的适用 `AGENTS.md`。
4. 方案路线在实质调查前取得尚未明确的交付前自查轮数和实施后反哺报告选择，推荐“两轮、不生成”。反哺报告由后续
   普通任务在实施和验证完成后独立生成，本 Skill 不生成。
5. 新问题始终只读。即使请求含“修复”“同步”或 `sync`，也不写项目文件、不运行测试、构建、产品、门禁或其他
   动态验证；方案中列明的动态验证保持 `not_run`。

用户对语义结果的确认不自动授权保存方案、登记待办、转换状态或实施。方案保存必须在最终问题中单独确认，保存后
立即停止。

## 活动真源与证据

先读取目标路径适用的全部 `AGENTS.md`，再从当前文档入口和职责声明识别活动所有者。若无法明确回答“本次声明由哪份
活动文档拥有”，停止内容审计并报告已读取入口、冲突或缺失、受影响范围和结构治理交接；不得根据当前代码更像哪一份
文档来猜测真源。

按声明类型选择证据：

- 描述性事实：对照代码、配置、schema、构建、调用关系、公开帮助或可观察行为；
- 规则、契约和决定：以明确承接它们的当前文档或已确认决定为权威，再检查实现和消费者；
- 历史记录和动态结果：按时间语境判断；当前运行状态需要实际执行证据或用户确认；
- 待办和方案状态：以活动生命周期真源和完成证据为准；
- 非穷举摘要：只有遗漏改变含义或违反文档职责时才是不一致。

测试入口、Registry、suite、断言和 CI 默认是契约消费者与验证证据，不因仍在活动登记就取得业务契约所有权。只有
活动入口明确委托测试治理拥有相应契约时，测试声明才可作为同级权威。当前权威已经唯一裁决的旧实现、旧配置或旧测试
直接列为修正项，不让用户重新决定是否继续兼容。

只有当前权威留白、多个同级当前权威冲突或存在真实价值取舍时，才形成语义决定。能够由当前证据唯一裁决的事实自行查明。

公开只读联网仅在用户指定或冻结声明确实需要公开证据时使用，不进行无边界浏览。不得把凭据、真实用户数据或原始运行
现场写入报告、方案或仓库。

## 冻结审计范围

在读取实现证据前记录模式、内容种子、直接依赖规则、排除项和精确活动文件路径。不得用“核心文档”或职责分组代替路径。

### `full`

用户未限定文件、功能或差异却要求审计项目文档时使用。由当前入口和职责声明形成活动文档集合，冻结后完整处理该集合。
`full` 不表示遍历全部源码、测试、CI、历史或归档；入口不能形成完整集合时报告未覆盖边界。

### `incremental`

用户明确指定文件、功能、声明、标识符或当前差异时使用。范围只包括精确内容种子和一轮直接依赖：直接提供该声明证据，
或直接消费该变更并改变一致性结论的文档、代码、配置、构建或可观察行为锚点。直接依赖不递归展开；边界仍不可靠时
报告证据不足并询问是否升级为 `full`，不得静默升级。

范围内活动文档必须完整读取；大型文件可稳定分块，但不得抽样。实现证据只读到足以理解声明和直接上下文。

**冻结的是文档路径和一轮依赖边界，不是问题发现集合。** 后续评审不得静默增加活动文档路径或递归扩大依赖，但必须
重新检查冻结路径中的原始正文，并可新增、删除、拆分、合并或改变一致性发现及处置。

## 单任务长审计

开始实质审计前完整读取
[`../project-doc-shared/references/long-audit-protocol.md`](../project-doc-shared/references/long-audit-protocol.md)。
按该协议交付 `S000`、`Axxx`、`Cnnn`、累计可恢复尾部和最终索引；同一任务内自动续跑，不因预计上下文或输出不足
停止，也不依赖不可见内部记忆。

本 Skill 的每个正式审计分片必须承接下节规定的自然单元三项证据、文档级一致性处置，以及新增或改变的发现、
`后续收缩候选` 和残余。

## 一致性审计单元与完成证据

长期文档按自然契约单元审计：

- 只有正文整体由同一角色、所有者和契约承接，且没有两个及以上稳定一级职责章节时，才可用一个单元覆盖全文；
- 有两个及以上稳定一级职责章节（通常是文档标题下的 `##`）时，每个一级职责章节至少一个单元，不得跨章合并；
- 表格、清单、矩阵或映射中的各行／项若分别声明不同值、所有者、状态、前提、例外或消费者，必须分别成为单元；只有这些字段与结论完全相同且逐项锚点可见时才可显式分组合并，不能用章节级结论覆盖独立行／项；
- 同一章内若角色、所有者、契约、适用前提或生命周期发生变化，继续拆分；
- 没有稳定标题时，在上述任一要素变化的位置分单元。

每个单元必须可见记录：

1. 被核对的具体声明、规则、决定或当前状态；
2. 命名的当前所有者，以及至少一个直接实现、配置、schema、构建、可观察行为、直接消费者或明确残余；
3. 一致性结论与理由：`一致`、`需要修正`、`无法核验`、`需要决策` 或 `未覆盖`。

“源码、配置和测试静态吻合”“职责清楚”“已完整读取”等概括只能作摘要，不能单独证明一个单元完成。章节范围加一句
统一结论不能证明其中各单元已经核对。

对每份活动文档形成同样五种文档级处置之一。`一致` 必须承接该文档全部自然契约单元，且任何单元都没有未解除残余。
疑似重复但语义相同的内容不改变一致性处置，只单独登记为 `后续收缩候选`。

## 必检轴

对每个自然契约单元检查：

- 值、默认值、范围、前提、例外、失败关闭、负合同和用户可观察结果；
- 当前实现、配置、schema、构建、帮助、注释或运维入口是否与权威声明一致；
- 需求、设计、字段契约、ADR、运维和待办之间是否对同一合同给出不同含义；
- ADR 的 accepted、superseded、部分替代和后继指针是否准确；
- 活动方案和待办状态是否与静态实现及已经存在的完成证据相符；
- 当前所有者是否唯一，直接消费者是否保留必要义务；
- Registry、manifest、suite、CTest／等价注册、实际入口和核心覆盖声明是否一致；
- 测试、旧实现或历史记录是否错误反向定义当前产品契约；
- 当前动态状态是否缺少实际运行证据；未运行时保持未知，不把静态存在写成通过。

若两处文字完全重复、实现细节镜像、过程快照或内容错位，但值、前提、例外和消费者义务没有冲突，只登记
`后续收缩候选`，不在本 Skill 中决定删除或简化。

## 完整性门

完整性门跨 `S000`、全部编号审计／纠正／评审分片、累计尾部和最终索引核对：

1. 精确活动路径或内容种子与审计记录一一对应；
2. 每份长期文档的自然契约单元覆盖全部实质正文；
3. 每个单元都有三项证据或明确残余；
4. 每份活动文档都有文档级一致性处置和文档特定依据；
5. 高显著度发现没有终止其余成员、其余单元或另一轮检查；
6. 分片、累计尾部和下一指针连续；
7. 每项纠正精确替代旧记录，最终索引没有两个同时有效且互相冲突的结论。

任一项缺失时先继续交付后续分片补齐；仍不能补齐则标为 `未覆盖`，只交付不完整停点报告，不得宣称完整范围完成、
形成完整方案候选、计入已完成评审轮次或询问保存。预计篇幅不是 `未覆盖` 理由。

问题标识和数量只用于防止已有发现丢失，不能证明没有漏项。

## 条件测试契约与验证交接

以下任一条件成立时完整读取
[`references/test-design-audit.md`](references/test-design-audit.md)：

- 用户明确要求核对 Registry、manifest、suite、CTest／等价注册、CI 或测试安全声明的一致性；
- 某项已冻结产品或治理契约，必须核对测试义务、选择、核心断言、CI 或安全声明才能裁决。

核对测试文档自身点名的路径、命令、入口、当前分类或一处直接实现，属于普通事实一致性取证，可以精确读取证据而不
加载完整测试设计参考。`full`、测试文档进入活动集合，以及仓库中存在测试目录、Registry、workflow 或 SAFETY 都不会
自动触发该参考。若精确直接证据暴露可执行断言仍强制已经删除、替代或收窄的路径、入口、生命周期或职责，记录
`结构机械断言漂移`，但不搜索其他测试。

方案包含动态验证、昂贵阶段、产品／GUI／外部环境、证据复用、实施期消费者漂移或认证终态时，完整读取
[`../project-doc-shared/references/validation-planning.md`](../project-doc-shared/references/validation-planning.md)。

## 交付审计报告

完整报告由 `S000`、编号审计／纠正分片和最终总索引共同承接。报告整体至少包含：

1. 活动真源所有者及证据，或所有权不清停点；
2. 模式、精确路径或内容种子、直接依赖和排除项；
3. 每份活动文档独立命名的自然契约单元、三项证据和文档级处置；
4. 事实、契约、状态、所有权、直接消费者、Registry／manifest／入口等一致性发现；
5. `后续收缩候选`，仅作为另一项显式任务的交接，不带收缩动作；
6. 无法核验、需要决策、未覆盖和未获授权操作；
7. 适用时的测试契约发现、结构机械断言漂移和验证交接建议。

每个一致性发现写明声明与位置、权威证据与位置、当前结论、影响、推荐承接和最小修正。只报告路线在完整报告和最终
索引交付后停止。

## 形成与评审方案候选

方案路线只为一致性发现和待决事项形成未保存候选。方案应自包含：

- 活动所有者、模式、完整性门结果和未覆盖边界；
- 每项一致性发现的证据、影响、用户决定和最小补证条件；
- 确定修改路径、可能修改路径和明确不修改范围；
- 每个确定切片的一致性目标、最小修正、一层直接消费者、验证义务、副作用、授权、完成条件和残余；
- 实施后的最终活动入口、确定切片和新产生一跳关系复核；
- 目标项目的生命周期承接位置和差额停止条件。

### 方案隔离

**一致性方案只能包含事实、契约、状态、所有权、Registry／入口或直接消费者的修正、校准和澄清，以及相应验证与
生命周期动作。** 不得形成删除重复正文、迁移内容、摘要加链接、合并、简化或降低默认加载量的实施动作；这些内容只
能保留为 `后续收缩候选`。

动作按实际效果分类，不按“职责收口”“真源恢复”“README 分层”或“清场”等名称分类。若各处的值、前提、例外、状态、所有者身份和消费者义务已经一致，动作只是删除、移动、缩短语义等价正文或只保留链接，则它属于内容收缩；一致性方案不能仅为减少副本或恢复文档层级执行该动作。

若某条错误表述必须退出，方案使用能恢复当前合同的精确替换、状态校准或所有者指针，而不是把“删除内容”作为独立
一致性目标。没有一致性问题时不创建空方案，也不把纯收缩候选混入方案。

## 一致性方案评审

用户只选择一轮时，同一轮同时完成下述两类记录；选择两轮及以上时：

1. **查漏轮**：以进入评审时所有文档级 `一致` 结论为固定集合，逐份回看原始正文和直接证据。每份记录 `改变` 或
   `未改变`；改变时列出新增或修正的自然契约单元，未改变时引用原报告单元并点名本轮复核的原始证据。重点查漏
   事实、契约、状态、所有权、Registry 和消费者漂移，不得只列新增发现。
2. **防语义误改轮**：逐项检查当前候选中的全部一致性修正，包括第一轮后的变化。每项记录原权威合同、目标修正、
   一层直接消费者，以及是否错误改变产品语义、权限、安全边界、测试选择、运行行为或历史决定；结论为 `通过`、
   `修改` 或 `撤销`。

评审轮次只有在正式 `Rxxx` 分片中实际交付上述逐份或逐项记录后才计数；最终摘要、方案正文、审阅包或事后重建表格不能补记为已完成评审。缺少正式记录时必须继续评审，不得询问保存。

两类评审都按共享长审计协议形成编号评审分片并自动续跑。评审改变旧结论或动作时，必须交付 `Cnnn` 并在最终索引
标记替代关系。发现遗漏、依据不足或误改时，先修订候选并重做受影响记录；修订前结论不计入完成轮次。路径数、发现数
或集合相等只能证明已有项目没有丢失，不能证明评审通过。

评审不得加入收缩动作，也不得自动调用 `project-doc-contraction`。最终方案只保留有效结论和残余，不保存逐轮推理日志。

## 用户决定与最终保存

证据不能唯一裁决的语义决定，或动作副作用超出当前授权时，一次只询问一项。用白话说明推荐、实际结果、主要代价、
可回退性和简短回复方式；内部字段、路径、ID 和命令只放在必要的技术备注中。用户选择“暂缓”时，受影响切片保持
待决并记录最小解除条件。
