# 项目文档一致性

## 保持职责单一

只维护现有活动文档中的项目事实一致性：先对照证据检查声明，再按用户显式选择决定只报告，或同步能够直接证明的事实正文。

不得创建、移动、重命名或删除文件，不得定义新的路径职责，也不得安装脚本、模板或持久化报告。结构、入口、生命周期和机械门禁问题交给显式调用的 `$project-doc-skeleton`；术语、`CONTEXT.md`、ADR、语义合并和价值取舍交给用户另行显式处理。不得自动调用其他 Skill。

## 选择模式

- `check`：只读检查并报告。用户未指定模式时默认使用。
- `sync`：执行同一检查，并为所有可直接证明的事实修订形成一份集中变更清单；取得确认后才写入。

把“检查、审计、只读核对”等明确理解为 `check`。把“同步、修订、修复可证明事实”等明确理解为 `sync`。同时出现冲突模式或无法判断时保持只读，只询问模式选择。

显式选择 `sync` 只授权准备变更清单，不自动授权写文件、运行命令或 Git 操作。

## 先检查规则和授权

1. 读取目标路径适用的全部 `AGENTS.md`。
2. 遵守项目已有语言规则；没有规则时与用户使用简体中文。
3. 不自动执行构建、测试、产品程序、真实数据、联网操作、commit、push、PR、发布或认证。
4. 不把归档正文当成当前事实，也不因历史内容与现状不同而改写归档。
5. 分别列明文件修改和验证命令。用户可以在一次回复中分别确认，但一类授权不得推定另一类授权。

## 确定检查范围

默认做增量检查：

- 用户指定的文档；
- 当前任务或当前改动涉及的能力；
- 与这些声明直接相关的代码、配置、构建和测试入口。

用户要求“审计当前项目文档事实”“检查全部或所有文档”“整仓检查”“全面审计”时，视为明确要求全量
内容检查。非标准既有项目准备首次迁移时也做全量检查。其他表达默认增量检查。开始调查前先说明采用的
范围；范围不足时标为“未覆盖”，不得推测为正确。

没有文档时报告“无内容可检查”，不得创建骨架。缺少标准入口时只报告结构问题并建议显式调用 `$project-doc-skeleton`。

## 先区分声明类型和真源

先按文档职责区分声明，不把所有 Markdown 句子都当成等待代码证明的同类事实：

- 当前描述性事实：用代码、配置、构建、测试或可观察行为核对；
- 规则、决策和项目内契约：把其明确承接文档视为决定真源，检查其他实现或文档是否与之冲突，不要求用
  代码反向证明“为什么这样决定”；本仓库声明的外部协作接口也先视为项目集成契约；
- 历史记录和动态验证结果：按其时间语境检查；运行通过、候选状态等动态结论需要执行证据或用户确认；
- 待办与方案状态：把活动待办或方案视为当前声明状态的真源。没有完成证据不能反向证明“待确认、待实施”
  等状态错误，只有直接冲突证据才形成内容问题；
- 非穷举摘要：只表达能力边界或流程概览时，不因没有复述源码全部细节而判错。只有文档声称完整、遗漏会
  改变现有表述含义，或其声明职责明确要求该事实时，才把缺失列为问题。

ADR 和归档中的旧名称、旧路径或旧行为不自动构成当前不一致。它们明确作为当前可调用接口或当前契约继续
生效且与现状冲突时，标为“需要决策”；不要在 `sync` 中静默改写历史决定。

## 建立声明与证据映射

调查活动 Markdown 和模块 README，在内存中记录：

- 文档路径和现有事实职责；
- 每项可验证声明；
- 对应项目证据；
- 依据现有职责可以识别的候选承接文档；
- 与其他文档的重复或冲突。

不得自行指定新的文件职责或承接路径。现有职责不足以唯一确定承接文档时标为“需要决策”。

映射缺失事实前，先确认它属于该文档声明的职责和抽象级别，并且补充后不会把长期文档变成代码、Skill
说明或测试实现的镜像。仅仅“源码里存在这个细节”不是文档缺失的证据。

按事实类别选择证据，不采用“代码永远正确”的单一优先级：

- 构建入口和产物：检查构建配置、脚本、用户确认及已获授权的执行结果；
- 当前实现结构：检查代码、配置、schema 和调用关系；
- 用户可观察行为：综合运行行为、测试、需求说明和外部契约；
- 术语和领域边界：检查 `CONTEXT.md` 和用户已确认决定；
- 难以逆转的设计取舍：检查 ADR 和用户已确认决定；
- 测试入口：检查实际 suite、规范命令、fixture、触发条件和覆盖声明；
- 运维事实：检查当前部署、配置和恢复入口。

来源冲突时同时展示证据，不自动让文档服从代码，也不让代码服从文档。测试目录、Registry 格式、测试 ID、执行类别字段和验证层级定义属于机械结构；具体类别、触发条件和命令是否符合项目事实属于内容一致性。

## 使用五种结论

每项声明只使用：

- `一致`：文档与对应证据相符；
- `不一致`：存在可以明确证明的矛盾或会改变含义的缺失，不包括正常抽象或非穷举省略；
- `无法验证`：描述性事实或动态结果证据不足，或未获必要运行授权；
- `需要决策`：代码、需求、测试或文档互相冲突；
- `未覆盖`：不在本次检查范围。

只有明确的全量检查中所有适用项均为“一致”，且没有“无法验证、需要决策、未覆盖”时，才允许给出整体通过结论。

## 执行 check

先说明本次是增量还是全量检查，再在交流中集中报告，不创建项目内检查文件。默认只展开“不一致、无法
验证、需要决策”的发现；“一致”只做简短范围摘要，用户要求时才逐项展开。每个问题包含：

- 文档声明和位置；
- 项目证据和位置；
- 结论与实际影响；
- 现有职责明确时的候选承接文档；
- 推荐的事实修订或结构、语义交接；
- 未覆盖范围。

报告后停止，不修改文件。用户随后明确改用 `sync` 时重新读取相关文件和证据，避免使用失效结果。

## 执行 sync

1. 先完成与 `check` 相同的证据映射和结论分类。
2. 只保留同时满足以下条件的同步项：直接证据充分；属于现有文档职责；现有文字错误、过期、误导，或
   职责明确要求的事实确实缺失；修订符合该文档抽象级别；不会制造重复真源。
3. 非穷举摘要不得仅因省略实现细节而扩写。采用维持准确性所需的最小修订；可以在现有事实正文中最小
   增补、替换，或删除已被直接证明错误、过期的句子，但不得把长期文档改写成源码镜像。
4. 将可同步项与“无法验证、需要决策、结构问题”分开；后三类不得写入。
5. 把所有可同步项合并为一份精确清单，列出每个现有文件、当前声明、证据和最小拟议修订，不逐项反复
   请求授权。
6. 明确列出不会修改的争议项、结构项和未覆盖范围。
7. 取得一次集中修改确认后，只修订清单中现有活动长期文档的事实正文。
8. 修改后另行列出精确验证命令、层级、工作目录、输出和副作用；取得命令授权后再执行。
9. 报告实际修改、验证结果、仍未解决的问题和未获授权的操作。

即使在 `sync` 模式下，也不得修改 `AGENTS.md`、`CONTEXT.md`、ADR、导航、索引、声明的路径职责、待办状态、方案生命周期、Registry 结构或归档关系。需要新增承接文档、移动内容或改变结构时只报告，不实施。

## 控制命令执行

静态证据足够时不运行命令。必须运行构建、测试或程序才能判断时，先列出：

- 精确命令和工作目录；
- 验证层级；
- 输出目录；
- 可能启动的进程、联网或数据副作用；
- 预期回答的问题。

未获授权时将相关结论标为“无法验证”。修改授权不包含命令、commit、push、PR 或发布授权。

## 交接边界问题

- 把路径、入口、导航、数量、待办与方案生命周期、Registry 和归档问题交给显式调用的 `$project-doc-skeleton`。
- 把术语含义、领域边界、`CONTEXT.md`、ADR、需求与实现冲突，以及合并、拆分、归档或删除的价值取舍交给用户另行显式处理。
- 在其他流程完成后重新读取相关文档和证据，再继续 `check` 或 `sync`。
