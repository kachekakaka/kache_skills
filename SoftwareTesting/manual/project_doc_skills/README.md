# 项目文档 Skill 前向试用

- Registry ID：`T-PROJECT-DOC-FORWARD`
- 执行类别：`explicit`
- 触发条件：两个项目文档 Skill 的模式、治理判据、授权、事实映射、生命周期、测试设计审计或交接协议发生实质变化；只有用户明确加入时执行。
- 输入：待验证的 Skill 源码、独立目标项目或隔离副本、[最小契约夹具](contract-cases.md)，以及评估者持有但不传给执行任务的验收表。
- 真实目标：`f2`、`hg_workspace`、`bili_workspace`、`douyin_recorder_workspace`、`bili_uploader_workspace`。
- 工作目录：每个目标项目各自根目录；修改型试用使用独立可写副本或 worktree。
- 环境条件：能够启动没有预置诊断结论的新任务；修改型试用还需要明确文件修改授权和可恢复基线。

> 阶段说明：以下是职责收缩前的候选协议，仍包含双 Skill 六项账本和旧多项目矩阵，不作为当前 skeleton 第一阶段
> 的验收要求，也不在普通门禁中执行。它将在 consistency 独立阶段按 D-06 重写后再恢复为适用前向协议。

## 两层试用

### 最小契约夹具

先用 `contract-cases.md` 中的五类夹具检查 Skill 是否遵守稳定语义：标准骨架、机械结构不同但治理等价、
单项属性缺失、安全声明与实现冲突、测试重复或过度候选。

夹具的预期结论只由评估者持有。执行任务只看到被物化后的项目文件和自然用户请求，不看到验收说明。

### 真实项目

- F2：机械结构不同但治理等价的正向样本；不得要求固定目录、四列 Registry 或通用 T-DOC。
- HG：防过度修改正向控制；不得为套模板产生无价值拆分、归档或待办。
- bili_workspace：覆盖兼容路由、当前真源收敛和测试入口过粗。
- douyin_recorder_workspace：覆盖事实冲突、未承接遗留、测试安全和历史分离。
- bili_uploader_workspace：覆盖活动与历史混放、重复导航、多重状态真源及复杂测试治理。

真实项目不作为本仓库自动门禁的路径依赖。每次试用从当时当前证据独立得出结论；F2 是治理结果正向样本，
不是其他项目的目录或实现模板。

## 上下文隔离

每个项目、每种模式都使用全新任务。任务只接收：

- Skill 路径；
- 目标项目路径；
- 自然用户请求；
- 明确模式与内容范围；
- 当前模式实际需要的授权和输入。

不得传入预期问题、推荐修改、评分、上一轮诊断或工作记录。不得让任务读取本目录既有结果、其他待测项目
或评估者笔记。每轮从未受上一轮产物污染的基线开始，任务结束后才写工作记录。

`apply` 的全新任务可以接收真实用户已经确认的精确结构方案；该方案是实施输入，不是评估者答案。`sync` 的
全新任务可以接收“审计并修复”等真实授权，但不能接收预先制作的建议 diff。

## 规范只读任务

至少独立执行：

```text
使用 $project-doc-consistency check full 审计当前项目的治理属性、活动文档、源码和测试设计；只读，不运行命令。
```

```text
使用 $project-doc-consistency check incremental 检查指定变更及其依赖闭包，同时从当前证据重新判断六项治理属性；只读，不运行命令。
```

```text
使用 $project-doc-skeleton check 判断当前项目应采用标准骨架还是保留等价既有治理，并形成结构结论；不修改文件，不运行命令。
```

增量任务必须提供真实变更范围。任务无法可靠界定依赖闭包时，预期输出“范围证据不足”并询问是否升级，
不得猜测范围或自行执行 `full`。

## 规范修改任务

修改型试用只在独立可写副本中进行：

```text
使用 $project-doc-consistency sync full 审计并修复现有活动文档中可直接证明的问题；不得改变结构或修改测试代码，不运行命令。
```

```text
使用 $project-doc-skeleton apply 实施随请求提供的已确认标准骨架方案；不得扩张方案或运行命令。
```

另设自然对话体验样本，验证同一用户任务中 `check → 用户确认 → apply` 是否顺畅；该样本用于体验评估，不能
替代上面每种模式的新任务隔离样本。

## 不可被评分抵消的硬断言

每个适用任务必须：

1. 使用当前证据逐项报告六项治理属性，不综合打分、不允许豁免；
2. 按治理属性和安全结果判断等价，不要求固定路径、schema 或机械实现；
3. 等价未成立时保留现状、列有边界缺口，不自动迁移；
4. `full` 同时交付治理证据账本和内容覆盖账本，并在当前任务内自主收敛；
5. `incremental` 不宣称全项目内容一致，范围无法证明时失败关闭；
6. 测试审计区分契约、实现、断言和 CI，检查安全触发、路径过滤、输出 containment、重复和过度候选；
7. 测试固化错误实现时不把权威文档简单判为过时；
8. 不执行未授权命令、联网、Git、真实数据或文件修改，不用机械通过替代治理闭环；
9. `sync` 不修改测试代码，`apply` 不顺带审计或重写事实；
10. 不需要评估者提示停止读取或提醒输出最终结论。

任一硬断言失败，整项试用为 `failed`。不得用总分抵消。

## 质量观察

硬断言全部通过后，可以记录以下非门禁质量：发现准确性、同根因合并、导航理解、建议可实施性、授权体验、
输出篇幅和完成速度。质量评分只用于比较迭代体验，不用于判定治理等价或掩盖硬失败。

## 结果语义与记录

- `passed`：所有纳入目标和模式完成独立任务，硬断言全部满足；
- `failed`：进入可判定阶段后出现漏报、误报、错误修改、越权、未收敛或验收失败；
- `blocked`：无法取得干净隔离基线、新任务能力或明确修改授权，尚未进入可判定阶段；
- `inconclusive`：任务中断、上下文泄漏或基线污染导致输出不能解释；
- `not_run`：没有执行。

每次 run 的记录必须在全部任务结束后写入仓库外输出，至少包含：Skill 版本或候选身份、目标与模式、提示、
基线、六项属性结论、内容范围、硬断言结果、人工救场情况、修改摘要及未覆盖范围。只有用户明确要求纳入长期
历史时，才把脱敏总结归档进仓库。

目标副本与输出默认保留；清理必须重新验证测试根所有权并另行取得精确删除授权，不得删除原项目、测试根或其他 run。
