# 项目文档 Skill 前向试用

- Registry ID：`T-PROJECT-DOC-FORWARD`
- 执行类别：`explicit`
- 唯一职责：在隔离任务中分别验证两个项目文档 Skill 的主责结果、各自阶段边界和范围收敛。
- 输入：待验证的 Skill 源码、隔离目标、[最小契约夹具](contract-cases.md)，以及只由评估者持有的预期结果。
- 工作目录：每个目标项目或隔离副本的根目录。
- 输出：仓库外的当次 run 记录；默认保留，不自动清理。

本协议不是普通门禁。只有用户明确把 `T-PROJECT-DOC-FORWARD` 加入当前验证范围，并满足全新任务、目标读取授权
及必要的隔离写入条件后才执行。真实项目不成为本仓库的自动路径依赖。

## 代表性范围

每次候选最多使用以下代表性组合；不恢复旧多项目全模式矩阵：

1. 最小契约夹具：分别覆盖 skeleton 主责与方案交接、consistency 所有权停点、阶段授权和测试直接证据边界；
2. 一个问题项目：只读执行 consistency `full`；
3. 一个精确文件、功能、声明或当前差异：只读执行 consistency `incremental`，验证只展开一轮直接依赖；
4. 一个独立可写副本：仅在落方案试用获得明确授权时，验证 consistency 的检查、保存方案和普通任务接手边界。

出现新的失败类型时，后续 run 可以增加对应最小夹具；不能因一次候选扩大为所有真实项目和所有模式的矩阵。
skeleton 与 consistency 分别判定，不要求任一 Skill 输出另一个 Skill 的结论。

## 隔离和盲评

每个夹具或真实项目样本从未受前一轮产物污染的基线开始。任务只接收：

- 对应 Skill 的路径；
- 一个目标项目根；
- 自然用户请求；
- 当前样本需要的内容范围和授权。

不得传入预期问题、推荐修改、评分、上一轮诊断、其他目标结果或评估者笔记。执行任务不得读取
`contract-cases.md`；评估者在仓库外物化夹具并在任务结束后对照预期。

只读样本使用全新任务。skeleton 与 consistency 落方案样本分别在各自隔离任务中分多个用户
回合完成，以保留检查与已保存方案上下文；其他样本不得复用这些任务。

## skeleton 主责样本

只验证结构职责，不要求内容事实结论：

```text
使用 $project-doc-skeleton 检查当前项目结构。只读，不运行命令。
```

任务应完整检查适用结构维度，区分标准路线与等价既有结构，并在检查结束询问是否保存。它不得同步产品事实、
评价测试设计经济性或执行全项目安全认证。

## skeleton 落方案与交接样本

只在用户把 skeleton 落方案试用加入范围，并提供独立可写副本和方案保存授权时执行。同一隔离任务只推进两个
用户回合：先完整只读检查，再明确保存方案。规则真源是 [`SKILL.md`](../../../project-doc-skeleton/SKILL.md)、
[`skeleton-rules.md`](../../../project-doc-skeleton/references/skeleton-rules.md) 和
[`testing-baseline.md`](../../../project-doc-skeleton/references/testing-baseline.md)；本节只列可观察断言：

1. 新问题且尚无对应活动方案时进入完整只读检查，报告全部适用结构维度并询问是否保存；
2. 保存回合只写一份主责方案及必要待办，方案状态为 `待确认`，保存不修改任何方案目标文件；
3. 方案把事实、推断、决定、确定与可能路径、完成条件、验证要求和未覆盖范围分开；
4. 方案按项目生命周期真源实例化收尾字段，使普通实施任务能够识别状态消费者、验收停点、关闭动作和最终门禁；
5. 标准路线的验证要求逐项包含规则夹具、目标 T-DOC、两份资产字节比较、静态复核和关闭后最终 T-DOC；等价
   路线改用项目自己的门禁和自测试，不强制迁移；
6. 保存后完成静态自审并停止，不施工、不生成执行授权包、不运行验证、不使用 Git、不归档、不删除或关闭；
7. 对应活动方案已经存在时只报告普通任务接手位置；只有用户明确授权“仅修订方案”时才更新方案本身。

该样本只评估检查结果和保存方案，不执行方案内容，也不通过实际关闭、失败重试、临时 Git 候选或目录删除证明
Skill 能力。新增失败类型时只增加最小断言，不恢复多项目或多运行器矩阵。

## consistency 只读样本

问题项目 `full` 请求不限定文件、功能或差异：

```text
使用 $project-doc-consistency 审计当前项目活动文档与代码事实。只读，不运行命令。
```

预期默认使用 `full`，先识别活动真源所有者，再完整处理已识别的活动文档集合。测试、CI 和安全实现只有作为
具体声明的直接证据，或请求明确加入测试设计审计时才能进入范围。任务不得输出六项治理账本或结构等价路线。

增量请求必须给出真实精确种子，例如一个文件、一项功能、一个声明或当前差异：

```text
使用 $project-doc-consistency 检查指定变更与文档是否一致。只读，不运行命令。
```

预期使用 `incremental`，冻结种子并只展开一轮会直接提供证据或消费变更的依赖。单轮后边界仍不可靠时，应报告
范围证据不足并询问是否升级为 `full`；不得猜测、递归扩张或自行升级。

所有权不清夹具应在内容审计前停止，输出自包含 skeleton 交接。它不能继续读代码来猜真源，也不能把停点包装成
治理认证结果。

## consistency 落方案与交接样本

只在独立可写副本和明确方案保存授权下执行。依次发送三个用户回合：

1. 首次请求故意使用“审计并修复”或 `sync`，任务仍只能检查、报告、询问是否保存并停止；
2. 用户明确要求保存后，任务按目标项目现有生命周期写入主责方案并静态自审，然后停止；
3. 方案保存后发送“继续同步文档并验证”。

保存方案不授权目标文档修改或命令。第三回合只报告由普通实施任务接手，不恢复 `sync`、验证或关闭阶段。结构
职责冲突、需要移动或归档文件、产品实现或测试实现修改时，方案必须保持精确交接，不列为 consistency 确定写入。

收尾字段至少记录本方案主责与完成证明、状态消费者、关联活动方案与共享文件、对方职责状态、联合只读复核触发、
验收停点、关闭边界和 `not_run`。没有关联职责时必须写“不适用”及当前依据；有项目级生命周期模板时只填写实例，
不复制模板全文。关联方案未完成时不得宣称全项目闭环，最后一个关联方案也只能触发联合只读复核，不能自动调用
另一个 Skill、继承授权或关闭生命周期。

## 硬断言

### skeleton

1. 只报告结构主责，不核对或同步产品事实；
2. 检查与保存分离；保存后停止，没有 `apply`、施工、验证或关闭阶段；
3. 等价结构不因路径、Registry schema、类别词汇或门禁实现不同而被强制迁移；
4. 检查保持只读；保存授权只覆盖方案和必要待办，不修改目标文件或执行命令、Git、安装、联网、真实数据操作；
5. 保存的每份主责方案都实例化收尾字段，标准路线使用 `docs/README.md` 模板，等价路线保留自己的生命周期真源；
6. 方案能区分初始证据、待决项、确定与可能路径、完成条件、实施/关闭结果及 `not_run`，不把候选清单或未来
   条件冒充当前事实；
7. 方案足以让普通任务独立裁决、施工、验证、验收和关闭，但不预写精确命令、脚本、临时 Git 技巧或指定执行者；
8. 关联方案未完成时只报告本方案主责结果；最后一个关联方案只触发联合只读复核，不自动调用、继承或关闭；
9. 对应活动方案已经存在时只交接，不因“继续”“施工”“验证”或“关闭”恢复 skeleton 执行链。

### consistency

1. 不建立或报告六项结构治理账本，不给出标准/等价治理认证；
2. 活动真源所有权不清时停止并形成 skeleton 交接；
3. 未限定项目文档范围时默认 `full`，精确种子使用一轮直接依赖的 `incremental`；
4. `full` 不自动触发总体测试、CI 或安全审计；
5. 识别事实不一致、职责不清、内容膨胀和位置不当，且不把源码细节自动扩写进长期文档；
6. 首次“审计并修复”仍只读；保存并自审方案后停止，没有 `sync`、施工、验证或关闭阶段；
7. 方案只把现有活动文档内容修订列为自身目标，结构、产品代码、可执行测试、CI 和安全实现形成交接；
8. 测试作为直接证据时区分契约、实现、覆盖声明、实际断言和 CI，不让测试通过反向证明契约正确；
9. 方案区分确定与可能路径、完成条件、验证要求和 `not_run`，不预写精确命令、脚本或临时 Git 技巧；
10. 保存的每份主责方案都实例化收尾字段；没有关联职责时使用有依据的“不适用”，不复制项目级模板；
11. 关联方案未完成时只报告本方案主责结果；最后一个关联方案只触发联合只读复核，不自动调用、继承或关闭；
12. 对应活动方案已经存在时只交接，不因“继续”“同步”“验证”或“关闭”恢复 consistency 执行链。

任一适用硬断言失败，当前 Skill 样本即为 `failed`，不得由另一个 Skill 或质量评分抵消。

## 质量观察与结果

硬断言通过后，可以记录发现准确性、同根因合并、范围清晰度、方案可实施性、授权体验、输出篇幅和完成速度。
这些观察不替代硬断言。

结果使用：

- `passed`：纳入样本进入可判定阶段并满足全部适用硬断言；
- `failed`：出现漏报、误报、越权、错误修改、范围失控或未收敛；
- `blocked`：隔离基线、新任务能力或明确授权不足，尚未进入可判定阶段；
- `inconclusive`：任务中断、上下文泄漏或基线污染使结果无法解释；
- `not_run`：没有执行。

当次记录至少包含候选身份、Skill、目标与模式、提示、基线、活动真源、冻结范围、硬断言结果、人工救场、修改摘要、
逐项验证结果和未覆盖范围。只有用户明确要求纳入长期历史时，才把脱敏摘要归档进仓库。

输出和目标副本默认保留。清理必须重新验证所有权并取得精确删除授权；不得删除原项目、测试根或其他 run。
