# 项目文档 Skill 行为样例

每个 CASE 都是独立、可选的隔离场景。评估用户可观察结果，不匹配逐字措辞、标题、固定问题数量或耗时。

## CASE-EXISTING-GOVERNANCE：成熟项目复用既有治理

目标项目已有不同于本仓库的文档入口、所有者和活动／历史边界，链接有效且没有竞争真源。

自然请求：显式使用 `$project-doc-skeleton` 检查项目文档结构。

预期：

- 完整读取项目入口识别的活动文档，不要求标准文件、Registry、T-DOC 或路径迁移；
- 在已检查范围内没有真实问题时明确报告无问题；
- 零写入、零新文档、零新测试、零方案。

## CASE-BRITTLE-ASSERTIONS：识别脆弱治理断言

目标项目用固定文案、文件白名单、源码 Token、固定数量或性能耗时判断文档治理是否合格，其中至少一项在行为未变时会
因重命名或普通性能波动失败。

自然请求：显式使用最相关的项目文档 Skill 只做审计。

预期：指出具体脆弱性、误报风险和较小替代方向，不把这些断言复制为新的通用标准，也不直接修改测试。

## CASE-NO-DUPLICATE-PROOF：同一行为不重复证明

一项直接测试已经充分证明当前文档声明；CI 和另一套 suite 没有独有消费者或失败模式。

自然请求：显式使用 `$project-doc-consistency` 检查声明与测试证据。

预期：接受现有直接证据，不要求 CI、额外 suite、新 schema 或长期证据记录重复证明。

## CASE-CONSISTENCY-ONE-HOP：一致性只做一层取证

活动文档的一条声明与直接配置冲突；配置被一处测试和一项 CI 引用，但项目还有大量无关源码、workflow 和历史记录。

自然请求：显式使用 `$project-doc-consistency` 检查全部活动文档。

预期：完整检查活动文档，只读取裁决该声明所需的一层配置或直接消费者；报告冲突、影响和可选方向，不修改产品代码，
不继续扫描全部源码、测试或 CI，也不形成架构、安全或测试治理方案。

## CASE-NO-CONSUMER-NO-ASSET：没有消费者就不建设资产

项目准备为很少变化的说明文档新增证据 schema、保留策略和 GC 工具，但没有调用者、已知失败或合理预期故障。

自然请求：显式使用任一相关项目文档 Skill 评估当前问题。

预期：反过度治理门不通过，只给可选替代建议，不建议落长期资产。

## CASE-GOVERNANCE-HEAVIER-THAN-CONTENT：治理设施重于内容

项目为删除少量重复文字准备生成多页审计记录、不可变基线和两轮复审；另一段文字的事实所有者不清。

自然请求：显式使用 `$project-doc-contraction` 检查活动文档。

预期：指出治理成本并建议直接轻量收缩；所有者不清的文字列为保留项，但继续检查其他独立内容；不要求 SHA、干净工作树、
一致性认证或新的审计设施。
