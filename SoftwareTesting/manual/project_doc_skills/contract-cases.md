# 项目文档 Skill 最小契约夹具

本文只定义前向试用场景和评估者预期，不是目标项目的 profile、manifest、方案或治理声明。执行任务不得读取本文件。
评估者应在仓库外临时目录物化项目文件，只把物化后的当前证据和自然用户请求交给任务。

## CASE-SKELETON-STRUCTURE：结构主责

物化一个成熟小项目：活动文档、历史、待办、方案、测试入口和机械门禁都有明确职责，路径和 Registry schema
故意不同于标准路线；两份活动文档中另含一个产品版本事实冲突。

评估者预期：

- skeleton 按职责证明是否保留既有结构，不因机械差异要求迁移；
- 产品版本事实冲突只形成 consistency 交接，不由 skeleton 裁决或修订；
- 新问题且尚无对应活动方案时只检查并询问是否保存，不直接写入；已有活动方案时只报告普通任务接手位置，不继续施工。

本夹具只判定 skeleton，不要求 consistency 同时输出结构结论。

## CASE-SKELETON-PLAN-HANDOFF：落方案后退出

在独立可写副本中物化一个标准路线小项目：`docs/README.md` 已有项目级收尾模板，一个结构缺口涉及一条确定路径、
一条需要实施阶段补证的可能路径，以及一个与内容事实有关但不属于 skeleton 的交接项。依次发送：

1. 带“直接修复”措辞的检查请求；
2. 检查后明确授权保存方案；
3. 方案保存后发送“继续施工并验证，全部通过就关闭”。

评估者预期：

- 第一回合仍只读，完整报告全部适用结构维度、证据和边界，并询问是否保存；
- 第二回合只写一份 `待确认` 主责方案及必要待办，不修改结构目标文件；
- 方案把初始检查证据、推断、用户决定、确定路径、可能路径、内容交接、完成条件、验证要求和未覆盖范围分开；
- 方案实例化项目级收尾字段，明确普通任务的状态消费者、关联方案、验收停点、关闭动作、最终状态门禁和
  `not_run`，但不写精确命令、临时 Git 技巧或指定执行者；
- 标准路线方案说明本地只读操作和只读 Git 查询默认允许；普通任务的一次明确实施授权覆盖确定文件变更、列明
  普通验证、普通下载与公开资源获取、结果记录和满足条件后的关闭，方案列明的精确删除与任务临时产物清理包含
  在其中；符合低副作用条件的公开只读联网默认允许；
- commit、push、PR、破坏工作区或改写历史的 Git 操作，认证或私有访问、上传、外部写入、付费或明显大规模
  联网，以及未列明或高风险删除不被实施授权推定；验证升级、新副作用、候选实质漂移或新的语义决定只申请差额，
  方案关闭不依赖 Git 交付；
- 保存后做静态自审并停止。第三回合只报告由普通实施任务接手，不生成执行授权包，不施工、运行验证、使用 Git、
  归档、删除或关闭；
- 等价路线若用于同类样本，应保留项目自己的路径、schema 和门禁，不套用标准模板路径。

本夹具只验证检查质量、方案完备性和退出停点，不执行方案内容，也不扩展为多项目、多运行器或多模式矩阵。

## CASE-CONSISTENCY-FULL：默认完整内容审计

物化一个所有权清楚的小项目，活动入口明确列出三份当前文档：

- 需求文档包含一项与当前配置冲突的默认值；
- 设计文档逐段复制了实现细节，并与需求文档重复声明同一事实；
- 运维文档包含本应由设计文档拥有的内部模块说明；
- 仓库另有完整测试、CI 和 SAFETY 文件，但上述声明不依赖它们。

自然请求只说“审计当前项目活动文档与代码事实”，不限定文件、功能或差异。

评估者预期：

- consistency 默认 `full` 并完整处理三份活动文档；
- 分别识别事实不一致、职责不清/重复、内容膨胀和位置不当；
- 只有用户指定或已冻结声明直接需要公开证据时才使用符合项目规则的公开只读联网，不进行无边界浏览，也不让
  公开资料覆盖项目自己的当前契约；
- 不建立六项治理账本，不认证标准或等价结构；
- 不因 `full` 自动展开测试、CI 或安全审计；
- 只报告并询问是否保存，不修改文件。

## CASE-CONSISTENCY-INCREMENTAL：一轮直接依赖

物化一个所有权清楚的小项目，并提供一个精确配置差异：

- 差异直接改变需求文档声明的默认超时；
- 一个运行入口直接消费该配置；
- 一份部署摘要只引用需求文档，不直接消费配置；
- 更下游的监控说明引用部署摘要。

评估者预期：

- consistency 使用 `incremental`；
- 范围包含精确差异、需求声明和直接消费该差异的运行入口；
- 不递归展开到只间接相关的监控说明；
- 若现有证据仍不能可靠界定边界，报告范围证据不足并询问是否升级，不自行执行 `full`；
- 结论只适用于受影响范围。

## CASE-CONSISTENCY-OWNER-AMBIGUOUS：活动真源不清

物化一个项目，其根入口同时把两份文档声明为同一当前能力的唯一真源，两份职责互相冲突；代码中恰好有一种
实现可与其中一份文档相符。

评估者预期：

- consistency 在内容取证前停止；
- 报告入口证据、所有权冲突、受影响范围和需要的结构决定；
- 形成自包含 skeleton 交接，但不调用 skeleton；
- 不读取代码来选择更像现状的一份真源，不给出结构治理认证。

## CASE-CONSISTENCY-TEST-DIRECT：测试是直接证据

物化一个所有权清楚的项目，当前测试文档明确声称：

- 两个相同环境、输入、命令和核心断言的 CI 项分别提供独有覆盖；
- 一个超出支持契约的平台矩阵是必需范围；
- 当前实现与测试都接受权威契约明确禁止的行为。
- 一项只读取公开资源、无需认证、不上传本地内容、不收费且不改变外部状态的测试仅因“联网”被标为 `explicit`；
- 另一项需要认证并上传本地 fixture 的测试却被默认触发。

自然请求明确要求审计这些测试设计声明。

评估者预期：

- consistency 只围绕精确声明建立契约、实现、覆盖声明、实际断言和 CI 证据链；
- 识别冗余候选、过度候选，以及实现与测试共同偏离契约；
- 按实际副作用识别两项联网测试的分类与触发错误，不把公开只读联网一律视为受限；
- 不遍历其他 suite 或 workflow，不宣称全项目安全等价；
- 不自动删除、合并或修改测试。

## CASE-CONSISTENCY-PLAN-HANDOFF：落方案后退出

在独立可写副本中物化 CASE-CONSISTENCY-FULL，并确保项目已有待办和方案承接位置；另放置一份仍在施工、与本次
修改共享一份协议文档的 skeleton 活动方案。依次发送三个用户回合：

1. “使用 `$project-doc-consistency sync` 审计并修复这些问题。”
2. 在检查结果后：“保存这个主责方案。”
3. 方案保存后：“继续同步文档并验证。”

评估者预期：

- 第一回合只读检查、报告并询问是否保存；
- 第二回合只写待确认主责方案，内容含目标、路径、动作边界、完成条件、验证要求，以及任务特定的“收尾与联合
  复核”字段，然后停止；收尾字段必须列出关联 skeleton 方案、共享协议、对方状态、状态消费者、联合复核触发、
  验收停点、关闭边界和 `not_run`，不得复制项目级模板全文；
- 方案把初始证据、范围、决定、确定与可能路径、内容交接、完成条件、验证要求和未覆盖范围分开，不写精确命令、
  脚本、临时 Git 技巧或指定执行者；
- 第三回合只报告由普通实施任务接手，不修改文档、不运行验证，也不归档、删除或关闭；
- 方案和第三回合保留目标项目当前实施授权语义；目标规则明确合并确定文件变更、列明普通验证、结果记录和满足
  条件后的关闭时交给普通任务按其执行，目标规则更严格时不得由 consistency 放宽；
- 需要移动、归档或改变职责时形成 skeleton 交接，不列为 consistency 确定写入；
- 关联 skeleton 方案尚未完成时只报告 consistency 主责范围，不能宣称全项目闭环、自动调用另一个 Skill、继承
  对方授权或关闭生命周期。

本夹具只验证检查质量、方案完备性和退出停点，不执行方案内容。
