# 项目文档内容审计

## 保持职责单一

审计文档内容是否符合当前项目事实。支持标准骨架和非标准文档结构，不创建目录骨架、不安装脚本、
不生成模板或持久化审计报告。即使取得事实修订授权，也不创建、移动、重命名或删除文件。

结构、入口、生命周期和机械门禁问题建议用户显式调用 `$project-doc-skeleton`。术语、
`CONTEXT.md`、ADR、语义合并和价值取舍建议显式调用 `$grill-with-docs`。不得自动触发另一个 Skill。

## 先检查授权和规则

1. 读取目标路径适用的全部 `AGENTS.md`。
2. 把显式调用理解为读取与审计授权，不理解为修改、命令执行或 Git 授权。
3. 遵守目标项目已有语言规则；没有规则时与用户使用简体中文。
4. 不自动执行构建、测试、产品程序、真实数据、联网操作、commit、push、PR、发布或认证。
5. 不把归档正文当成当前事实，不因归档内容与现状不同而要求改写历史。

## 确定审计范围

默认做增量审计：

- 用户指定的文档；
- 当前任务或当前改动涉及的能力；
- 与这些声明直接相关的代码、配置、构建和测试入口。

以下情况才做全量活动文档审计：

- 用户明确要求“全量内容审计”；
- 非标准既有项目准备首次迁移，需要职责与事实映射。

范围不足时标为“未覆盖”，不推测为正确。归档只检查是否被错误当成当前真源。

## 识别文档职责

不要依赖固定文件名。先调查活动 Markdown 和模块 README，在内存中形成：

- 文档路径；
- 当前承担的事实类别；
- 每项可验证声明；
- 对应项目证据；
- 依据现有声明职责可以识别的候选承接文档；
- 与其他文档的重复或冲突。

不得自行指定新的文件职责或路径。现有职责不足以唯一确定承接文档时标为“需要决策”。

没有文档时报告“无内容可审计”，不创建骨架。缺少标准入口时只建议显式调用
`$project-doc-skeleton`。

## 按事实类别选择证据

不采用“代码永远正确”的单一优先级：

- 构建入口和产物：检查实际构建配置、脚本及已获授权的执行结果；
- 当前实现结构：检查代码、配置、schema 和调用关系；
- 用户可观察行为：综合运行行为、测试、需求说明和外部契约；
- 术语和领域边界：检查 `CONTEXT.md` 和用户已确认决定；
- 难以逆转的设计取舍：检查 ADR 和用户已确认决定；
- 测试入口：检查实际存在且可执行的 suite 和命令；
- 运维事实：检查当前部署、配置和恢复入口。

来源冲突时同时展示证据，不自动让文档服从代码，也不让代码服从文档。

对于测试文档，只审计具体命令、触发条件、fixture、覆盖声明和交付产物是否符合代码与配置。目录、
Registry 格式、测试 ID、执行类别字段和验证层级定义属于 `$project-doc-skeleton` 的机械职责；测试项
所选类别是否符合实际风险与触发条件仍属于内容审计。

## 不自动运行命令

静态证据足够时不运行命令。必须运行构建、测试或程序才能判断时，先列出：

- 精确命令；
- 验证层级；
- 输出目录；
- 可能启动的进程、联网或数据副作用；
- 预期能回答的问题。

取得独立确认后才执行。未获授权时将相关结论标为“无法验证”。

## 使用五种结论

每项声明只使用：

- `一致`：文档与对应证据相符；
- `不一致`：存在可以明确证明的差异；
- `无法验证`：证据不足或未获运行授权；
- `需要决策`：代码、需求、测试或文档互相冲突；
- `未覆盖`：不在本次审计范围。

只有明确的全量审计中所有适用项均为“一致”，且没有“无法验证、需要决策、未覆盖”时，才允许给出
整体通过结论。

## 报告并逐项处理

先在交流中报告，不创建项目内审计文件。每个问题包含：

- 文档声明和位置；
- 项目证据和位置；
- 结论；
- 实际影响；
- 现有职责明确时的候选承接文档；
- 推荐的事实修订，或需要交给其他显式 Skill 的动作；
- 未覆盖范围。

能够直接证明的事实也不得自动修改。用户要求修订时：

1. 把可直接证明的事实修订与“需要决策”项分开；后者不在本 Skill 内裁决；
2. 列出精确文件变更清单；
3. 取得修改授权；
4. 只修正已确认活动长期文档中的事实正文；
5. 另行列出精确命令并取得命令执行授权后，运行与变更相称的普通验证；未获授权则明确标为未运行；
6. 报告实际结果和仍未覆盖范围。

不得创建、移动、重命名或删除文件，不得修改 `AGENTS.md`、`CONTEXT.md`、ADR、导航、索引、声明的
路径职责、待办状态、方案生命周期、Registry 结构或归档关系。需要这些变化时只报告，并建议显式调用
对应的 `$project-doc-skeleton` 或 `$grill-with-docs`。

修改授权不包含 commit、push、PR 或发布；commit、push 和 PR 分别取得授权。

## 交接语义问题

发现以下事项时只展示证据，建议显式调用 `$grill-with-docs`：

- 术语含义或领域边界不清；
- `CONTEXT.md` 可能混入实现细节；
- ADR 是否需要创建、替代或精简；
- 重复文档应合并、归档还是删除；
- 需求正确但实现可能是 bug；
- 多个真源互相冲突且无法从事实直接裁决。

进入 `$grill-with-docs` 前单独说明其可能即时修改 `CONTEXT.md` 或 ADR，并取得独立授权。完成后重新读取
相关文档再继续审计。

需要结构变化时遵循“审计提供证据 → `$grill-with-docs` 裁决真实取舍 → `$project-doc-skeleton` 实施
结构变化”。没有真实取舍且仅涉及现有文档事实正文时，审计可以在独立授权后直接修订。
