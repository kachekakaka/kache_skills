# 项目文档内容收缩审计与方案

## 职责与退出边界

本 Skill 只负责：

- 在已完成一致性整改和验证的固定提交上确认活动文档、唯一所有者和直接消费者；
- 找出完全重复、换措辞重复、竞争真源、实现／配置／schema／算法／测试细节镜像；
- 找出施工过程、单次 PASS、日期化运行结果、历史快照和失效阶段残留；
- 找出内容错位、聚合入口复制下级命令或矩阵、摘要膨胀、默认入口负担；
- 找出过度复杂、模糊、不精准或前提缺失的表达；
- 为删除、迁移、摘要加链接、合并和简化形成最小、安全、可验证的方案；
- 按用户明确要求交付只读报告，或保存一份纯内容收缩实施方案。

本 Skill **不负责事实裁决或一致性修正**。它不修改当前值、默认值、业务规则、状态、所有权决定、Registry 分类、
运行行为、安全边界或测试义务。发现事实冲突、所有权无法裁决或一致性尚未关闭时，必须标记
`consistency_blocked`，停止该单元的收缩，不得自行决定哪一方正确。

本 Skill 不调用或依赖 `project-doc-consistency`、`project-doc-skeleton`，也不认证项目骨架、不施工、不运行验证、
不归档、不关闭目标项目生命周期。它只报告精确交接点，不自动启动另一项审计。

归档和历史材料默认只提供历史语境；只有活动入口明确继续把它定义为当前合同时，才作为当前活动内容。

以下标准项目级 Agent Skill 根是工具资产，不是活动项目文档：

- `.agents/skills/**`
- `.cursor/skills/**`
- `.claude/skills/**`
- `.codex/skills/**`
- `.opencode/skills/**`
- `.opencode/skill/**`
- `.github/skills/**`

其他 Skill 根只有在用户、适用项目规则或已冻结的精确配置明确声明时才排除。

## 必要前置：一致性基线

实质调查前必须固定一个不可变提交 SHA，并由用户确认两件事：

1. 该提交已经完成项目文档一致性整改；
2. 用户已经做过一致性验证。

不要求用户粘贴验证日志、命令输出、审阅包或 `not_run` 清单；用户确认是本 Skill 接受的前置声明，不表示本 Skill
重新认证一致性质量。

用户未给出 SHA 时，先读取遵守安全边界所必需的适用 `AGENTS.md`，再用只读 Git 取得当前 `HEAD` 的完整 SHA，
把它作为候选基线。用户未指定范围和交付路线时，默认使用 `full` 与只读报告。随后只问一次：

> 我将以当前 HEAD `<完整 SHA>` 执行 full 内容收缩只读报告。请确认：这个提交已经完成文档一致性整改，并且你已经
> 做过一致性验证？回复“确认”即可；若没有，请回复“没有”。如需 incremental 或形成方案，可在同一回复中说明。

不得要求用户按模板填写 SHA、验证证据、`not_run` 边界、范围和交付路线。用户回复“确认”即接受已展示的候选 SHA、
默认范围和默认路线；同一回复里明确指定的 SHA、范围或路线覆盖默认值。用户已经在调用中明确给出 SHA 并确认完成
整改与验证时，不再重复提问。

取得确认后，只读核对：

- 提交可解析且记录精确 SHA；
- 活动入口、待办和一致性方案生命周期没有显示未关闭的阻断；
- 当前工作树或用户要求的审计对象与基线是否一致；
- 当前活动入口没有与用户确认直接冲突的未关闭一致性事项。

用户回复“没有”、无法取得不可变提交、工作树中的活动文档相对候选基线存在未提交修改，或活动生命周期明确显示
一致性尚未关闭时，不开始 `full` 收缩；报告 `consistency_blocked`、最小解除条件和建议交给
`project-doc-consistency` 的精确种子。缺少验证日志本身不是阻断理由。不得自动调用另一项 Skill。

## 请求分流与只读边界

1. 明确只要检查、审计、review 或报告时，直接走只报告路线；报告后停止。
2. 明确要求形成、保存或修订方案时，直接走方案路线。
3. 请求只有 `$project-doc-contraction` 时，按上一节自动识别当前 `HEAD`，默认 `full + 只读报告`，只提出一次一致性
   前置确认；不得再单独追问基线、范围或交付路线。
4. 方案路线未指定自查轮数和反哺报告时，默认“两轮、不生成”，不为默认项额外提问；用户明确给出的值直接覆盖。
5. 新问题始终只读。即使请求含“清理”“精简”“修复”或 `sync`，也不写项目文件、不运行测试、构建、产品、
   门禁或其他动态验证；方案中的动态验证保持 `not_run`。

用户对语义结果的确认不自动授权保存方案、登记待办、转换状态或实施。方案保存必须在最终问题中单独确认，保存后
立即停止。

## 活动所有者与范围

先读取目标路径适用的全部 `AGENTS.md`，再从基线提交中的当前入口和职责声明识别活动所有者。所有权无法唯一裁决时，
对应单元直接 `consistency_blocked`；不得通过移动内容来制造一个看似唯一的所有者。

### `full`

用户未限定文件、主题或差异却要求内容收缩时使用。由基线提交的活动入口和职责声明形成精确活动文档集合，冻结后完整
处理该集合。`full` 不遍历全部源码、测试、CI、历史或归档；只读取能证明所有者、消费者和内容去留的一轮直接锚点。

### `incremental`

用户明确指定文件、章节、声明、重复关系或当前差异时使用。范围只包括精确内容种子和一轮直接所有者／消费者。
直接依赖不递归展开；边界仍不可靠时报告证据不足并询问是否升级为 `full`，不得静默升级。

范围内活动文档必须按基线提交完整读取；大型文件可稳定分块，但不得抽样。**冻结的是文档路径和一轮直接关系，不是
问题发现集合。** 后续评审可以在冻结路径内改变收缩发现和动作，不得静默扩大文档范围。

## 单任务长审计

开始实质审计前完整读取
[`../project-doc-shared/references/long-audit-protocol.md`](../project-doc-shared/references/long-audit-protocol.md)。
按该协议交付 `S000`、`Axxx`、`Cnnn`、累计可恢复尾部和最终索引；同一任务内自动续跑，不因预计上下文或输出不足
停止，也不依赖不可见内部记忆。

`S000` 还必须记录基线提交 SHA、用户对一致性整改和已做验证的确认，以及任何可见生命周期冲突。每个正式审计分片
必须承接下节规定的自然收缩单元四项记录、文档级收缩处置、`consistency_blocked`、新增或改变的发现和残余。

## 收缩审计方法

实质审计前完整读取
[`references/content-contraction.md`](references/content-contraction.md)。

对每份长期活动文档形成以下文档级处置之一：

- `需要收缩`
- `无需收缩`
- `consistency_blocked`
- `需要决策`
- `未覆盖`

`无需收缩` 必须承接全部自然收缩单元且没有未解除残余。`consistency_blocked` 必须列出冲突双方、证据缺口和精确
一致性交接种子；该文档可以继续审计其他互不依赖的单元，但阻断单元不得进入收缩动作。

## 完整性门

完整性门跨 `S000`、全部编号审计／纠正／评审分片、累计尾部和最终索引核对：

1. 基线 SHA、用户确认和可见生命周期前置已经固定；
2. 精确活动路径或内容种子与审计记录一一对应；
3. 每份长期文档的自然收缩单元覆盖全部实质正文；
4. 每个单元都有四项记录或明确 `consistency_blocked`；
5. 每份长期文档都有文档级收缩处置和文档特定依据；
6. 高显著度发现没有终止其余成员或单元；
7. 分片、累计尾部、纠正和下一指针连续，最终只有一个有效结论；
8. 阻断单元没有进入收缩动作。

任一项缺失时先继续交付后续分片补齐；仍不能补齐则标为 `未覆盖`，不得宣称完整范围完成、形成完整方案候选、
计入评审轮次或询问保存。预计篇幅不是 `未覆盖` 理由。标识和数量只用于防止已有项目丢失，不能证明没有漏项。

## 交付收缩报告

完整报告由 `S000`、编号审计／纠正分片和最终总索引共同承接。报告整体至少包含：

1. 基线提交、用户确认和可见生命周期核对结果；
2. 活动所有者、模式、精确路径／内容种子、直接关系和排除项；
3. 每份长期文档独立命名的自然收缩单元、四项记录和文档级处置；
4. 重复、竞争真源、实现镜像、过程／快照、错位、摘要膨胀、默认加载量和表达问题；
5. `consistency_blocked` 交接、需要决策、未覆盖和未获授权操作；
6. 活动真源总内容足迹与默认入口加载量的分别结论。

每个收缩发现写明目标内容、唯一所有者、直接消费者、风险、最小动作和保留事实。只报告路线在完整报告和最终索引
交付后停止。

## 形成与评审方案候选

方案路线只为收缩发现和真实价值取舍形成未保存候选。方案应自包含：

- 基线 SHA、活动所有者、模式、完整性门结果和阻断边界；
- 每项收缩发现的证据、影响、唯一事实归宿和最小动作；
- 确定修改路径、可能修改路径和明确不修改范围；
- 每个确定切片的删除／迁移／摘要加链接／合并／简化动作、一层直接消费者、验证、副作用、完成条件和残余；
- 实施后的最终活动入口、必要链接和新产生一跳关系复核；
- 生命周期承接位置和差额停止条件。

方案包含动态验证、昂贵阶段、产品／GUI／外部环境、证据复用或实施期消费者漂移时，完整读取
[`../project-doc-shared/references/validation-planning.md`](../project-doc-shared/references/validation-planning.md)。

### 方案隔离

**收缩方案只能包含内容删除、迁移、摘要加链接、合并或简化，以及相应验证与生命周期动作。** 不得包含当前事实、
默认值、业务规则、状态、所有权决定、Registry 分类、测试义务、运行行为或安全边界的修正。

任何 `consistency_blocked` 单元都不得进入确定修改范围。方案只报告其交接种子，不自动调用
`project-doc-consistency`，也不把“一致性修正后可能可以删除”写成当前确定动作。没有收缩问题时不创建空方案。

## 收缩方案评审

用户只选择一轮时，同一轮同时完成下述两类记录；选择两轮及以上时：

1. **查漏轮**：固定进入评审时全部 `无需收缩` 文档，逐份回看原始正文和原报告证据。每份记录 `改变` 或
   `未改变`，点名自然收缩单元和原始证据；改变时新增或修正发现，发现事实冲突时改为 `consistency_blocked`。
2. **防误伤轮**：逐项检查全部删除、迁移、摘要加链接、合并和简化，包括第一轮后的变化。确认没有误删唯一事实、
   用户合同、必要决定理由、字段合同、测试特定义务或运维步骤，并确认消费者仍有必要摘要、链接和义务；结论为
   `通过`、`修改` 或 `撤销`。

两类评审都按共享协议形成编号评审分片并自动续跑。评审改变旧结论或动作时，必须交付 `Cnnn` 并在最终索引标记
替代关系。发现遗漏、依据不足、阻断或误伤时，先修订候选并重做受影响记录；修订前结论不计入完成轮次。数量或集合
相等不能证明通过。

## 用户决定与最终保存

证据已经稳定但存在真实保留／简化价值取舍时，一次只询问一项。用白话说明推荐、实际结果、主要代价、可回退性和
简短回复方式；内部字段、路径、ID 和命令只放必要技术备注。事实冲突不形成收缩决策卡，直接
`consistency_blocked`。

完成所选评审轮次后，展示基线、方案目标、保存路径、确定范围、阻断交接、残余和实际完成轮次，再询问是否
“只保存收缩方案，不开始实施”。只有明确确认后才一次写入项目已有承接位置及必要待办；项目没有精确候选状态时
使用 `待确认`，没有承接位置时保存前询问，不自造目录或生命周期入口。保存后机械核对写入内容与候选一致并立即停止。
