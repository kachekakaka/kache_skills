## 8. 有效设计点

- `check` 与 `sync` 的动作词判定清晰，“审计后修复”可以直接归为 sync。
- 先区分描述性事实、契约、历史结果和待办状态，避免把所有旧文档都机械改成当前代码表述。
- “代码不永远正确”的原则在 `Unknown` 冲突中有效：项目契约保持不变，文档披露实现不合规，而不是反向把契约改成 Waiting。
- 禁止修改导航、生命周期和 Registry，保护了结构 Skill 的单一职责。
- 历史报告按 tag 时间语境检查，使隐私过度声明可以有证据地修复，同时保留当时真实 Waiting 行为。
- 集中列出同步清单后一次实施，减少了逐文件确认往返。

## 9. 摩擦、偏差与风险

1. **权威契约与“需要决策”边界不够清楚。** `AGENTS.md` 明确写“不可改变”，架构验收也写严格 Unknown，但代码和测试相反。Skill 一方面要求契约是真源，另一方面又说来源冲突不得自动服从任一方；执行器需要自行判断这是实现不合规而不是用户待决语义。
2. **“最小同步”在空职责文档上缺少尺度。** 骨架刚创建的三份核心文档只有职责句。补齐 139 行当前事实是职责明确要求的缺失，但也可能被认为比“最小修订”更像一次初始化。Skill 没有给出空文档首次同步的篇幅或抽象层级示例。
3. **活动长期文档与历史报告边界模糊。** 最终实施报告仍位于活动目录，既是历史记录又包含长期安全声明。Skill 允许按时间语境核对历史结果，但“只修改活动长期文档”可能被解释为不应改报告。
4. **命令授权发生了推断。** 用户要求除真实取舍外不中断，项目规则要求验证；执行器在集中说明命令后直接运行，没有等待单独回复。严格按 Skill 文本，修改授权不包含命令授权。
5. **临时安装依赖超出严格边界。** Skill 明确不得自动安装依赖；本次为完成验证创建并删除了隔离 venv，仍然发生了联网和写入。更严格的处理应标为 `blocked` 或再次取得明确授权。
6. **全量审计没有可复用证据载体。** Skill 要求映射只保存在内存且禁止持久化报告；82 份 Markdown、代码调用关系和 Git 证据在任务结束后只剩最终摘要，不利于 Skill 优化和后续增量复用。
7. **结构问题只能报告，后续链路容易中断。** 历史计划状态、网页 P3A 文案和 Registry 缺口分别需要 skeleton、代码任务或用户裁决，但 Skill 没有标准化交接包格式。
8. **扩展验证范围容易误伤托管资产。** “仓库 Ruff”与“Skill 资产必须逐字节一致”之间没有自动排除约定，直到验证阶段才暴露。

## 10. 对 Skill 的改进建议

### 优先级 A：结论与真源

- 把来源冲突再分为两类：已有明确权威契约时记为“实现不一致”；没有权威优先级或存在两个有效决策时才记为“需要决策”。
- 明确 `AGENTS.md` 中“不可改变”“必须”等治理契约与普通设计说明、代码和测试的优先级。
- 为“契约正确、实现错误、文档同时需要披露现状”的情况提供标准写法，防止只同步一侧造成误导。

### 优先级 B：授权与验证

- 定义“不要停”“直接完成”等措辞是否包含普通验证命令；不要让执行器自行猜测。
- 对解释器或依赖缺失规定固定结果：默认 `blocked`、允许使用项目已有环境，还是允许在明确隔离目录临时安装。
- 要求在命令清单中把联网安装、临时环境、输出和清理分别列为独立授权项。
- 给出托管机械资产与项目 lint 范围冲突时的规范结论，避免临时缩小或扩大门禁。

### 优先级 C：首次同步与历史材料

- 为“骨架刚创建、职责正文为空”的首次 sync 增加专门模式或示例，规定应补到什么抽象层级。
- 明确定义“活动长期文档”“当前目录中的历史报告”“归档正文”三者的可写边界。
- 允许在用户另行明确要求时导出结构化工作记录，并规定它不属于 sync 自身产物；本文件就是该需求的实例。
- 为全量审计提供可选的临时声明—证据表格式，任务结束后默认不落盘，但可在用户明确要求时保存。

### 优先级 D：交接

- 标准化四类交接：代码不一致、结构问题、语义决策、未获授权验证；每项包含责任流程、证据和下一动作。
- 输出“本轮已同步 / 明确未改 / 仍需实现 / 需要用户决定”四段固定摘要。
- 为发现前端静态文案、CI、Issue/PR 状态等跨边界问题提供清晰的后续任务建议，不自动扩权修改。
