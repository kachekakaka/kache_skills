## 3. 目标与非目标

### 3.1 目标

1. 把 `project-doc-skeleton` 收缩为两个阶段：完整只读结构检查，以及用户明确授权后的方案保存与静态自审。
2. 删除 skeleton 自身的 `apply`、施工、命令授权包、验证执行、重试、归档、删除和关闭编排职责；方案保存后停止并交接。
3. 让每份保存方案在不再次调用 skeleton 的前提下，足以指导普通实施任务完成裁决、施工、验证、独立验收和项目级生命周期关闭。
4. 保留标准骨架与等价既有治理判断、完整结构维度、内容边界、测试治理结构和机械门禁检查，不因减重降低方案准确性。
5. 同步当前能力文档、默认提示和最小前向契约，消除“三阶段 skeleton”与新职责之间的直接冲突。

### 3.2 非目标

- 不修改 `project-doc-consistency`；它是否继续支持 `sync` 由独立方案决定。
- 不改变标准骨架路径、条件目录、导航、Registry schema、T-DOC 规则或等价既有治理路线。
- 不删除项目级验收与关闭契约，不允许文件改完或中途门禁通过后直接宣称完成。
- 不核对产品事实，不评价测试覆盖充分性、重复性或经济性，不执行全项目安全认证。
- 不把施工命令、Git 技巧、临时索引、复制方式、删除命令或特定 agent 写入方案模板。
- 不在本方案保存回合处置现有重叠活动方案，也不施工任何 Skill 或消费者文件。

## 5. 拟定职责结果

### 5.1 skeleton 的运行终点

1. **检查**：显式调用后读取适用规则，冻结有限结构范围，完成全部适用结构维度，报告路线、证据、缺口、待决项、未覆盖范围和推荐。
2. **落方案**：只有用户明确要求保存后，写入一份主责方案及必要活动待办；对保存结果做静态自审，确认方案准确、完整、可执行且边界清楚，然后停止。
3. 保存之后，skeleton 不实施方案、不运行验证、不形成执行授权包、不处理 Git 或临时产物、不验收、不归档、不删除目录，也不关闭生命周期。再次显式调用时，若对应活动方案已经存在，默认只报告应由普通实施任务接手；只有用户明确要求“仅修订方案”时才在新的文件修改授权下调整方案本身。

### 5.2 保存方案的最低完备性

每份有可施工问题的方案至少明确：

- 初始检查证据、证据不足项、本轮未覆盖范围，以及事实、推断和建议之间的区别；
- 每项差异的影响、可选处理、推荐理由和用户决定，未决项及其最小补证或决策条件；
- 目标、非目标、确定修改路径、可能修改路径、明确不修改范围和需要重新冻结范围的触发条件；
- 动作边界、完成条件，以及恰好一次测试层级、验证影响域和具体验证项；
- 实施前置条件、授权类别和验收停点，但不写精确命令、脚本、运行器技巧或绑定某个执行者；
- 按目标项目当前生命周期真源实例化的收尾字段，包括完成证明、状态消费者、关联方案和共享文件、联合复核条件、关闭动作、未运行验证及最终状态门禁。

没有可施工问题时仍使用项目已有检查或历史记录承接规则，不伪造活动待办或空方案。

### 5.3 普通实施任务的接手责任

后续普通任务读取目标项目适用 `AGENTS.md`、已保存方案和项目级生命周期真源，在当前证据下：

1. 补齐待决用户决定并检查方案是否漂移；
2. 分别取得实际需要的文件修改、命令、Git、安装、联网、进程、删除或关闭授权；
3. 按方案施工并只记录真实实施和验证结果；
4. 在验收停点交付独立只读验收，不用中途门禁代替验收；
5. 获得关闭授权后退出活动待办、归档方案、更新索引、处理获批的精确条件清理并运行最终状态门禁。

这些是方案的交接要求，不是 skeleton 的运行步骤；后续任务无需再次调用或安装 skeleton。
