# 设计文档

本文件承接当前实现结构、入口、引用路由、调用关系和验证拓扑。用户可观察合同见
[需求文档](需求文档.md)；完整运行规则由各 Skill 入口及其 references 唯一实现。

## 高层调用关系

```text
显式用户请求
→ 对应 SKILL.md 判断交付路线和必要前置
├─ 裸调用或意图不清：先询问只报告还是形成方案
├─ Contraction 缺少已验证一致性基线：先询问基线并停止
├─ 明确只报告：进入只读报告路线
└─ 明确形成方案：进入只读方案路线
→ 读取目标项目规则和当前入口
→ 内容 Skill 读取共享长审计协议
→ 交付 S000 冻结范围
   → 按文档／对应自然单元交付 Axxx
   → 每个分片以累计可恢复尾部承接全部状态和精确下一步
   → 上下文压缩后从 S000 + 最近尾部恢复
   → 结论变化时交付 Cnnn，最终索引只指向有效记录
├─ 只报告：输出完整报告与总索引 → 停止
└─ 形成方案：按当前 Skill 的两轮评审目标复核
   → 最终保存确认 → 保存一份待确认的单一职责方案 → 停止
   → 全新普通任务按目标项目规则实施、验证和关闭
```

裸调用停点前只允许读取 Skill 自身、共享参考和遵守安全边界所必需的适用 `AGENTS.md`；路线或 contraction 基线
确认前不读取目标项目活动入口。

## 一致性运行结构

Consistency 以自然契约单元核对具体声明、当前所有者／直接证据和一致性结论。稳定一级职责章节至少各形成一个单元，
不得跨章合并成统一“静态吻合”。文档级处置只有 `一致`、`需要修正`、`无法核验`、`需要决策` 或 `未覆盖`。

Consistency 的发现只覆盖事实、契约、状态、所有权、Registry／入口和直接消费者。纯重复、镜像、过程或错位内容只进入
`后续收缩候选`，不产生收缩动作。第一轮评审逐份挑战所有 `一致` 文档；第二轮逐项确认修正不会改变产品语义、权限、
安全边界、测试选择、运行行为或历史决定。

## 收缩运行结构

Contraction 在用户明确指定的不可变提交上工作，并先确认一致性整改和验证已经关闭。自然收缩单元记录内容角色、
唯一所有者／消费者、收缩风险或 `consistency_blocked`，以及最小动作或保留依据。

事实冲突、所有权不清或一致性未关闭时，单元只形成精确交接，不进入动作，也不自动调用 consistency。第一轮评审逐份
挑战全部 `无需收缩` 文档；第二轮逐项防止删除、迁移、摘要加链接、合并和简化误伤唯一事实或必要消费者义务。

## 方案隔离

- 一致性方案只包含事实、契约、状态、所有权、Registry／入口或直接消费者的修正、校准和澄清。
- 收缩方案只包含删除、迁移、摘要加链接、合并和简化。
- 两类方案都可包含本类动作所需验证与生命周期，但不得混合另一类动作。
- 一个 Skill 只能报告另一项工作的精确交接点，不能自动调用、继承授权、继续实施或关闭另一项方案。
- 普通任务实施后只做当前方案的最终入口、确定切片、已列消费者和新产生一跳关系复核，不重跑两个 Skill。

## 长任务恢复结构

`full` 可以在一个用户任务线程内跨多个模型上下文运行。`S000` 固定有序范围；每个正式分片末尾的累计可恢复尾部
紧凑汇总全部已完成处置、进行中单元、有效发现／阻断／残余、替代关系和精确下一步。最近一个可见尾部就是检查点；
活跃上下文只镜像该尾部。

已交付分片不可改写。后续审计或评审改变旧结论时，新纠正分片点名被替代的分片、路径、单元、发现、决定或动作；
最终索引只承接最新有效记录。完整性门既防止路径／单元遗漏，也防止冲突结论同时有效。预计篇幅不构成主动停点。

## 适配边界

- 需求文档是用户可观察合同所有者；Skill 是运行实现；测试入口和夹具是消费者，不能反向定义产品合同。
- 目标项目的 `AGENTS.md`、活动入口、生命周期和授权规则在运行时优先；标准 references 不能覆盖成熟项目的明确规则。
- 项目级 Agent Skill 工具资产按各 `SKILL.md` 的精确路径语义排除；其他同名目录和非标准位置的 `SKILL.md` 不被
  宽泛忽略。
- 三个 Skill 不保存 profile、manifest、版本号、持久评审日志或上次运行结论；范围、累计尾部、纠正和编号报告分片
  只构成当前任务的可见交付，不写入目标仓库，也不供另一个任务续跑。
- 共享目录是安装支持资产，不是第四个 Skill；任何一个内容 Skill 不依赖另一个内容 Skill 的目录。
- 每份综合方案只承接一个审计职责；Skeleton 仍只拥有结构治理。

## 验证拓扑

当前验证分三层：

1. `SoftwareTesting/doc_consistency/` 的标准 T-DOC 和规则夹具检查活动入口、链接、生命周期、Registry、归档和顶层
   Markdown 根所有权。
2. 同目录的 `test_project_doc_skill_responsibilities.py` 检查三个 Skill 的显式调用、共享协议引用、职责隔离、
   `consistency_blocked` 和方案不混合反例。
3. `SoftwareTesting/manual/project_doc_skills/` 的 `T-PROJECT-DOC-FORWARD` 是 `explicit` 前向试用；当前标准矩阵
   继续承接 skeleton 与 consistency 的既有行为，不作为本次职责拆分的机械完成门。

动态结果只由对应活动方案或归档记录承接，不在本设计文档维护。
