# 设计文档

本文件承接当前实现结构、入口、调用链、数据流和适配边界。目标结构和一次性实施步骤不在此维护。

## 模块结构

```text
project-doc-skeleton/
├── SKILL.md
├── agents/openai.yaml
├── references/
│   ├── skeleton-rules.md
│   └── testing-baseline.md
└── assets/SoftwareTesting/doc_consistency/
```

每个 `SKILL.md` 是对应工作流和授权边界的主入口；`agents/openai.yaml` 提供显示信息、默认提示并关闭隐式调用。
两个 Skill 分别携带自身所需判据，运行时不互相调用，也不要求另一个 Skill 已安装。

## 当前阶段模型

ADR-0003 将结构治理与内容一致性重新分开。当前 skeleton 第一阶段施工候选已经落地并处于独立验收前停点；
consistency 仍保持旧候选，等待独立待办施工。两者不保存 profile、manifest、版本号或上次运行结论。

```text
skeleton 新问题
→ 完整只读结构检查
→ 询问是否保存
→ 待确认方案与逐项裁决
→ 再次选择施工
→ 实施中方案与结构写入

consistency 候选
→ 当前仍按旧契约运行
→ 后续独立施工与验收
```

## 骨架处理流

1. 显式调用先进入只读 `check`，完整读取适用协作规则和 skeleton 参考。
2. 冻结有限结构维度和本轮文件集合，在范围内充分读取；完成上下文、结构职责、入口导航、活动/历史、待办/
   方案/记录、测试治理、机械门禁与授权边界全部适用维度，不在首个缺口短路。
3. 全部维度满足时保留等价既有结构；否则保留现状并列出全部已发现结构缺口。标准化迁移只是一个候选处理。
4. 检查结束报告摘要并询问是否保存。明确保存后写一份 `待确认` 方案，不在同一次运行继续施工。
5. 差异裁决完成且用户再次选择施工后，待办和方案转为 `实施中`；实施先建立承接与入口，再退出旧位置。
6. 通用 T-DOC 只在标准路线从资产整文件逐字节复制并比较结果；具体机制施工时决定，不增加永久复制 helper，
   不能保证整文件复制时停止。结构等价项目保留自己的门禁和自测试。
7. 每次申请命令授权前，在对话中建立运行器、工作目录、现有依赖、输出和嵌套副作用的临时验证执行账本；
   自动化、外部副作用或授权选择先给出会发生、不会发生和既有状态三行摘要。
8. 取得命令授权后运行路线适用的普通门禁，并静态 review 工作区差异；未运行的规范验证保持 `not_run`。
9. 用户验收并授权关闭后，按验证记录、待办退出、方案归档与索引、已预授权的精确空目录清理、最终状态
   T-DOC 顺序关闭；中途门禁结果不能替代最终状态门禁。

骨架只读取直接相关的治理证据，不持续核对产品事实，不评价测试设计经济性，也不认证全项目安全。内容问题、
语义取舍和测试实现缺口形成自包含交接包，不产生运行时 Skill 依赖。

施工授权内可以最小修改可与产品行为断言分离的路径、入口、生命周期或自动化副作用结构断言。退出旧入口前
核对引用、默认配置、启动接线、自动化触发、运维入口和这些结构断言组成的直接消费者闭包；出现部署或产品
行为选择时保留上游入口并停止裁决。

## 内容一致性当前候选处理流（待独立收敛）

1. 显式调用后选择只读 `check` 或最小写入 `sync`，并判断内容范围是 `full` 还是 `incremental`。
2. 每种内容范围都重新建立六项整体治理账本；`full` 另建项目内容覆盖账本，`incremental` 建立变更及依赖闭包账本。
3. 增量依赖闭包无法证明时失败关闭并询问是否升级，不猜测范围或静默转为完整审计。
4. 区分当前事实、规则与决定、历史结果、待办状态和非穷举摘要，再按职责映射权威来源、实现和可观察证据。
5. `check` 分别报告治理结论、内容范围及问题；`sync` 只保留证据充分、属于现有职责且不会制造重复真源的最小修订。
6. 已有“审计并修复”等明确授权时，事实性清单说明后直接实施；真实语义取舍逐项确认，修改后再单独申请命令授权。

`sync` 不创建、移动、重命名或删除文件，不改变导航、路径职责、待办状态、方案生命周期、Registry schema、
`CONTEXT.md`、ADR 或归档关系，也不修改可执行测试代码。

## 测试设计审计流

```text
权威需求/设计契约
→ 当前实现与风险
→ 测试义务
→ Registry 或等价选择机制
→ suite 与实际断言
→ CI 选择和安全触发
```

审计按测试义务、层级、运行边界、故障信号、核心断言、成本与触发六维比较测试项，并区分覆盖缺口、声明
错位、有意重叠、冗余候选、过度候选和失效测试。

测试通过不能反向证明实现符合权威契约；实现和测试共同固化错误行为时报告共同偏离。安全审计同时比较：

- SAFETY 中 `explicit`、真实数据和进程约束与 CI push、PR、schedule、手动入口及默认输入；
- workflow 路径过滤与 Dockerfile、锁文件、脚本、契约、suite 文档和 fixture 等真实输入；
- 实际输出根、owner marker、containment、保留和删除实现与安全声明。

静态证据不足时使用“无法验证”。运行、故障注入、mutation testing 或测试代码修改由独立任务另行授权。

## 验证结构

当前验证分两层：

1. `SoftwareTesting/doc_consistency/` 的 T-DOC 与规则夹具只验证本仓库及标准骨架的机械规则；
2. `SoftwareTesting/manual/project_doc_skills/` 是 `explicit` 前向试用入口，当前协议仍待 consistency 独立阶段按
   D-06 收敛；它不属于 skeleton 普通门禁，也不把真实项目变成自动路径依赖。

本阶段普通验证只运行 skeleton Skill 结构校验、T-DOC 规则夹具、本仓库 T-DOC、资产一致性和静态 diff review。
