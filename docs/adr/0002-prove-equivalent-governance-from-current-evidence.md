# 允许用当前证据证明等价文档治理

> 状态：部分被替代。不新增 profile／manifest、允许 skeleton 以当前证据保留成熟等价治理的决定继续有效；
> 两个 Skill 共享六项治理账本的范围由 [ADR-0003](0003-separate-structure-governance-from-content-consistency.md)
> 替代，施工退出与综合方案范围分别以 [ADR-0005](0005-skeleton-ends-after-plan-handoff.md)、
> [ADR-0006](0006-consistency-ends-after-plan-handoff.md) 和
> [ADR-0008](0008-consistency-plan-coordinates-cross-responsibility-slices.md) 为准。

项目文档骨架同时支持标准骨架和成熟既有治理。既有项目不需要为了被识别而新增 profile、manifest、版本号或隐藏状态；每次检查都从当前入口、职责、生命周期、Registry、suite、CI 和机械门禁重新建立证据映射。等价按治理属性和安全结果判断，不要求路径、表格 schema 或机械实现逐项相同。只有全部必要职责能够唯一证明时才判为等价治理，证据不足或存在多个真源时保持待决，不能由项目自行声明等价。

等价判定不采用综合打分，也不允许单项豁免。以下治理属性必须全部由当前证据证明：

1. 当前事实有唯一责任归属和可达入口。
2. 当前事实与历史记录明确分离。
3. 未完成事项有登记、推进与退出机制。
4. Registry、suite、CI 或等价机制能够证明测试选择关系。
5. 命令、Git、真实数据、进程和输出目录受到安全及授权约束。
6. 存在可执行的机械门禁，并能验证门禁自身没有失效。

任一属性缺失、互相冲突或证据不足，均不能判定为等价治理。

## 考虑过的方案

- 所有项目强制迁移到固定骨架：机械规则最统一，但会破坏 F2 这类已经形成成熟项目专用治理的工程。
- 新增治理 profile 或 manifest：识别更快，却引入第二份治理真源、版本漂移和额外维护。
- 每次从当前项目证据证明等价：检查成本更高，但不保存隐藏状态，能够发现治理漂移，并保留成熟既有结构。

## 后果

- 新项目默认采用标准骨架。既有项目无法证明等价时，保留现有结构，只输出有边界的缺口清单和修复方案，不自动套用标准骨架；是否迁移必须由用户另行明确选择。
- 等价判断必须可复核，不能因为路径名称不同而失败，也不能因为项目自称成熟而通过。
- 对已证明等价的成熟项目，`project-doc-consistency sync` 默认在原有治理拓扑内修复其职责范围内的内容缺口；`project-doc-skeleton apply` 只有在用户另行选择结构迁移时才执行。两者均不得自动创建标准路径、替换项目专用门禁或安装通用 T-DOC。
- 检查结束后可以把迁移或更换为标准骨架作为独立可选项，说明收益、代价和影响范围；只有用户另行明确授权后才能执行。
- 每次 `check` 都建立六项治理属性账本；`full check` 另外建立项目范围的内容覆盖账本。`full` 不要求无限遍历仓库或历史：治理属性和适用内容分别取得足以复核的通过、未通过或证据不足结论后即停止，只有证据冲突时才扩展调查。结果必须分别列出治理证据、已检查内容范围、未检查范围及原因。
- 测试审计按“项目声明的权威契约 → 当前实现 → 测试断言 → suite/CI 选择”建立证据链，分别识别实现偏离、测试偏离、覆盖缺口、无新增安全结果的重复测试，以及成本或脆弱性超过独有风险价值的过度测试。测试通过不能反向证明实现符合契约；实现和测试共同偏离契约时，应报告共同偏离，不能简单认定文档过时。
- 安全等价不能只靠文档声明证明。检查必须核对受限操作的实际触发路径和默认参数、CI 路径过滤对真实输入的覆盖及误触发范围，以及脚本实际输出位置、owner marker、路径包含检查、保留和删除行为。只有声明而没有实现证据时，结论必须是证据不足。
- `project-doc-skeleton` 与 `project-doc-consistency` 共享上述六项判据，但运行时互不调用，也不要求另一个 Skill 已安装。前者在建立或迁移骨架前独立判断现有治理能否保留；后者独立执行深入 `check`，并在授权后通过 `sync` 修复缺口。仓库测试负责发现两套判据的语义漂移。
- 验证分为两层：通用 T-DOC 的规则夹具只验证标准骨架机械门禁；Skill 的契约夹具与隔离前向试用覆盖标准骨架、机械结构不同但治理等价、单项属性缺失、安全冲突以及测试重复或过度等情形，断言治理属性和安全结果，不要求固定路径或表格 schema。F2 等真实项目用于隔离的端到端试用和工作记录，不作为自动测试的外部路径依赖。
- 每个真实项目和每种模式必须在全新上下文中独立试用，提示只提供目标和明确模式，不泄露预期结论，也不传入前次分析或工作记录；试用完成后才能写结果记录，未收敛、越权或需要人工救场均视为失败。F2 只作为机械结构不同但治理等价的正向样本，不是其他项目必须模仿的结构基准。
- 用户已明确要求 `sync` 或“检查并修复”时，对当前源码能够直接证明、位于授权范围且属于本 Skill 写入职责的文档修复，不再逐文件重复询问；只有真实语义取舍才逐项询问。全部语义取舍确认后，只进行一次共同理解确认再统一实施，不要求用户确认可以从仓库自行发现的事实。
- `incremental check` 每次仍从当前证据重新核对六项治理属性，因此可以判断整体治理是否等价；内容一致性仅覆盖本次变更及其依赖闭包，只能声明受影响范围一致或不一致。只有 `full check` 可以声明项目范围的内容一致性。
- 增量检查无法可靠确定依赖闭包时，必须判为范围证据不足，列出无法界定的部分并询问是否升级为 `full check`；不得猜测较小范围后判通过，也不得未经同意静默扩大为完整审计。
- 契约明确的覆盖缺口由 `sync` 在允许范围内修订文档、待办或 Registry，并形成精确的测试实现交接，但不修改可执行测试代码；测试实现必须由用户另行授权的实现任务完成。重复或过度测试不得自动删除或合并；只有能够证明失败语义完全相同，且不存在平台、参数、边界或安全差异时，才能提出合并建议，并在说明成本收益和可能失去的独有证明后作为语义取舍另行确认。证据不足时只登记问题。
- `project-doc-skeleton` 只负责新建或用户明确授权的结构迁移，并在修改前判断现有治理是否应保留；`project-doc-consistency check` 负责发现事实、治理和测试一致性问题，`sync` 负责在现有治理拓扑内补充或修订内容。`sync` 不顺带迁移目录，`skeleton` 不承担持续内容审计，不再增加第三个填充 Skill。
- 后续如果引入持久 profile、manifest，或重新要求所有项目使用固定结构，应明确替代本 ADR。
