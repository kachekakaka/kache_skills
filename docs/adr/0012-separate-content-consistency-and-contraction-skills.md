# 将内容一致性与内容收缩拆为两个显式 Skill

此前 `project-doc-consistency` 在一次 `full` 中同时核对事实／契约、判断内容去留、评审删除动作并规划验证。真实大项目
试用表明，这会让事实查漏、内容收缩、测试设计和方案闭环同时争夺注意力：一致性发现可能因收缩矩阵而漏检，纯收缩动作
也会与事实修正混入同一实施方案。

现决定：

- `project-doc-consistency` 只核对事实、契约、状态、所有权、Registry／入口和直接消费者；疑似重复只形成
  `后续收缩候选`，不决定删除、迁移、摘要加链接、合并或简化。
- `project-doc-contraction` 只在用户明确指定、已经完成一致性整改与验证的不可变提交上审计内容去留；遇到事实冲突、
  所有权不清或一致性未关闭时使用 `consistency_blocked`，不自行裁决。
- 两个 Skill 只能显式调用，不自动调用、继承授权或关闭对方任务；一致性方案与收缩方案不得混合。
- `S000`、`Axxx`、`Cnnn`、累计可恢复尾部、上下文续跑和验证规划抽到不含 `SKILL.md` 的共享支持目录；共享参考
  不拥有事实裁决或内容处置。
- 两个 Skill 仍然只读检查，只在最终单独确认后保存一份由普通任务实施的单一职责方案。

这一决定部分替代 ADR-0008。ADR-0008 中“一项审计目标只保存一份自包含方案、方案保存后 Skill 退出执行链”的原则
继续有效；“一致性方案可以统一协调内容收缩等跨职责动作”的范围决定失效。结构治理仍由 `project-doc-skeleton` 独占，
测试设计只在一致性声明确实需要时有界加载。

代价是同一项目通常先完成一致性整改和验证，再在新的稳定提交上单独执行收缩；安装任一内容 Skill 时还需同时安装共享
支持目录。收益是每次审计目标、评审集合、实施方案和验证影响域更单一，事实冲突不会被删除动作掩盖，收缩也不再建立在
未稳定的当前真值上。
