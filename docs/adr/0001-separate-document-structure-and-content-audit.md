# 将文档结构管理与内容一致性处理拆为两个 Skill

项目文档治理拆为两个显式调用的 Skill：`project-doc-skeleton` 只负责目录、入口、生命周期和机械门禁，`project-doc-consistency`（原 `audit-project-docs`）只负责对照项目证据检查事实正文，并仅在独立授权后同步已确认、可直接证明的事实。这样将“发现证据、裁决取舍、实施变化”分开，避免一个 Skill 同时判断内容、决定归属并执行结构修改，也避免修改、命令和 Git 授权在职责之间隐式继承。

## 考虑过的方案

- 合并为一个 Skill：调用较少，但职责会持续膨胀，事实判断与结构实施容易互相越界。
- 拆为两个 Skill 并自动串联：使用较省步骤，但调用方向和授权来源不透明，难以确认哪个阶段获得了什么权限。
- 采用两个显式 Skill：职责和授权边界清楚；遇到无法由证据直接裁决的真实语义取舍时，用户可以另行显式调用外部 `$grill-with-docs`。它不是本仓库维护的第三个 Skill，也不硬编码、调用或替用户选择任何后续 Skill；裁决完成后只说明待实施的动作类别，由用户显式选择后续流程。

## 后果

- 用户可能需要多一次或多次显式调用，以换取可审计的职责、证据和授权边界。
- 骨架 Skill 不判断项目事实，一致性 Skill 不创建、移动、重命名或删除文件。
- 后续可以分别精简或增强两个 Skill；如果要重新合并职责、允许自动串联或改变授权继承规则，应明确替代本 ADR，而不是静默改变边界。
