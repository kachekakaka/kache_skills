# 需求文档

本文件承接当前已交付、用户可观察且可验收的行为和支持边界。尚未实现的事项登记到[已知问题与待做需求](已知问题与待做需求.md)。

## 交付能力

本项目交付两个相互独立、只能显式调用的 Skill。

### `project-doc-skeleton`

- 对单一上下文项目调查现有协作规则、文档入口、测试目录、归档和工作区修改。
- 集中确认互不依赖的未知项，只对存在依赖或冲突的真实取舍逐个澄清；在最终清单确认并取得精确修改授权后，建立或迁移固定与条件文档结构、导航、待办与方案生命周期、归档索引和测试治理结构。
- 从自身通用资产逐字节安装文档机械门禁，并检查固定路径、链接可达性、生命周期、Registry 和归档关系。
- 不判断文档事实是否符合代码或产品行为；发现多上下文结构时停止，不将其压平成单一骨架。
- 不修改产品代码、`CONTEXT.md` 或 ADR 正文，也不创建、检查或清理仓库外测试现场。

### `project-doc-consistency`

- `check` 模式先按文档职责区分当前事实、规则与决定、历史结果、待办状态和非穷举摘要，再对照代码、配置、构建、测试和可观察行为，只读检查标准或非标准文档中的当前事实。
- `sync` 模式先执行相同检查，再在集中清单确认后，以不制造重复真源为前提最小同步现有活动长期文档中可直接证明的事实正文。
- 两种模式都使用“一致、不一致、无法验证、需要决策、未覆盖”报告每项声明，不生成项目内检查报告。
- 不创建、移动、重命名或删除文件，不改变文档结构、导航、生命周期、Registry、`CONTEXT.md` 或 ADR。
- 不安装脚本、模板或持久化报告，也不自动调用其他 Skill。

## 共同授权边界

- 显式调用只授权只读调查或审计，不自动授权文件修改、命令执行或 Git 操作。
- 文件修改、构建或测试命令、commit、push 和 PR 分别取得授权；一个 Skill 获得的授权不会自动传递给另一个 Skill。
- 术语、`CONTEXT.md`、ADR 和无法由证据直接裁决的语义取舍交给用户另行显式调用相应 Skill。
